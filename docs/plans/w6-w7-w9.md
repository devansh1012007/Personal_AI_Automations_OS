**This is the detailed plan for the remaining substrate-track work** in
`docs/MCP_AND_PLUGINS.md` §"The substrate track (W3–W8)" — **W6** (the suites
that would have caught the above) and **W7** (the cleanup the review found) —

document states **the exact changes**, each with the evidence that forces it,

wave structure, the disjoint write-sets and the acceptance criteria** each

**Status: planned, not started.** The baseline at `02f3636` is `ruff` **0**,
`mypy` **0**, **1915 passed / 233 skipped** without a database and **2070 / 78**

### The evidence this plan rests on

All of it was measured on this host against the repository's own code, not
inferred.

* **The S3 path has no error vocabulary at all.** `src/paa/storage/` has no
  `errors.py`; the only neutral vocabulary is `relational/errors.py` — relational
  concepts that cannot express "absent", "forbidden", "unreachable" or
  "corrupt".
* **Raw botocore exceptions escape from six sites** in
  `src/paa/storage/coldlake/minio_backend.py`: `:194-196`, `:197`, `:309-310`,
  `:398-404`, plus `:145-152` and `:362-364`. And `put()` on a missing bucket
  raises a raw `ClientError` while `put_stream()` on the same condition raises
  `StorageError` — a divergence *inside one class*.
* **Every S3 test runs against a stub.** 23 tests, 100 % `StubS3Client`
  (`tests/storage/test_minio_backend.py:34`); the stub has no `head_bucket`, no
  `create_bucket`, no `list_objects_v2`. `boto3` is **not installed** in
  `.venv` and **not** in the `dev` extra.
* **RustFS is not in the repo** — five prose mentions, no image, no service, no
  test. The image *is* on this host (`rustfs/rustfs:latest`, v1.0.3, S3 on
  9000, credentials from `RUSTFS_ACCESS_KEY` / `RUSTFS_SECRET_KEY`).
* **SeaweedFS publishes no host port** (`docker-compose.yml:337-338`) and is
  reachable only at the bridge IP `172.21.0.4:8333` — so a host-side suite must
  start **its own** container, exactly as the PostgreSQL suite does.
* **W7's MinIO half is already clean.** Every `minio` occurrence in a tracked
  file is a deliberate alias, a historical reference, or the deliberately
  un-renamed filename. **Zero** live stale references. The W7 sentence *"the
  `BlobStore` protocol and the cold lake's own store disagree"* is **stale** —
  the signature mismatch was fixed in `03f635a`; what remains is behavioural.
* **`if TYPE_CHECKING:` blocks in `src/paa/`** — the count is **41** at the base
  commit, not 48; and the number that is load-bearing for a **real runtime
  cycle** is **one**, not nine. Both figures were wrong in the first draft of
  this plan, and both were corrected by measurement: an AST sweep over the tree
  plus converting each block one at a time and watching what breaks. The one

## 2. W6 — the suites

### 2.1 T-002 — the parametrised S3 lifecycle and failure-mode suite

The suite runs **the same lifecycle against two independent S3 servers** —
SeaweedFS (the deployment's) and RustFS (a different implementation) — because
the point is not "does S3 work" but "does *this client* work against an S3
server that is not the one it was written against".

* **A test-owned server per session.** Two containers, unique names, published
  loopback ports, a uniquely-named bucket per run
  (`paa_s3_test_{pid}_{uuid8}`, mirroring `tests/storage/conftest.py:55`),
  dropped in teardown. The deployment's `paa-stack-seaweedfs-1` and its
  `paa-cold-lake` bucket are **never** touched.
* **The env convention**, following the house pattern: `PAA_TEST_S3_ENDPOINT`,
  `PAA_TEST_S3_ACCESS_KEY`, `PAA_TEST_S3_SECRET_KEY`, `PAA_TEST_S3_BUCKET`. The
  variable names the **server**; the fixture makes its own bucket. The suite
  **skips** when they are absent — a test that fails for a missing server fails
  for the wrong reason.
* **The marker**: `requires_s3`, registered in `pyproject.toml`, plus an
  `importlib.util.find_spec("boto3")` guard. And `paa[s3]` joins the `dev`
  extra.
* **The lifecycle** (per server): put → get → get_stream → exists → stat →
  delete → dedup (a second put is a no-op) → empty payload → uncompressed → a
  payload above the 1 MiB spool boundary → a unicode digest refused → a
  traversal-shaped digest refused.
* **The failure modes**: missing bucket, missing object, permission denied
  (wrong credentials), endpoint unreachable, corrupt content at the key
  (overwritten out-of-band with a raw client), and a zstd frame that is not a
  frame.
* **On the list step**: the `BlobStore` protocol has **no** list operation, and
  `S3BlobStore` has no `list_objects_v2` call. The decision is **not to widen
  the protocol for a test's convenience** — the suite asserts the object is
  really present and really gone through a **raw boto3 client**, and the
  asymmetry is recorded in ADR-0032. Enumeration is not part of a
  content-addressed store's contract; the CAS's `iter_blobs` is a local-store
  convenience, not a substrate requirement.
* **No mock.** The stub stays for the *unit* tests; the live suite is the thing
  that would have caught the six raw-escape sites.

### 2.2 T-003 — the fetch-images ↔ compose parity, closed

W4's parity test is real, but it has eight holes. The important one is **G1**:
`docker-compose.gvisor.yml` is not in the parity test at all, and the script
has **no merge semantics** — it reads exactly one file — while the documented
gVisor command runs a merged stack the script never sees. Today the two
coincide *by accident*, because the override's `paa` service declares no
`image:`.

| Gap | What it is | Disposition |
|---|---|---|
| G1 | the gVisor override is invisible to the script and to the parity test | **T-003 fixes it** — the script takes compose files, merged in order |
| G2 | the parity test compares two hand-rolled readers, not Compose | **recorded, not fixed** — the module's own docstring already calls it "a shape lock, not an equivalence proof" |
| G3 | the service-name set is duplicated in the test (`pulled == {postgres, redis, qdrant, seaweedfs}`) | **T-003 fixes it** — derive the set, do not hard-code it |
| G4 | nothing pins the image strings; bumping a digest changes the deployment with zero test failures | **T-003 fixes it** — assert every pulled image *is* digest-pinned, not *which* digest |
| G5 | a service with both `image:` and `build:` is exempt from the pin rule, and the exemption is untested | **T-003 fixes it** — pin the exemption as intended |
| G6 | the Dockerfile base images are in neither the compose file nor the plan | **recorded** — they are fetched by `docker build`, not by the script; ADR-0030 already scopes it |
| G7 | the readers' blind spots (`profiles:`, `extends:`, anchors, a multi-line `image:`) are untested | **T-003 fixes it** — the reader corpus gains those shapes |

## 3. W7 — the cleanup

### 3.1 T-001 — the blob substrate gets a neutral error vocabulary *(DEEP)*

ADR-0025 established the rule for the relational substrates: **the translation
happens at the substrate boundary, once, and the repository layer catches a
concept rather than a driver's exception.** The blob substrate never got one,
and the `BlobStore` protocol **declares no error behaviour at all** — which is
precisely why the divergence between `put()` and `put_stream()` on a missing
bucket went unnoticed.

* **A new `src/paa/storage/coldlake/errors.py`**: the blob vocabulary
  (`NotFound`, `AccessDenied`, `Unreachable`, `Corrupt`, `NotSupported`, …),
  every member a `paa.core.errors.StorageError`, each carrying the `substrate`
  that produced it.
* **The translation at the boundary**, mirroring
  `storage/relational/connection.py::translate_sqlite_error` — **idempotent**
  (an error that is already ours comes back unchanged), and it must not
  swallow a `PaaError` that is not ours.
* **The six raw-escape sites closed**, and the `put` / `put_stream` divergence
  on a missing bucket resolved to **one** answer.
* **The `BlobStore` protocol gains an error clause** — what each method raises
  when the object is absent, when the server refuses, when the bytes are
  corrupt. A contract that is silent about failure is what made the divergence
  invisible.
* **The CAS's residue too**: a raw `OSError` from `get_stream`, and a raw
  `zstandard.ZstdError` from a corrupt frame.
* **The `sha256=key` mislabelling** — `_body`'s not-found path passes the
  **S3 key** where the contract says the **digest**.
* **ADR-0032** records the vocabulary, the idempotence rule, the boundary, and
  what was deliberately *not* done (no list operation; no rewrite of the two
  implementations' internals).

### 3.2 T-004 — the `TYPE_CHECKING` leftover

Commit `1c9ffa3` made `memory/creator.py` a **runtime** import of
`RelationalBackend` and left **eight siblings** under `TYPE_CHECKING` — the
same dependency, expressed two ways, inside one family. T-004 converts the
family, which is provably cycle-free (`paa.storage.relational.base` has no
heavy dependency at module scope), and adds a **convention lock** — the same
kind of source-shape assertion W4 wrote for *"the script carries no hand-copied
image table"*. The other ~22 vestigial blocks are **documented and deferred**,
with the cycle proof, because converting them is a separate change to the
import graph and nine of them are load-bearing for reasons the sweep must not
undo.

### 3.3 T-010 — the stale documentation, and the checker that stops it returning

Fixing ~26 wrong `path:line` references without a guard means they rot again
inside a month. T-010 does both: the sweep, and a **docs-reference checker** in
the suite that extracts every `path:line` from `docs/**/*.md` and asserts the
file exists, the line exists, and **the line is not blank** (a blank cited line
is almost always a wrong reference — that is how `cli/main.py:208` and
`daemon.py:61` were found). The sweep covers the five documents W7 names, the
two worst offenders in `docs/operations/`, the three out-of-range references,
README's three contradictory test counts, and ADR-0019's stale paragraph.

### 3.4 Two findings the recon added

* **T-005 (inside 0.1)** — the malformed JSON-Schema keyword value. A
  model-supplied schema with `minLength: "abc"` **crashes** the deterministic
  gate. The fix is a policy, not a patch: a keyword whose value has the wrong
  type is a **schema error**, reported like any other, never a `TypeError`.
* **T-011** — the marketplace's HTTP registry lets the server choose the local
  exception type. The remote body is untrusted: a malformed body must produce
  the project's own error, with the server's text bounded and never
  interpolated into a message that reaches a log. (It is also the largest
  attack surface in the design, per the ROADMAP — worth closing now rather than
  after a storefront exists.)

### The pre-mortem, per wave

* **Wave 1** — *How could this go wrong?* T-001 and T-004 both touch
  `src/paa/storage/coldlake/` and `src/paa/agents/`. ⟹ **T-001 owns the whole
  `coldlake/` package; T-004 owns the eight family files and is forbidden from
  `coldlake/__init__.py`**, whose vestigial block it defers. T-001 and T-003
  both want `docs/deployment/docker.md` ⟹ T-001 does not touch it.
  *Second risk:* T-004 converts eight imports to runtime and creates a cycle
  that only shows up under a specific import order ⟹ the acceptance criterion
  is "every module in `src/paa` imports cleanly in a **fresh interpreter**",
  checked by a subprocess, not by the test session's already-imported state.
* **Wave 2** — *How could this go wrong?* Five agents writing tests at once,
  and the suite's runtime is the shared resource. ⟹ every agent runs only
  **scoped** test files; the full suite is the **gate's** job and it runs only
  when no writer is active. The PostgreSQL-backed tests need a server ⟹ the
  `PAA_TEST_POSTGRES_DSN` convention (each test makes and drops its own
  database); the S3 suite's own containers carry unique names. *Second risk:*
  the agents collide on `pyproject.toml` ⟹ **T-002 owns it alone**; T-009 must
  not touch it.
* **Wave 3** — *How could this go wrong?* The docs checker fails on references
  the sweep did not reach, and the sweep's own edits move a line the checker
  reads ⟹ the checker is written **after** the sweep, in the same task, and the
  improve step is the last change. *Second risk:* the CI workflow's first run
  is red for an environment reason ⟹ the workflow's steps are run locally, in
  order, before the commit.

### The commit plan

One commit per task, in wave order, each message carrying the *measured* "why"
in the body and the trailers (`Task:`, `Agent:`, `Wave:`, `Report:`), then one
docs commit for the records. Each commit's tree is verified **gate-green at
that commit** — the W3–W5 run proved the gate can hold at every commit, and
the property is worth keeping.

### The gate

After every wave, with no writer active:

```bash
.venv/bin/python -m ruff check src tests
.venv/bin/python -m mypy src
.venv/bin/python -m pytest tests/ -o addopts="--strict-markers --strict-config"
```

…and the same three with `PAA_TEST_POSTGRES_DSN` set, and — for W6 — with
`PAA_TEST_S3_*` set against both servers.

**D-1…D-6 were taken as the plan's recommendations.** They are recorded here so
a later reader can see which forks were closed by reasoning and which by
default; a different answer to any of them is a change to the plan, not a
change to the code.

Stated so the boundary is not mistaken for an omission.

  have to discover the substrate's behaviour.

  with the cycle proof**, not silently skipped.
* The `BlobStore` contract does not grow a list operation.

  re-baselined against the real collection in the records commit.
* `docs/MCP_AND_PLUGINS.md` §4's status lines for W6 and W7 are rewritten to
  **past tense** in the records commit, as W3–W5's were.
