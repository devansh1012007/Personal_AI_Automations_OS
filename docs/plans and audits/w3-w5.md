# The W3–W5 execution plan

**This is the detailed plan for the three substrate-track items** in
`docs/MCP_AND_PLUGINS.md` §"The substrate track (W3–W8)": **W3** (entity
resolution is the same answer on both substrates), **W4** (the deployment
fetches what it claims to fetch) and **W5** (the container's start is not
charged to the work).

The track document states *what* each item is for and *why* it matters. This
document states **the exact changes**, each with the evidence that forces it.
Where a design choice was open, the measurement that closed it is recorded
here, because a plan whose reasoning cannot be re-derived is a plan nobody
can check.

**Status: W3, W4 and W5 are implemented and reviewed.** Each of the three
landed with its own ADR (0029, 0030, 0031), its own independent review, and
the review's findings fixed. The "Status" line of each item in the track
document is updated. The sections below are the plan **as it was written**;
where the implementation changed the design, the change is recorded in the
section and the section says so.

### The evidence this plan rests on

All of it was measured on this host (2026-10-21) against the repository's own
code, not inferred.

**FTS5's trigram tokenizer, and the gate's model** (`src/paa/memory/facts.py`):

| Model | Definition |
|---|---|
| The Python gate — **before** this change | the 3-grams of `"  " + lower(collapse_ws(s)) + " "` — two leading spaces, one trailing |
| The Python gate — **after** this change | the 3-grams of `lower(s)` — the raw text, no padding, no whitespace-run collapsing |
| `pg_trgm.similarity()` | **per word, padded**: pg splits the text into words and pads *each one* — `show_trgm('alpha-beta')` = `{'  a', '  b', ' al', ' be', 'alp', 'bet', 'eta', 'ha ', 'lph', 'pha', 'ta '}`. The cross-boundary gram `"t s"` of `"widget service"` is **absent** from pg's set, so pg's gram model is not the gate's. Every word is padded, short ones included: `show_trgm('a')` = `{'  a', ' a '}` and `similarity('a', 'a')` = **1.0**. |
| FTS5's `trigram` tokenizer | the 3-grams of the **raw** text — no padding, no whitespace-run collapsing; case-folded; punctuation kept |

The old gate called itself "deliberately the same shape as
`pg_trgm.similarity`", and for a **single word** it was — `show_trgm('abc')`
is `{'  a', ' ab', 'abc', 'bc '}`, the padded model exactly. Across a word
boundary it is not, and FTS5 is not either. The consequence is the defect:
the gate can accept a pair that shares **no FTS5 token at all**, because the
grams they share are all grams of the *padded* model, and not one of them is
a token the index can hold:

```
term = "aba", candidate = "abba"
  gate score                = 0.5000   (>= 0.34  ->  ACCEPTED)
  shared gate grams         = {'  a', ' ab', 'ba '}   (all three are grams of the *padded* model)
  FTS5 tokens("aba")        = {'aba'}
  FTS5 tokens("abba")       = {'abb', 'bba'}
  intersection              = {}        -> SQLite's MATCH finds NOTHING
```

A brute-force sweep found **67** (term, candidate) pairs the gate accepts and
FTS5's token sets miss. Over a realistic 8-entity corpus, **5 of 18 terms
violated the superset property on SQLite**; the worst was `Widgt Servce`,
where the gate accepts two entities and SQLite's candidate set is **empty** —
so the answer is `None` on SQLite and `Widget Service` on PostgreSQL.

**The tie-break is decided by the engine's arbitrary order.** Two entities
scoring *exactly* 0.625:

```
sqlite  answer: 'Abcy Service'    candidate order: ['Abcx Service', 'Abcy Service']
postgres answer: 'Abcx Service'    candidate order: ['Abcy Service', 'Abcx Service', ...]
```

and the PostgreSQL answer is **not even stable** — the same seven entities
inserted in a different order give `'Abcy Service'`. The winner is a function
of the heap layout, because `bm25` and `similarity` both tie and the gate's
`>=` tie-break takes the *last* maximum.

**The `OR`-token leak.** The same parameter is an FTS5 *expression* on SQLite
and a *literal term* on PostgreSQL, so the second pass compares against the
three-word literal `"Johnson" OR "Alice"` — and `OR` contributes the grams
`"  o"` / `"or "`, which match a large fraction of the table:

```
similarity('["Johnson" OR "Alice"]', 'Doctor')       = 0.0435   > 0
similarity('["Johnson" OR "Alice"]', 'Widget Service') = 0.0667   > 0
```

`'Doctor'` and `'Orchid'` enter the PostgreSQL candidate set and cannot enter
SQLite's.

**The alias scoring.** PostgreSQL scores `similarity(e.aliases, term)` over
the **raw JSON blob**; the gate scores **each alias individually**:

```
similarity('["Gadget Assembly"]', 'Service')  = 0.0000
similarity('Service',                  'Service')  = 1.0000
```

The gate would score that entity's alias `"Service"` at **1.0**; the engine
scores the blob at 0. And the blob is what the `LIMIT` cut ranks by.

**FTS5's tokenizer, measured** (this is what makes the design below work):

```
FTS5 token set of the PADDED form  ==  the gate's _trigrams(padded)   for every sample
FTS5 token set of the RAW form     ==  the raw 3-grams                (by construction)
MATCH '"g1" OR "g2" OR ...'        ==  "the documents sharing >= 1 of these grams"   (exact, all samples)
MATCH '"a phrase"'                ==  "the phrase is a substring of the stored text"  (exact, all samples)
```

**The container's phases, measured** (live Docker daemon, `paa/base_worker:v4.1`):

| phase | duration |
|---|---|
| `docker create` | 165–205 ms |
| `docker start` (returns once the container's process is running) | 530–740 ms |
| the container's **lifetime** (`State.StartedAt` → `State.FinishedAt`) for `sh -c true` | **186–225 ms** |
| the same for `python -c 'print(1)'` | 206–219 ms |
| the same for `python -c 'time.sleep(0.25)'` | 478–548 ms |
| the same for `python -c 'time.sleep(3.0)'` | 3212–3226 ms |

So the container's **fixed** cost (the runtime's setup and teardown, inside
the lifetime, before and after the workload) is **~200 ms**, and the
workload's own duration is additive on top of it. And `docker logs`
**demultiplexes**: a container that writes to both streams comes back with
`MARKER_OUT` on stdout and `MARKER_ERR` on stderr, exactly as `docker run`
does.

**These are the busier of the two hosts the phases were measured on, and
the quieter one answers the same questions differently.** `ADR-0031` records
both: on a quieter host the same measurements, same image, same day, gave
`docker create` 161–194 ms, `docker start` 202–229 ms, a fixed cost of
114–130 ms for `sh -c true` and a 3142 ms lifetime for the three-second
workload. The difference is the daemon's load, not a disagreement about
what was measured — `docker start` is the phase that *waits*, for the
runtime to report the container running, so it is the phase the load shows
up in, while the container's fixed cost (inside the container's own
lifetime) moves by less than half as much. The table above is this plan's
own measurement, and the ADR quotes the busier host's start (530–740 ms)
and fixed cost (~200 ms) for the same reason this plan does: they are the
figures a *loaded* daemon — the case the start grace exists for — produces.

## 1. W3 — Entity resolution is the same answer on both substrates

### 1.1 The contract

Three properties, in the order they matter:

1. **The candidate set is a superset of the gate's acceptance set**, on both
   substrates — for the **ASCII** corpora the suites use; the non-ASCII
   divergence is recorded in §1.6 rather than claimed away. Proved by a test,
   not asserted in a comment.
2. **The gate decides, in Python, identically on both engines.** The gate is
   the authority; the database only decides *which rows the gate gets to look
   at*.
3. **The cut is reproducible.** The `LIMIT` is applied against a total order,
   so the same data gives the same answer on both engines and in any insertion
   order.

### 1.2 The design, and why each piece is there

**The gate's model changes to FTS5's model.** The gate's grams become the
3-grams of `text.lower()` — no padding, no whitespace-run collapsing.

*Why:* the gate must be decidable from what the SQLite index can see. Under
the padded model the gate can accept a pair sharing **no** FTS5 token (the
`aba`/`abba` counterexample above), so no candidate predicate over the FTS5
index can be a superset of it. Under the raw model the FTS5 index is
*exactly* the gate's model on SQLite ✓ — the same 3-grams, character for
character, which the tests assert — and the gate's gram set is the same
measure the portable gram count computes, so the candidate predicate and the
gate agree by construction rather than by resemblance.

*Consequence, stated honestly:* the gate's scores change, and the floor's
meaning shifts slightly away from "the `pg_trgm` default". The gate's
docstring — which says "Deliberately the same shape as `pg_trgm.similarity`" —
is rewritten to state what is now true: the gate uses the same gram model as
the FTS5 index and as the portable count, and it is the **stricter** of the
two engines' measures (measured over 702 pairs from a 27-name corpus: every
one of the 38 pairs the gate accepted at the 0.34 floor was visible to
`pg_trgm`, and `pg_trgm` accepted 14 more that the gate refuses).

**The two candidate queries, each with one unambiguous parameter.** The track
document requires the FTS5 *phrase* and the bare search term to become two
separate, deliberate queries. They are:

| query | parameter | SQLite | PostgreSQL | set |
|---|---|---|---|---|
| the **phrase** | the term's text | `MATCH '"<term>"'` | `lower(col) LIKE '%<term>%' ESCAPE '\'` | the term appears as a substring |
| the **broad** | the term's grams | `MATCH '"g1" OR "g2" OR ...'` | the gram count > 0 | shares at least one gram |

The **broad** one is a superset of the gate's acceptance set — it asks the
gate's own precondition — and the **phrase** one is not. The phrase query is a
*relevance* refinement, not a coverage one: the broad set contains the phrase
set, and the phrase set is a stronger signal — so the repository runs the
phrase query first and falls back to the broad one when the phrase rows
**do not produce a candidate that clears the floor**. The fallback is a
*gate* decision, not a query decision: the phrase query is not a superset of
the gate's acceptance set, so a fallback that ran only when the phrase query
found *nothing* would never show the gate a row it would have accepted.

**Both engines use the *same* predicate, and it is the gate's own
precondition.** A pair the gate accepts shares at least one gram — a Jaccard
of 0.34 needs a shared gram — so "shares at least one gram" is exactly the
gate's precondition, and it is expressed the same way on both engines:

- SQLite: the FTS5 `MATCH` of the term's grams, OR'd. **Measured** to be
  exactly "the documents sharing at least one of these grams", over every
  sample tried.
- PostgreSQL: the same gram count, expressed with the portable `LIKE`
  fragment, tested against zero.

This is stronger than the plan's first draft, which used
`similarity(col, ?) > 0` on PostgreSQL and argued the extra candidates were
harmless because they shared no gram. The extra candidates *are* harmless —
the gate scores them 0 and they cannot change the answer — but that is not
the property a candidate query has to have, and the reason the design
changed is worth recording: `pg_trgm` does not use the whole text as one
unit — it splits the text into words and pads *each word*:

```
show_trgm('abc')          = {'  a', ' ab', 'abc', 'bc '}
show_trgm('alpha-beta')   = {'  a', '  b', ' al', ' be', 'alp', 'bet', 'eta', 'ha ', 'lph', 'pha', 'ta '}
```

The cross-boundary gram `"t s"` of `"widget service"` is **absent** from
pg's set. So the gate's gram set is *not* a subset of pg's, and a pair that
shares only cross-boundary grams is invisible to `similarity()`. A
`similarity > 0` candidate query is therefore answering a *different*
question from the gate's, and the superset property would be an empirical
accident rather than a property of the predicate.

**Measured, the risk did not bite.** A 462-pair sweep (22 names × 21
others, the short-word, tie and typo shapes included) against live
PostgreSQL 16 found **no** pair the gate accepted at the 0.34 floor with a
zero `pg_trgm.similarity`: 16 pairs were accepted by the gate and 26 by
`pg_trgm`, and every gate-accepted pair was visible to the engine. (The
short-word case is *not* the counterexample it looks like: `pg_trgm` pads
**every** word, so `show_trgm('a')` is `{'  a', ' a '}` and
`similarity('a', 'a')` is **1.0**.)

The gate's raw model is the right one for a second reason, then: the gram
count is the gate's **numerator**, so the count expression and the gate must
use the *same* gram model, and the whole-text model is the only one the
count expression can express portably. The gate and the count are now the
same measure, and the candidate query is that measure's own precondition —
so the superset property is a property of the predicate, on both engines,
and it does not depend on `pg_trgm`'s gram model at all.

**The order is a total order, and it is portable for ASCII text.** The
primary key is the gate's *own numerator* — the number of the term's grams
present in the candidate's text — computed with the same expression on both
engines:

```sql
ORDER BY (CASE WHEN lower(e.canonical_name) LIKE ? ESCAPE '\' THEN 1 ELSE 0 END
              + CASE WHEN lower(e.aliases)        LIKE ? ESCAPE '\' THEN 1 ELSE 0 END
              + ...) DESC, e.id ASC
```

`e.id` is the unique secondary key `AGENTS.md` requires for a `LIMIT` cut. It
is a `TEXT` primary key on SQLite and a `UUID` on PostgreSQL, and
`upsert_entity` writes the canonical hyphenated form — whose lexicographic
order is the UUID's byte order — so **the two engines order identically** ✓.
The gate's `>=` tie-break ("the last maximum wins") then becomes
deterministic: among equal scores, the highest id wins, on both engines.

*Why the count proxy and not the engine's own relevance:* `bm25` and
`similarity` rank differently, so an engine-native order would cut a
different set on each engine, and a cut that differs is a cut that can change
the answer. The count proxy is the gate's own numerator and it is expressed
the same way on both engines, and it is the same measure the candidate
predicate uses.

**But the count proxy is the numerator, not the score, and it is portable
only for ASCII text.** The gate's score is a Jaccard — the count divided by
the *union* of the two gram sets — and the union's size varies with the row,
so two rows can hold the same count and score differently: measured against
the term `"widget service"`, `"Widget Services"` holds all twelve of the
term's grams and scores 0.9231, `"Widget Service Platform"` holds the same
twelve and scores 0.5714. A cut between them is therefore decided by the
id, not by the score, and the proxy is a promise about *ordering*, not about
which row the gate would have scored highest. And the count is the same
measure on both engines only where the two engines fold alike: the column's
fold is the engine's (SQLite's `lower()` is ASCII-only, PostgreSQL's is
locale-aware), so outside ASCII the counts can differ — measured, the row
`"CAFÉ NOIR"` against the term `"café"` counts 1 on SQLite and 2 on
PostgreSQL — and the cut is not guaranteed to keep the same rows. See §1.6.

### 1.5 The risk surface

- **FTS5 query-language injection.** The MATCH expression is built from the
  term's grams, each quoted by `_fts_phrase`. Inside a quoted phrase FTS5
  treats `*`, `AND`, `OR`, `NEAR`, `^`, `-` and `:` as literal characters, so
  the quoting holds — *measured*, with the table of hostile terms. If the
  quoting is ever removed, a hostile term becomes an FTS5 *statement* error,
  which is classified as `QueryRejected` and therefore **fails closed** (the
  candidate set becomes empty, the answer is "no match"). The behaviour
  degrades; it does not raise.
- **The NUL.** psycopg refuses the bound parameter outright, with a
  `DataError` carrying no SQLSTATE — which is *not* a `QueryRejected` and
  would therefore **not** be caught by the fail-closed wrapper. The refusal
  in `resolve_entity`, before any statement is issued, is the only thing
  standing between that and the caller. It must not move.
- **A corrupt alias row.** On PostgreSQL the alias expansion
  (`jsonb_array_elements_text((e.aliases)::jsonb)`) raises `22P02` on a
  corrupt row — and because the expansion scans the table, ONE corrupt row
  makes the lookup fail for *every* term.
  **The candidate query does not add to this.** The plan predicted that
  "the candidate query now touches the alias column, so the corrupt-row
  degradation moves from the alias rung to the fuzzy rung" — it does not.
  The candidate query reads the alias column as **plain text**
  (`lower(e.aliases)`) and never casts it to `jsonb`; only the alias rung
  casts it, to expand it. So a corrupt row breaks the alias rung and
  nothing else, and the fuzzy rung still answers. Measured on both
  substrates with one corrupt row in the table: the fuzzy rung resolves the
  term, the alias rung answers "no match". The degradation is total and
  identical on both substrates — which is also why the alias rung carries
  **no `LIMIT`**: with one, the engine could stop at the first match and
  the table-wide expansion would be evaluated for some rows only, making
  the degradation a function of the id order.
- **The count proxy's `lower()`.** SQLite's `lower()` is ASCII-only and
  PostgreSQL's is locale-aware, so for **non-ASCII** text the counts can
  differ, the order can differ, and the cut can differ. See §1.6.
- **The count proxy's cost.** The predicate is O(rows × grams) with no
  index to help it: the column is wrapped in `lower()`, so the `pg_trgm`
  GIN indexes cannot be used by it, and the server's statement evaluates
  the filter twice per row (once in the predicate, once in the `ORDER BY`).
  Measured on PostgreSQL over 20 000 rows: 4 grams 0.057 s, 18 grams
  0.466 s, 45 grams 1.146 s, 132 grams 2.443 s, with `EXPLAIN ANALYZE`
  showing `Seq Scan` and `Rows Removed by Filter: 20000`. For a *short*
  term the new query is faster than the `pg_trgm` one it replaced
  (12.9 ms against 52.9 ms) — the cost is in the long tail.

### 1.6 The limitation this plan records rather than removes

The exact rung (`lower(canonical_name) = lower(?)`) and the alias rung
(`lower(a.value) = lower(?)`) are **not** changed, and they are not
engine-identical: SQLite's `lower()` is ASCII-only, PostgreSQL's is
locale-aware. So the two substrates hold different *key sets* for
non-ASCII names, and they can answer differently.

**The direction of that divergence matters, and it is one-directional.**
PostgreSQL's locale-aware `lower()` sees rows the ASCII-only fold cannot
see at all, so the answers differ in two ways — sometimes one substrate
resolves a term and the other does not, and sometimes **both** resolve the
same entity but report a different match kind and a different score.
Measured, live PostgreSQL 16 and the embedded substrate, the same corpus
in both:

```
stored 'İstanbul'  term 'istanbul'  sqlite: ('İstanbul','fuzzy',0.625)
                                      postgres: ('İstanbul','exact',1.0)
stored 'İZMİR'     term 'izmir'      sqlite: None
                                      postgres: ('İZMİR','exact',1.0)
stored 'éåİ'       term 'éåi'        sqlite: None
                                      postgres: ('éåİ','exact',1.0)
```

So "a non-ASCII canonical name resolves on PostgreSQL and not on SQLite"
is only half of it: for `"İstanbul"` **both** substrates resolve, and they
disagree about *how* — an exact answer on one, a fuzzy guess at 0.625 on
the other. The broad candidate set diverges with it (the term `"izmir"`
offers the row `"İZMİR"` on PostgreSQL and offers nothing on SQLite), so
the difference is not confined to the exact rung.

Closing that needs a **stored normalised form** — a column holding the
Python-computed normalisation — and the backfill for it cannot be written in
SQL (SQLite has no `regexp` to collapse whitespace runs, and its `lower()`
is ASCII-only), so it would need a Python-executed re-index. That is a larger
change than the one this plan makes, and it is the same class of limitation
the exact and alias rungs have carried since the beginning.

**So W3 delivers parity for ASCII corpora** — which is where the corpus, the
floor's calibration and the parity suite live — **and records the non-ASCII
divergence as a known, bounded limitation with its mechanism named.** The
count proxy's use of `lower()` falls under the same limitation, so it is
recorded with it: the count is the same measure on both engines for ASCII
text and not outside it. The follow-up is written down, not left implicit.

## 2. W4 — The deployment fetches what it claims to fetch

### 2.1 The contract

Six separable promises, each of which the current script fails:

| # | promise | today |
|---|---|---|
| C1 | the set of images the script fetches **is** the set compose runs | a hand-copied table; two of the four are **older versions** than compose's (`qdrant` 1.15.4 vs 1.19.2, `seaweedfs` 3.97 vs 4.48) |
| C2 | every pulled image is **digest-pinned** | tags only; the script's own "third field" is dead documentation — no row has it and no code reads it |
| C3 | a download **and its digest check are one attempt** | there is no check at all |
| C4 | a present image is detected by the reference compose uses | the check uses `postgres`, `redis`, `qdrant`, `seaweedfs` — local names that resolve to `:latest` and that the daemon does not have, so **the script fails on every image even when every pull succeeds** |
| C5 | `--load` works for the runtime present; `--list` needs no daemon; the timeout mechanism is portable or the requirement is stated | `--load` is **unreachable** (it consumes two arguments and shifts one → exit 2) and would not `exit` if it were; `--list` needs a running daemon; `timeout` is GNU-only and unstated |
| C6 | a containerised runtime can reach a provider **by either route** (file or shell) | `env_file: .env` delivers the file; the documented `export OPENROUTER_API_KEY=…` is **silently ignored** |

### 2.2 The design

**The compose file is the single source of truth, and the script reads it.**
The script's hand-copied table is deleted. The script parses
`docker-compose.yml` for its `image:` and `build:` values and classifies each
service:

- a service with a **`build:`** section is **built here** — its `image:` is
  the tag the build produces (`paa/runtime:4.1` for `paa` and `paa-init`),
  and the script reports it as built, not pulled;
- a service with **only** an `image:` is **pulled**.

**The parse is dependency-free.** PyYAML is *not* a dependency of this
project — the deployment tests say so explicitly and read the compose files as
text with a regex. The script does the same, in `awk`, and **a test locks the
script's list to the compose file's** (that test is W6's
"fetch-images ↔ compose parity test", and it is the reason a hand-rolled
parser is safe here).

**A pulled image must be digest-pinned, and the script says so loudly.** A
service whose `image:` has no `@sha256:` is an **error**, not a warning: a
tag is a promise about a moving target, and the deployment's own compose file
already pins all four. The pin is read from compose — the script does not
carry a digest of its own.

**The digest check is inside the retry unit.** One attempt is *one pull plus
its verification*, the rule the Dockerfiles already follow:

> The download AND its verification are one attempt, so a corrupt transfer is
> a failed *attempt* rather than a failed build. — `Dockerfile`

The check compares the **digest**, not the repository path: the compose
reference is `postgres:16@sha256:X` but the daemon's `RepoDigests` entry is
`postgres@sha256:X` (no tag), and a mirror changes the path — while a digest
names exactly one image, forever. So the check is "does any of this image's
repo digests end with `@<expected digest>`?".

`.Id` is **not** used: it is the *config* digest, not the *manifest* digest,
and they differ for a multi-platform image. `RepoDigests` is the canonical
source — the repository's own documented refresh procedure uses it.

**`--load <dir>` is made to work, and it stops.** It consumes two arguments,
loads every `*.tar` in the directory with the same retry policy, and
**exits** — today, if it were reachable, it would load the tarballs *and then
pull every image*. A digest check does not apply to a loaded image: a
`docker save` / `docker load` round trip restores the image by its config ID
and cannot restore the manifest digest, so the script reports what it loaded
and leaves the verification to the pull path. That is stated, not glossed.

**`--list` needs neither the docker CLI nor a daemon.** The list comes from
the compose file, so the daemon-reachability gate moves *after* the `--list`
branch.

**The GNU requirement is stated.** The script uses `timeout`, which is GNU
coreutils; the header says so and the script checks for it and fails with a
clear message rather than "command not found" mid-pull.

**`paa-init` gets a `build:` section** — the same context and Dockerfile as
the `paa` service. Today it works only because the `paa` service's build
happens to produce the same tag in the same invocation; starting `paa-init`
alone fails with a pull error.

**The model credential and the `PAA_MODELS__*` settings are forwarded from
the shell.** The compose `environment:` block gains entries with `${VAR:-}`
interpolation:

```yaml
OPENROUTER_API_KEY: ${OPENROUTER_API_KEY:-}
ANTHROPIC_API_KEY: ${ANTHROPIC_API_KEY:-}
PAA_MODELS__LOCAL_PROVIDER: ${PAA_MODELS__LOCAL_PROVIDER:-}
PAA_MODELS__LOCAL_MODEL: ${PAA_MODELS__LOCAL_MODEL:-}
PAA_MODELS__ESCALATION_PROVIDER: ${PAA_MODELS__ESCALATION_PROVIDER:-}
```

Compose's interpolation source is **the shell environment, then the project
`.env`** — so `${VAR:-}` gives the shell export precedence *and* keeps the
file working when the shell has nothing. Measured:

```
# with a shell export
$ OPENROUTER_API_KEY=SHELL PAA_MODELS__LOCAL_MODEL=shell/model docker compose config
      OPENROUTER_API_KEY: SHELL
      PAA_MODELS__LOCAL_MODEL: shell/model
# without one
$ env -u OPENROUTER_API_KEY -u PAA_MODELS__LOCAL_MODEL docker compose config
      OPENROUTER_API_KEY: sk-or-v1-fb0f63c2…      # the .env value
      PAA_MODELS__LOCAL_MODEL: nvidia/nemotron-3-ultra-550b-a55b:free
```

The key names are the registry rows' `api_key_env` values
(`src/paa/models/registry.py`) — the same indirection `StorageSettings` uses
for the S3 store. **No new exposure**: `environment:` sets a runtime variable
on a container, exactly as `env_file:` already does; the image never reads
it, and `.dockerignore` keeps `.env` out of the build context.

## 3. W5 — The container's start is not charged to the work

### 3.1 The contract

> `timeout_seconds` is the wall-clock budget on the step's **work**.
> `container_start_grace_seconds` is the wall-clock budget on the
> container's **start**. The two are enforced independently: a start that
> overruns the grace is a *start* failure, not a work timeout.

The current implementation adds the two together and gives the result to one
timer, so the *workload* may run for `timeout_seconds + grace` — **12× over
a caller's 0.25s budget, reported as `timed_out=False`**. The plan document
records the original measurement: a 0.25-second step took **3.6 s** (the
plan's own "about four seconds", rounded) and was told it had not timed out.

### 3.2 The design, and the measurement that forces it

**`docker run` is one opaque call.** It creates, starts, attaches, waits and
tears down inside a single `proc.communicate()`, so the backend **cannot
observe where the start ends and the work begins**. That is why the
implementation had to be additive, and it is the thing any real fix has to
solve. The fix is to use the daemon's own accounting:

```
docker create  →  docker start  →  docker inspect  →  docker wait
                →  docker logs  →  docker inspect  →  docker rm -f
```

- `docker start` returns once the container's process is running ⟹ **the
  start boundary is observable**;
- `docker inspect` gives `State.StartedAt` (the daemon's own clock — the
  same clock the host has) ⟹ the work deadline is computed from the daemon,
  not from the client;
- `docker wait` returns the exit code ⟹ the work phase is bounded;
- `docker logs` **demultiplexes** (measured: `MARKER_OUT` on stdout,
  `MARKER_ERR` on stderr) ⟹ the stream separation survives;
- `docker rm -f` replaces `--rm`, because the logs must still be there after
  the container exits.

**The two budgets.**

| budget | bounds | enforced by | reported as |
|---|---|---|---|
| `container_start_grace_seconds` | the `docker create` + `docker start` calls | a `wait_for` around each call | `start_duration_ms` |
| `timeout_seconds` | the container's **lifetime** (`StartedAt` → `FinishedAt`) | the kill at the work deadline | the duration in the result |

**The work deadline is `StartedAt + timeout_seconds`**, in the daemon's clock.
The kill is issued when the wait exceeds it, and the container is killed with
`docker kill` — the same path the current code uses, because killing the
*client* leaves the container running and holding the workspace bind mount,
which is precisely the orphan the timeout exists to prevent.

**The fixed cost is charged to the caller, and that is the honest answer.**
The container's lifetime includes the runtime's setup and teardown —
**~200 ms, measured** (a `sh -c true` container's lifetime is 186–225 ms on
the busier of the two hosts the phases were measured on; 114–130 ms on the
quieter one) —
which is *before* and *after* the workload's own execution. The subprocess
backend charges its own ~5 ms fork to the caller today; the container backend
charging its ~200 ms setup is the same rule at a different scale. The
workload's duration is not separately observable — the daemon reports the
lifetime, and that is what the budget bounds.

**Consequence, and it is a policy change: the modality profiles' budgets are
raised.** A SIMPLE step's budget is 0.25 s, and the container's fixed cost is
~200 ms — so a 0.25 s budget cannot accommodate even a trivial container
step, and a 0.25 s *workload* needs a ~450 ms lifetime. **SIMPLE goes from
0.25 s to 1.0 s** (five times the measured fixed cost). STANDARD (10 s),
COMPLEX (30 s) and MAX (unbounded) are unchanged.

The trade-off, stated plainly: a SIMPLE step's blast radius grows from 0.25 s
of container time to 1.0 s. The *wall clock* barely changes, because the
container's start (530–740 ms on the busier of the two hosts, 202–229 ms on
the quieter one — measured) is most of what the old quarter-second step
spent — and that start is no
longer charged to the work. **This is the one consequence in this plan that a
reviewer should push back on, and it is the one thing here worth a
deliberate decision rather than a default.** The alternative — leaving the
profiles alone — makes every SIMPLE step fail on the container backend,
because the fixed cost alone exceeds the budget.

**`duration_ms` keeps its meaning** — the total wall clock, and the sandbox's
own measurement of the two phases together. The ranking signal is a
*different* field of the same name: the improvement loop
(`improvement/optimizer.py`) reads `duration_ms` from the *run record*
(`hot_serving_execution_runs`), which `observability/runs.py` computes from
the run's own `started_at`/`ended_at` and never from `SandboxResult.duration_ms`.
The two only share a name, so redefining *this* field would not change a
ranking signal — it is left alone because a total that silently stops
counting the start is not a total. The *start* is reported separately, in
`start_duration_ms`.

**`killed_reason` gains a value.** `"timeout"` means the *work* overran;
`"start_timeout"` means the *start* overran the grace. They demand opposite
responses — the first is a workload problem, the second is a host problem
(the daemon is slow, the image is missing, the runtime is not registered) —
and today the result cannot tell them apart. The interaction with the memory
detection (`exit_code == 137 and not timed_out ⟹ "memory"`) is ordering-
sensitive: a container killed by the *start* grace also exits 137, so the
start timeout is checked **first**.

**The other backends are honest about the setting.** The subprocess and WSL
backends have no container start phase — a `fork`/`exec` is milliseconds, and
the WSL2 VM start happens in the (cached) healthcheck, not per run. They
**ignore** `container_start_grace_seconds` entirely rather than adding it to
something, and say so in their `preflight`/`describe` output. A setting that
only one backend honours must not be silently applied to the others.

The gate must be green at **every** commit, and the count is now **zero** —
so a commit that fixes one section and leaves another broken would not be
green. The split is therefore by *concern*, not by file:

1. `fix(memory): the candidate set is a superset of the gate's, on both engines`
   — W3, with ADR-0029.
2. `fix(deploy): the script fetches what compose actually runs`
   — W4, with ADR-0030.
3. `fix(sandbox): the container's start is not charged to the work`
   — W5, with ADR-0031 and the profile change.
4. `docs: the substrate track's three items, and what they cost`
   — the plan document's status lines, the ADR index, and the module docs.

Each commit carries the ADR that explains it, because "a deviation from the
RFC without an ADR is a review failure" — and a review cannot be conducted
against a diff whose rationale is in a later commit.
