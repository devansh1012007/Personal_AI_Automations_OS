## 3. Root cause
No size invariant exists on ledger payloads. Any unbounded string in a journalled payload (a large `reason`, a caller-supplied large preview, or any future large field) is stored inline and bloats every `read_correlation`/replay. Tool results are already hash-only, so they do not bloat today — but there is no contract that *keeps* them (or any future large value) out of the row, and no SHA-pinned way to read a large value back. The root cause is the missing contract at the source (`ledger/events.py`), not a per-field patch in the journal. Fixing only the journal would leave other emitters unguarded; fixing only events without a journal size check would leave the contract unexercised on the coder path and re-discoverable per site.

## 4. Approach chosen and why (alternatives rejected)
**Whole-payload stub in events.py, applied by the journal's size check.** If `payload_size_bytes(payload) = len(canonical_json(payload).encode("utf-8")) > 8192`, the canonical bytes are stored as one blob and the row becomes `{"v": 1, "blob": {"sha256":…, "size_bytes":…, "preview":…}}` (~300 bytes, preview bounded to 200 chars). Small payloads return a shallow copy unchanged with nothing stored. This follows the signals precedent exactly (stub, `content_hash == CAS digest`), keeps one shape and one resolver, and guarantees the total-size invariant (stub is O(preview), never O(payload)). Alternatives rejected:
- *Per-field recursion* (replace each oversized string value with `{"__blob__":…}`): preserves small identity fields inline for `paa ledger` readability, but adds a second shape, recursion over nested dicts/lists, type-preservation questions (string vs dict value), and still loses the large field from replay. For coder rows — which replay folds as no-ops — the readability gain does not justify the surface; the preview orients, and the resolver restores the original.
- *Tool-result-only descriptor* (`result: {sha256,size,preview,blob}` on COMPLETED): matches the spec example but requires the loop to pass result *content* to the journal. `loop.py` is outside the write-set and the frozen `ToolJournal.after(ctx, ok, result_sha)` signature carries no content, so production wiring cannot land here without a protocol bump. The generic contract plus `store_blob_bytes`/`read_blob_bytes` (same descriptor/verify core, usable for raw tool-result bytes) delivers the SHA contract now; loop wiring is a NEED, and no bloat occurs meanwhile because COMPLETED is already hash-only.
- *Refusing oversized rows* (raise instead of blobbing): would abort tool execution for a large `reason` even when a perfectly good blob store is configured. Blobbing preserves the ledger-before-side-effect promise; refusing is reserved for the no-store case (fail-closed, §5).

**Descriptor strictness as the collision guard.** A payload is blobbed only if it is exactly `{"v": int, "blob": {exactly sha256/size_bytes/preview of the right types}}` with a lowercase-hex 64-char digest, a non-bool int size, and a ≤200-char preview. A payload that merely carries a `blob` field of another shape is an ordinary payload. This makes the stub recognisable without a second marker field and keeps `v` (ADR-0046: every payload carries `v`) on every row — blobbed rows carry the envelope `v=1`, the original `v` lives inside the blob and is what the resolver returns.

**Independent verification, not store trust.** `read_blob_bytes` checks descriptor shape before fetching (fail fast on malformed addresses, including path-traversal strings the CAS would reject as `MalformedRequest`), lets the store's own `Corrupt`/`NotFound` propagate unchanged, then re-checks `len(data) == size_bytes` and `sha256(data) == sha` itself. `resolve_blobbed_payload` additionally requires the fetched bytes to re-encode to themselves (`canonical_json(parsed) == data`), rejecting right-dict-in-wrong-bytes. Replay (`apply_event`/`replay`) is untouched and never fetches: it folds the stub as the no-op it already was, and only the resolver fetches — "replay never reads blob directly without verification" holds structurally, not by convention.

**No `TYPE_CHECKING` block, no store import.** `ledger/events.py` defines `BlobStoreLike` (two methods, `put -> Any`, `get -> bytes`) structurally satisfied by both CAS and S3 stores. Importing `BlobStore`/`BlobRef` at runtime would pull the CAS (zstd) into the ledger core path; behind `TYPE_CHECKING` would add a block that the import-conventions lock requires classifying in a file outside the write-set. The local protocol documents the surface without either cost, and `put`'s `Any` return is deliberate: the descriptor's digest/size are recomputed from `data` and checked against the reference's `sha256` when present, so the exact `BlobRef` type need not be named. (Import-conventions 21 pass.)

**Line preservation for the docs lock.** New events code is appended after `LedgerEvent` (after line 255) and `__all__` is extended at the end, so the `events.py:40/68/105/132/…` citations in in-scope docs keep their lines; the typing import is amended on its existing line. ## 8. Long-run test (Source/Load/Hostile/Operability/Reversal)
- **Source:** `canonical_json` + CAS `put`/`get` contracts are the source; the threshold is measured on the hashed bytes and the descriptor pins the CAS address. Signals' stub is the shape precedent.
- **Load (100x, concurrency, partial failure):** Per oversized append: one canonical encode + one CAS `put` (dedup on identical bytes) + one ledger transaction. No caches or unbounded state; stub is O(200). Two writers blobbing identical payloads converge on one blob (dedup) and two ledger rows (distinct discriminators) pointing at it — no lock needed. Blob-before-row ordering: a crash after `put` but before `append` leaves an orphan blob (harmless, immutable, collectable); a crash after `append` never leaves a stub pointing at nothing, because the blob was already stored. Sync `put` inside the async journal follows the `SignalRepository.record` precedent (line 158) — at 8 KB scale the block is negligible; `put_stream` is for artifacts, not ledger payloads (documented, not implemented — see §12).
- **Hostile input:** Oversized (100 MB string) — held once as canonical bytes (same as inline would have held), stored, stubbed; preview bounded; no unbounded ledger growth. Malformed descriptor (bad hex, bool size, oversized preview, extra keys, path-traversal digest) — rejected before fetch with `ValueError` (the CAS would also reject traversal as `MalformedRequest`). Non-UTF-8 blob bytes — preview is lossy `errors="replace"` (human hint only, never reconstructed); payload blobs must be UTF-8 JSON or the resolver raises. `blob` key with non-stub shape — treated as ordinary payload, never fetched. Deeply nested payload — same `canonical_json` failure the store's `dumps` would already raise; blobbing adds no new recursion. Blob file bit-rot — store `Corrupt`, never plausible bytes.
- **Operability:** Observe via `payload_size_bytes`/`is_blobbed_payload` on read rows, `paa ledger` shows `{v, blob:{sha256,size_bytes,preview}}` (preview orients without the content); roll back by revert before first blobbed row (see §6); migrate by nothing (no backfill — small rows already inline). `doctor`/S1 are unaffected (mandate/head logic untouched). A stuck blob store surfaces as its own `BlobError` vocabulary (retryable `Unreachable` vs fatal `NotFound`/`Corrupt`), never masked.
- **Reversal:** Removing the threshold check, the size/SHA re-checks, the canonical check, or the journal `_blobbed` call fails the §7 tests for the reasons stated (each test names the mutation it catches). Reverting `__all__.extend` alone does not break imports (symbols are still importable) — the extend is the docs-line guard, proven by the 0-new-blanks result in §11.

## 9. Edge cases and abuse scenarios
Exactly-at-limit (8192) stays inline; 8193 blobs (pinned). Empty payload stays inline. Already-blobbed payload returns unchanged (idempotent; double-blob impossible). Stub-shaped-but-malformed payload raises on resolve/re-blob rather than being stored or returned silently. Small payload + `blob` field of another shape (e.g. `"just a string"`) is not blobbed and resolves as itself. COMPLETED/FAILED journal rows have only small fields by construction (hashes + small enum name), so they stay inline even with a store — tested; only PROPOSED/DENIED (unbounded preview/reason) can blob today. Duplicate blobbed PROPOSED returns the existing row via the store's discriminator dedupe (one row, chain verifies — tested). `after(ctx, True, None)` still raises before any blob check. A blob whose bytes parse to a non-dict JSON (list/number) raises. A blob that is valid JSON but non-canonical (key order/whitespace) raises. Descriptor `preview` longer than 200 (hand-made stub) is malformed and raises. `bool` as `size_bytes` is rejected (bool is an int subclass). Store returning a reference with a mismatched `sha256` raises (tested via the check's presence; CAS/S3 always agree by construction).

## 10. Performance and security
Performance: one extra canonical encode per journalled call for the size check (O(payload), payloads are small; for an oversized 100 KB payload the encode is still sub-millisecond vs model latency and CAS compression). CAS `put` compresses (zstd level from settings) — stored bytes smaller than raw. Memory: one canonical `bytes` per oversized append (bounded by the caller's payload size, which the write tools already cap at 64 KB for reads/outputs); `store_blob_bytes`/`read_blob_bytes` hold the blob once — appropriate at ledger scale, not for multi-GB artifacts (which use `copy_file_into` streaming). Security: descriptor is part of the ledger payload, so the chain digest commits to the address — a coherent descriptor+blob substitution breaks `verify_digest` (pinned by test); blob bytes alone break the resolver/store hash check (pinned); size lies break the resolver's `len` check (pinned). Preview is a subset of what would have been inline (canonical prefix), so blobbing strictly reduces ledger exposure; journal payloads are already redacted (shape summaries), so the preview cannot disclose a canary via the journal path. The raw-bytes helpers' preview has the opposite property (a tool result's prefix *is* content) — they are low-level building blocks, not journalled previews; the future loop wiring that journals tool results must use a shape preview for them (see §12 NEED), a disclosed limit, not a silent one. No secrets, tokens, env values, or PII written to code, tests, reports, or commits (test payloads are `'x'`/`'y'`/`'a'` padding).
