The LIKE guard fires for missing-or-old and is silent once the new trigger lands - the guard-on-effect form for a trigger replacement.

## Long-run test answers (per standing orders)
- **Source:** Guard-on-effect honored structurally - 4 steps, each with its own guard(s): add-canonical, add-aliases, FTS sync (3 trigger guards), backfill (data guard). The backfill's guard asks "does any row lack a norm?" - a state only the backfill produces - so the crash-mid-step test (nullable columns + NULL rows) fails without the Python loop. The FTS guards ask "does the trigger already insert the norm?", not "does the trigger exist?", so an old trigger cannot satisfy them. `python` field is called only when its guard fires.
- **Load (100x, concurrency, partial failure):** Backfill is a full-table read-then-update per NULL row - O(rows), no unbounded loop beyond the table. Concurrency: runner holds the advisory lock / exclusive SQLite writes for the whole migration; upsert read+write are one transaction so two writers of one name serialise on the write lock (tested via `asyncio.gather` - same id, merged aliases, norm consistent). Partial failure: steps + version row are one transaction on both engines; a crash rolls back to v5, and the next start re-runs to the same end state. Idempotency: once at v6, `pending()` is empty; guard-level test proves every v6 guard is satisfied (returns no row) on a v6 database.
- **Hostile input:** norm columns carry no CHECK (any folded text is valid). The LIKE helper still owns every pattern (no f-string patterns at call sites); the backfill binds via `?` params; NUL refusal and the 400-gram ceiling stay in `resolve_entity` before any statement (tested). FTS5 quoting unchanged (seam-only). The backfill never interpolates user text into SQL - canonical/aliases are bound params.
- **Operability (observe, roll back, migrate):** observe via `SELECT version FROM schema_migrations` + `SELECT COUNT(*) FROM hot_serving_entity_index WHERE canonical_name_norm IS NULL`. Roll back = code falls back to raw columns (columns ignored one-way, per plan §K one-way rule - the rows and raw blob are untouched). Migrate: v5->v6 deterministic Python fold, no Settings flag (a flag would let two deployments backfill differently under one version).
- **Reversal (which test fails if the fix is reverted?):** Remove v6 -> `test_schema_version_is_six`, v5->v6 backfill, guard, crash, shape, and the PG gated test fail. Remove the Python loop (leave guards) -> crash-mid-step rows stay NULL. Revert dialect columns to `lower(raw)` -> éclair test fails (SQLite alias-branch mismatch), İZMİR broad test fails (SQLite empty), CAFÉ NOIR exact test fails (fuzzy not exact). Revert `_seed` norm -> parity repaired tests fail (NULL-invisible). Remove one SQL file's columns -> `test_schema_parity` column-set test fails.
