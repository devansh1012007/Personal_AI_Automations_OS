## 3. Root cause

The script's *plan* is a projection of the compose file, and the projection had **one
input** where the deployment has **many**. `docker compose -f a -f b up` composes a
merged model; the script composed nothing, it read a file. Everything else follows:

* the script could not be pointed at the gVisor stack, so it never saw it;
* the parity test compared two readers over the same single file, so it could not
  notice that the deployment's stack was a merge;
* the expected service set was written down in the test, so the test had no way to
  *derive* what the compose files say — it asserted a snapshot.

The accident (the override declares no image) hid the defect completely: the merged
plan and the base plan were identical, so "the script reads the base file" and "the
script reads the merge" were indistinguishable from the outside.

## 4. Approach chosen and why

**The script merges, and the merge is a documented subset that refuses the rest.**

Alternatives considered and rejected:

* **Use `docker compose config` to get the merged model.** This is what a reader with
  a YAML library would do, and it would close G2 as well. Rejected: it makes `--list`
  require the Docker CLI, and the whole point of `--list` is that it is a report
  about a *file* — available on a host with no Docker at all, which is what makes it
  usable as a CI gate (ADR-0030). It would also replace the hand-rolled reader with a
  dependency the project deliberately does not have (PyYAML is not a dependency; the
  deployment tests say so and read the compose files as text).
* **Read the override as a separate file and union the two plans.** Rejected: it is
  not a merge. The gVisor override's `paa` service *replaces* parts of the base `paa`
  service; a union would keep the base's image even when the override declares one —
  which is exactly the failure the task is about.
* **Implement Compose's whole merge.** Rejected: it is a deep, well-specified
  algorithm, and a shell/awk implementation of it would be wrong in a dozen ways that
  no test would catch. The brief asks for the subset the repository's files use, plus
  a refusal for the rest, and that is what this is.
* **Add a `PAA_COMPOSE_FILES` variable for the several-file case.** Rejected: D-1
  names the flag, `PAA_COMPOSE_FILE` stays the single-file spelling, and one spelling
  per shape is one less contract to document, scrub and get wrong. **No new
  environment variable was introduced**, so the test's scrub list did not have to grow
  (see §7).

**How this addresses the cause and not the symptom:** the reader takes a *list* of
files and produces the merged projection, and every shape the merge does not
implement is a **refusal** — a loud failure — instead of a silent wrong plan. The
parity test then drives the merged stack, so the merge itself is under test rather
than assumed.

## 8. Long-run test

* **Source.** The reader reads the operator's own files and nothing else. The paths
  are resolved once, checked with `[ -f ]`, and handed to `awk` as arguments (never
  interpolated into the program text). The `awk` program's only inputs are the file
  contents; the only output is rows on stdout. The refusal messages travel back as
  rows so the **shell** owns the wording of an error — the awk program never writes
  to the terminal behind the script's back (and never to `/dev/stderr`, which would
  truncate a redirected stderr file).
* **Load.** The plan is a handful of rows; the merge is O(services) per file. The
  string accumulation in `build_plan` is O(n²) in the number of services, which is
  six today and would be noticeable at a few thousand — irrelevant for a compose
  file, and I would not pretend otherwise: it is a shell script reading a file a
  human wrote.
* **Partial failure.** A missing compose file stops the plan before anything is
  fetched. A refusal stops it the same way. A failed *pull* is a failed **attempt**
  (unchanged), and the digest check stays inside the retry unit (unchanged).
* **Hostile input.** A compose file is operator input, but it is also the input a
  *supply chain* could touch. The reader treats it as text and refuses what it does
  not understand (anchors, aliases, tags, `extends:`, `include:`, multi-line
  images) rather than guessing. A path with spaces or a newline in it is quoted
  everywhere it is used (`"$2"`, `"${COMPOSE_FILES[@]}"`).
* **Operability.** `--list` still needs neither the CLI nor a daemon, so the plan is
  inspectable on a host that cannot run it; the merged plan is exactly what the
  fetch will do. The refusals name the file, the service and the construct. The
  profile exclusion names the service.
* **Reversal — which test fails if the merge is reverted?**
  **`test_an_image_added_to_the_gvisor_override_changes_the_plan`** is the one to
  name: it takes the repository's own `docker-compose.gvisor.yml`, gives its `paa`
  service an `image:`, and asserts the plan follows it. Revert the merge (read one
  file, or drop the merge from the reader) and that test fails, because the plan
  would still carry the base file's image.
  `test_the_merged_plan_is_what_the_fetch_pulls` is the second: it fails if the
  merge reaches the report but not the fetch.
  `test_the_merged_stack_is_the_stack_the_script_reads` is the third, and it is the
  one that would catch a merge that is wrong in a way the other two do not.

## 9. Edge cases and abuse scenarios

**Handled:**

* a file that does not exist → refused, by name, before anything else;
* a directory passed to `--compose` → refused (the check is `-f`);
* the same file given twice → idempotent (the merge of a file with itself is itself);
* an empty compose file → contributes nothing (no rows), and a plan that is empty
  overall is refused as a broken source of truth;
* a service with neither `image:` nor `build:` → not a row (unchanged);
* an `image:` with no value → `-`, and the "declares an image: with no value"
  refusal (unchanged);
* a reference that is a variable → refused (unchanged);
* a carriage return on every line → stripped (unchanged);
* trailing whitespace after an image value → **stripped** (new): a pull reference
  with a space on the end of it names no image any registry has heard of, and the
  `--list` output cannot show it, because the list is parsed;
* an anchored service key → refused (new): otherwise the reader would attribute the
  keys below it to the *wrong service*;
* a profile-gated service → excluded and announced (new).

**Consciously not handled:**

* `profiles: []` (an empty list) is treated as "gated", because the rule is the
  key's *presence*. The consequence is over-exclusion — one image not fetched — and
  it is **announced on stderr**, so it is not silent. The alternative (parsing the
  list, and its block form, in two hand-rolled readers) buys a degenerate case at
  the cost of two more places to get wrong. Compose's own treatment is the other way
  round (`[RAN docker compose -f prof.yml config -> a service with 'profiles: []'
  IS in the model]`), so this is a known, documented divergence in the degenerate
  case.
* A `profiles:` list in one file and a service with the same name in another: the
  exclusion is the **union** — if any file gates the service, it is gated. Compose
  replaces the key when a later file declares it; the difference only shows when a
  later file declares an *empty* profile list, which is the case above.
* `extends:` is refused rather than resolved: resolving it means resolving a
  service *map* from another file, which is a second merge.
* The script does not read `.env` and does not interpolate compose variables
  (unchanged, ADR-0030).

**Unknown:** how Compose merges a `profiles:` *sequence* in the presence of an
override is a detail of Compose's specification that this implementation does not
reproduce exactly. It is documented in the ADR amendment as the subset it is.

## 10. Performance and security considerations

* **Performance.** One `awk` invocation for all the files (not one per file): the
  merge is done inside the reader, so the shell never has to join rows. The plan is
  read once per run, as before.
* **Security.** The script still touches the local image store and nothing else; the
  allowed `(verb, subcommand)` set is unchanged and still asserted as *exactly* that
  set. No container is touched, no network call is made that was not made before.
  The reader refuses the shapes it does not understand, which is the security-adjacent
  property here: a compose file is an input, and a wrong plan is a wrong fetch.
* **The refusal path runs before the daemon gate**, so a file the reader does not
  understand is refused on a host with no Docker at all — the same property
  `--list` has.

## 13. Out-of-scope findings

1. **`deploy/fetch-images.sh`'s `usage()` breaks when the script is invoked by a
   *relative* path.** It does `sed -n '2,/^set -euo/p' "${BASH_SOURCE[0]}"` after
   `cd "$REPO_ROOT"`, so the relative path no longer resolves and the usage text is
   not printed: `[RAN bash old-script.sh --help -> "sed: can't read old-script.sh:
   No such file or directory"]`. Pre-existing, harmless in practice (the script is
   invoked as `deploy/fetch-images.sh`, and the operator's shell is at the repo
   root), and it is not in my scope — but it is a real defect in the same file.
   Reported, not fixed.
2. **The script resolves a relative compose path against the REPOSITORY ROOT, not
   the caller's working directory** (`[VERIFIED old-script.sh:109-113]`, unchanged by
   this work). An operator running the script from elsewhere with
   `--compose ./my-compose.yml` gets the repository root's file — and, if there is
   none, a "no such compose file" error naming a path they did not write. It is the
   pre-existing `PAA_COMPOSE_FILE` semantics, kept for compatibility, and it is now
   documented in `docs/deployment/docker.md`.

## 14. Known limitations, risks, rollback notes

* **G2 is NOT fixed, and this is deliberate.** The parity test still compares **two
  hand-rolled readers** — the script's `awk` and this module's Python — and not
  Compose itself. It is a *shape lock* on the current files, exactly as its own
  docstring says: two readers can agree about one file and disagree about the next.
  The corpus mitigates that; it does not remove it. The way to remove it is
  `docker compose config`, and that would make `--list` require the Docker CLI —
  which is why it was not done. **This is recorded, not fixed.**
  What *was* done is a **manual, one-off cross-check** of the merge subset against
  Compose v5.6.0 on this host (§2) — a verification recorded in this report, not a
  test, because a test that needs the Docker CLI would take a dependency out of a
  suite that is deliberately dependency-free, and because adding one would be
  quietly fixing G2, which the brief says to record and not fix.
* **G6 is NOT fixed, and this is deliberate.** The Dockerfile base images are in
  neither the compose file nor the plan; they are fetched by `docker build`, not by
  this script, and ADR-0030 already scoped the script to the compose file's
  services. **Recorded, not fixed.**
* **The merge subset is a summary of Compose's merge, and Compose's merge is not
  frozen.** If Compose changes how it merges a service map, this subset does not
  follow automatically — it follows when somebody notices, and the parity test is
  what makes the noticing cheap.
* **The refusal set is a maintenance surface.** A sixth compose feature that
  changes the image set has to be added to it deliberately, or it becomes a silent
  wrong answer again. It is written down in the ADR amendment and in the reader's
  own comments for that reason.
* **Rollback:** the change is one commit (`954705d`) and touches no `src/`, no
  schema, no configuration contract. Reverting it restores the single-file
  behaviour and the old hard-coded test expectations; nothing else in the tree
  depends on the flag (no caller in the repository invokes the script).

## 15. Where I am least confident / what the reviewer should scrutinise

1. **The `profiles:` rule.** "The key's presence gates the service" over-excludes
   `profiles: []` and a null `profiles:`. I chose the simple rule because both
   readers would otherwise have to parse a list in two shapes, and because the
   exclusion is announced. If the reviewer disagrees, the change is local to the two
   readers and one test.
2. **The merge subset's fidelity to Compose.** I implemented "a later file's
   `image:` replaces an earlier file's; a later file that says nothing about
   `build:` leaves it alone" from the compose-spec's key-by-key merge rule. It is now
   **checked against the real Compose** (§2): the subset matches Compose v5.6.0's
   behaviour on every shape the repository's files use, including the one the gVisor
   case rests on. What remains unverified is Compose's behaviour on shapes *outside*
   the subset — which is exactly why they are refused rather than approximated. The
   residual uncertainty is small but not zero: the subset was verified against **one
   Compose version** on one host, and Compose's merge is not frozen.
3. **The `!` custom-tag check.** It fires on any `image:` value starting with `!`.
   A legitimate image reference cannot start with `!` (Docker's reference grammar
   allows only lowercase alphanumerics and `.`, `_`, `-`, `/`, `:`, `@`), so the
   check cannot misfire on a real reference — but it is a *syntactic* judgement, not
   a parse.
4. **The refusal of an anchored service key.** `  postgres: &pg` is refused. A
   compose file that anchors a service and then *aliases* it elsewhere would
   otherwise have its keys misattributed. I judged the refusal safer than the
   misattribution; a reviewer might prefer "ignore the anchor and read the block",
   which would be a small change.
