# Implementation report — W1-IMPL-01 — T-001 the blob substrate gets a neutral error vocabulary

## D1. Design decision record (written BEFORE coding)

> This section was written before `minio_backend.py` was edited, as the brief requires.
> If the design changed during implementation, the change is recorded in §1a below with the
> reason.

### The problem, in one sentence

The blob substrate has no error vocabulary: `src/paa/storage/` has no `errors.py`, the
`BlobStore` protocol declares no error behaviour at all, the S3 path lets a raw
`botocore` exception escape from six sites, and **the same condition — a missing bucket —
arrives as two different exception types depending on which method the caller used**
(`put()` raises a raw `ClientError`, `put_stream()` raises a generic `StorageError`).

### The constraints this design has to satisfy

| # | Constraint | Where it comes from |
|---|---|---|
| C-1 | `botocore` is **not installed** in this venv and **must never be imported at module scope**. The substrate is an optional extra (`paa[s3]`), and a laptop install has no `boto3` at all. | `AGENTS.md`; the brief's trap list |
| C-2 | The unit tests must pass **without `boto3`**, against the existing duck-typed `StubS3Client`. | the brief; the live S3 suite is wave 2's (T-002) |
| C-3 | The translation must be **idempotent** — an error that is already ours comes back unchanged — exactly as `storage/relational/connection.py::translate_sqlite_error` is. | the brief; ADR-0025 |
| C-4 | A `PaaError` that is **not ours** must not be swallowed or translated. | ADR-0025: "the boundary translates the driver's errors and nothing else" |
| C-5 | Every member of the vocabulary is a `paa.core.errors.StorageError`, so every existing `except StorageError` keeps working. | the brief's §9; ADR-0025 |
| C-6 | `PaaError.to_payload()` merges `details` **verbatim** into a ledger payload, so the details must be **identifiers**, never text that could carry a credential. | the brief's trap list |
| C-7 | The `BlobStore` method **signatures** are already correct and pinned by `test_blobstore_contract.py`; they are not to change. | the brief's skip list |
| C-8 | The `BlobStore` contract does **not** grow a `list` operation (decision D-6). | `docs/plans/w6-w7-w9.md` §6 |
| C-9 | `minio_backend.py` is not renamed and `boto3` is not added to the `dev` extra (T-002 owns `pyproject.toml`). | ADR-0026; the brief |
| C-10 | ruff (`line-length = 100`, bandit `S` on) and mypy (`strict`, `warn_unreachable`) must both stay at **0**. | `AGENTS.md` |

### The invariants the implementation has to establish

* **I-1** — No driver's exception escapes `S3BlobStore` or `ContentAddressedStore`. Every
  exception that leaves either implementation is a member of the blob vocabulary (all of
  which are `StorageError`s) or a `PaaError` that is not ours and is not translated.
* **I-2** — The **same condition** produces the **same type** on both substrates and on
  every method of a substrate. A missing bucket is one answer, not two.
* **I-3** — The translation is idempotent, and it does not swallow a `PaaError` that is
  not ours.
* **I-4** — The `BlobStore` protocol **states** the error behaviour, and a test proves the
  two implementations agree with it.
* **I-5** — A caller's `except StorageError` keeps catching everything it caught before
  (C-5), and a caller who wants the *kind* of failure can now catch it.

### The options considered

#### Option 1 — one vocabulary module + one shared translator, S3 dialect beside it

`storage/coldlake/errors.py` holds the vocabulary and the substrate-neutral translation;
`storage/coldlake/minio_backend.py` holds the S3 error-code table and the S3-specific
classification. This is the shape ADR-0025 established for the relational substrates:
`relational/errors.py` (vocabulary) + `connection.py` / `postgres.py` (one translator per
dialect). **Chosen.**

#### Option 2 — one vocabulary module + one translator that also holds the S3 table

Everything in `errors.py`. Rejected: it makes the "neutral" module know the S3 dialect,
which is the one thing ADR-0025's *dialect seam* exists to keep separate, and it puts the
S3 error codes two files away from the S3 client that raises them.

#### Option 3 — translate at the call sites (each `except` block decides)

Rejected: it is the bug, not the fix. Six sites × two implementations is twelve places to
keep in step, and it is exactly the shape that produced the `put`/`put_stream` divergence.

#### Option 4 — keep the driver's exception and add a *marker* to it

Rejected: the caller still has to import the driver to catch it, which is the property
ADR-0025 exists to remove, and `boto3` is not installed on a laptop.

#### Option 5 — mirror botocore's own hierarchy in the vocabulary

Rejected: botocore's classes are not importable (C-1) and are not stable across
versions; and the vocabulary would then be a copy of a driver, not a set of *concepts*
a caller can act on. The relational seam made the same call.

#### How the translator recognises a driver exception without importing the driver

This is the crux of the brief's second trap, and it has three candidate answers:

* **(a) `isinstance` against `botocore.exceptions`, imported lazily inside the
  classifier.** Rejected: it makes the classification *depend on whether the driver is
  installed*. The same exception would be classified by two different code paths in the
  unit suite (no botocore) and in wave 2's live suite (botocore present), so the unit
  suite would not be testing the code the deployment runs. It is also the reason the
  existing `_is_not_found` is structural.
* **(b) The error *code* only** (`response["Error"]["Code"]`). Necessary but not
  sufficient: botocore's *connection* failures (`EndpointConnectionError`,
  `ConnectTimeoutError`, `NoCredentialsError`, …) carry **no** `response` at all, so
  "the endpoint is unreachable" — one of the conditions the brief names — would fall
  through unclassified.
* **(c) Structural: the code, the HTTP status, and the exception's class names read off
  the MRO.** **Chosen.** `type(exc).__mro__` gives the class *names* of the exception and
  of every base it inherits from, so `IncompleteReadError` is recognised as a
  `ResponseStreamingError` without importing botocore and without hard-coding the
  hierarchy. The MRO is exactly what `isinstance` consults; only the *names* are read
  instead of the classes.

So the classifier reads three signals, in this order: the error **code** (precise),
the HTTP **status** (coarse), the **class names** (the only signal a connection failure
carries).

#### The vocabulary — what it must be able to express

The brief names four judgements a caller has to be able to make: *absent*, *forbidden*,
*unreachable*, *corrupt*. Those four are not enough for what the code actually does, and
adding the missing ones is not gold-plating — each one is a condition the current code
raises today and would otherwise have to report as "something went wrong":

| Member | The judgement | Real condition in this tree |
|---|---|---|
| `NotFound` | the addressed thing is not there | missing object; **missing bucket** |
| `AccessDenied` | the server refused — credentials or permission | `head_object` → 403; `put_object` → `AccessDenied` |
| `Unreachable` | the substrate could not be reached or could not complete the request | `EndpointConnectionError`; a 503; a mid-body read that dies |
| `Corrupt` | the bytes are not what the address says | hash mismatch; a frame that is not a zstd frame |
| `NotSupported` | the substrate cannot serve this request at all | the `s3` extra is not installed; the deployment selected `s3` with no endpoint |
| `MalformedRequest` | the request was refused as malformed | a digest that is not a digest; a size hint that lies |
| `BlobFailure` | the substrate failed and the reason is not one this vocabulary names | the unclassified fallback |

`BlobError` is the base of the family and is **never raised directly** — the same
arrangement as `relational/errors.py::ConstraintViolation`, which is a grouping base whose
subclasses do the naming.

**Why `BlobFailure` is a sibling and not the base.** The base has to be the *supertype* of
everything so that `except BlobError` catches everything; if the unclassified case *were*
the base, then "catch `BlobError`" and "catch the unclassified failure" would be the same
statement, and a caller could not tell "the substrate failed for a reason I do not model"
from "the substrate failed". `BlobFailure` is deliberately **not** a subclass of
`Unreachable`: it makes no retry promise, because a caller that retries on `Unreachable`
must not be told to retry on this.

**Why `NotFound` covers a missing bucket as well as a missing object.** They are the same
judgement — "the thing you addressed is not there" — and they are told apart by the
details (`bucket=` versus `sha256=`), not by the type. Splitting them into two classes
would give a caller two types to catch where one answer ("it is not there") is what the
caller needs.

#### The decision on `exists()` / `stat()` when the *bucket* is missing

This is the one place the design could have gone either way, and it is the change with the
widest blast radius, so it is recorded explicitly.

* **Option A (chosen).** The missing bucket is detected in `_head()`, which raises
  `NotFound` for a *bucket*-level not-found and returns `None` for an *object*-level one.
  A missing bucket therefore raises from `put`, `put_stream`, `get`, `get_stream`,
  `exists`, `stat` and `delete` alike.
* **Option B (rejected).** `_head()` keeps returning `None` for a missing bucket (today's
  behaviour), and only the write paths translate the bucket-level error.

Option A is chosen because it makes the `put`/`put_stream` divergence disappear **at the
source** rather than at two call sites: both writes fail in `_locate()` → `_head()`, so
they cannot disagree. It also stops `exists()` from answering "no" when the truth is "the
store cannot answer at all" — a lie that would make a daemon believe the archive is empty.
The cost is a behaviour change: `exists()`/`stat()`/`delete()` raise `NotFound` on a
missing bucket where they used to return `False`/`None`/`False`. That is recorded in the
ADR, and the contract's error clause states it.

#### The decision on the driver's own text

**The message names the concept; the driver's own wording is the `__cause__`.** The
details carry identifiers only (`s3_code`, `http_status`, `driver_error`, `key`,
`sha256`, `bucket`, `path`). This is stricter than the current code (which interpolates
`{exc}` into the message) and stricter than `translate_sqlite_error` (which does the
same). The reason is C-6: the message reaches the ledger through `to_payload()`, and
botocore's connection errors quote the **endpoint URL**, which an operator may have
written with credentials in it (`http://user:pass@host`). The traceback keeps the
driver's wording, so the operator loses nothing they can act on. The cost is recorded:
`str(exc)` no longer contains the driver's text, so the ledger records the *concept* and
the *identifiers* rather than a free-text message.

#### The decision on `put_stream`'s spool write failure

A spool write failure is a **host** resource failure (the temporary directory is full),
not a substrate failure — but it is still an exception that leaves the store, so it cannot
be allowed to escape as a raw `OSError` (I-1). It is translated by the shared translator
into `BlobFailure` (an `OSError` that is not a permission error, a missing file or a
connection failure is not one of the four named judgements). The report says so
explicitly because the brief asked for the decision to be deliberate.

### The decision, in one paragraph

A new `src/paa/storage/coldlake/errors.py` holds a seven-member vocabulary under a
`BlobError` base — every member a `StorageError`, every member carrying the `substrate`
that produced it — and a shared boundary translator that is **idempotent**, that **passes
a `PaaError` that is not ours through unchanged**, and that turns a zstd frame error into
`Corrupt` and an `OSError` into the concept its errno implies. The S3 dialect lives
beside the S3 client in `minio_backend.py`: a table of the S3 error codes, a table of
botocore's class names, and a classifier that reads the **code**, then the **HTTP
status**, then the **class names off the MRO** — never importing the driver. The six
raw-escape sites are closed, the `put`/`put_stream` divergence is resolved at the source
(a missing bucket raises `NotFound` from `_head()`, for every method), the `sha256=key`
mislabelling is fixed, the CAS's raw `OSError` and raw `ZstdError` are closed, the
`BlobStore` protocol gains the error clause it never had, and ADR-0032 records the
decision.

### What was explicitly NOT done, and why

* **No `list` operation on the protocol** (D-6): enumeration is not part of a
  content-addressed store's contract, and the live suite uses a raw client for that one
  assertion.
* **No rename of `minio_backend.py`** (ADR-0026 defers it deliberately).
* **No change to any `BlobStore` signature** (C-7).
* **No `boto3` import at module scope, and no lazy import either** (C-1, and the
  "same code path in both suites" argument above).
* **No change to `src/paa/config.py`** — a hotspot no task in this run owns.
* **No rewrite of the two implementations' internals** beyond the error paths: the
  addressing, the fan-out, the dedup and the verify-on-read are untouched.
* **No `S3UploadFailedError` unwrapping beyond one level of a recognisably
  driver-shaped cause** — the unwrap is what makes `put_stream` agree with `put` for
  *every* code, not only for a missing bucket, and it is bounded so it cannot recurse.
* **No new dependency, no extra, no marker** (C-9; T-002 owns those).
* **The signal and artifact repositories were not touched** — they are not in the
  write-set, and they keep working because every new member *is* a `StorageError`.

### §1a — design changes made during implementation

Two, both recorded here because the design record above is the *before* picture.

**1. The vocabulary grew a base class and a fallback class.** The design above
already had `BlobError` as the base and `BlobFailure` as the unclassified
member; what changed while implementing is *why* `BlobFailure` is a sibling and
not the base. It is a sibling because the base has to be the supertype of
everything — `except BlobError` must catch everything the vocabulary names —
and if the unclassified case *were* the base, then "catch `BlobError`" and
"catch the unclassified failure" would be the same statement. The tests pin
this: `test_the_unclassified_failure_is_not_a_retry_promise`.

**2. The `OSError` mapping is narrower than the design implied.** The design
said "an `OSError` → the concept its errno implies". Implemented, it is three
exact cases (`ENOENT` → `NotFound`, `EACCES`/`EPERM`/`EROFS` → `AccessDenied`,
a failed connection → `Unreachable`) and **everything else → `BlobFailure`**.
The reason is that `Unreachable` is a *promise* — "retry me" — and a full disk
(`ENOSPC`) or a name too long (`ENAMETOOLONG`) is not worth retrying. Calling
them "unreachable" would tell a caller to retry something that cannot
succeed. `test_a_full_disk_is_not_reachable_and_not_retryable` pins it.

**Not changed from the design:** the missing-bucket decision (decision 5 in
D1), the structural classification, the "message names the concept" rule, and
the idempotence rule.

## 3. Root cause

The blob substrate never got the seam ADR-0025 established for the relational
substrates: no vocabulary, no translator, and — the reason it went unnoticed —
**a protocol that was silent about failure**. Silence in a contract is not
neutral: it means the two implementations were free to disagree, and they did,
in the one place a caller could least afford it.

## 4. Approach chosen and why

See D1 above. In one line: a vocabulary of seven concepts under a `BlobError`
base, all of them `StorageError`s; a shared boundary translator that is
idempotent, passes a `PaaError` that is not ours through untouched, and reports
what it cannot classify as `BlobFailure`; an S3 dialect that reads the driver's
error code, then its HTTP status, then its class names off the MRO — never
importing the driver; and an error clause in the protocol, checked by a test
against both implementations.

**Alternatives rejected:** one vocabulary + one translator that also holds the
S3 table (mixes the neutral module into the dialect); translating at the call
sites (that is the bug); mirroring botocore's hierarchy in the vocabulary
(copies a driver, and the driver is optional); a lazy `import botocore` inside
the classifier (makes the classification depend on whether the driver is
installed, so the unit suite would not exercise the code the deployment runs);
and splitting "missing bucket" and "missing object" into two classes (two types
to catch where the judgement is one).

## 8. Long-run test

- **Source.** The only source of truth is still the bytes: content addressing
  is unchanged, verify-on-read is unchanged, and the digest is still taken
  over the *raw* bytes ✓. What changed is the *reporting* of a failure, not
  what is stored. The error's `details` carry the digest, the key and the
  substrate, so a ledger record of a failed write says which blob and which
  substrate — which is more than the free-text message it replaced.
- **Load.** The translation is a handful of set lookups per failure; the hot
  paths (put/get) are untouched — one extra `dict` build *per failure*, not
  per byte. `_translated_chunks` adds one `try` per chunk read, which is a
  `next()` call in a `try` — measurable only at 100x the chunk count, and
  negligible against the SHA-256 of the same bytes. Concurrency: the stores
  hold no new state; the unwrap reads `__cause__`/`__context__`, which is
  per-exception ✓. Partial failure: a failed upload leaves no object (the
  server rejected it) and the spool is closed ✓; a failed CAS write leaves a
  staging file, which the sweep removes ✓ — and the cleanup no longer
  *replaces* the original failure with its own ✓.
- **Hostile input.** A hostile digest is refused at the door on both
  substrates ✓ and the rejected value is echoed up to 128 characters, so a
  megabyte of garbage cannot make the ledger grow by a megabyte ✓ (this is a
  change, and it is recorded in the ADR). A driver's message is not in the
  ledger payload at all ✓ — the endpoint URL cannot leak a credential into it
  ✓. A hostile *server* cannot choose the local exception type: every code it
  sends maps to a fixed class, and a code the table does not name becomes
  `BlobFailure` rather than an arbitrary one ✓.
- **Operability.** `s3_code`, `http_status`, `driver_error`, `op`, `key`,
  `sha256`, `bucket` and `path` are in the error's details, so
  `PaaError.to_payload()` puts them in the ledger as queryable fields ✓. The
  driver's own wording is in the traceback ✓. The `op` detail says which
  operation failed, which the old free-text message said in prose ✓.
- **Reversal.** Which test fails if the fix is reverted? **Twenty-six of
  them** (§7 — the number was corrected from 28 on 2026-10-22; the method
  is in §7 and the count was re-measured), plus the whole of
  `test_blob_errors.py`, which cannot be collected without the fix. And the invariant test
  (`test_no_driver_exception_escapes_the_store`) fails on the *first* failure
  mode, so a partial revert is caught immediately ✓.

## 9. Edge cases and abuse scenarios

**Handled:** a missing bucket (raises, from every method); a missing object
(answers, on the query methods; raises on the read methods); a refusal
(credentials or permission); a throttled or timed-out request (retryable); a
connection that failed; a connection that died mid-body; a corrupt frame; a
hash mismatch; a hostile digest; a lying size hint; a blob deleted between
the locate and the read; a full disk; a refused file; an unwrapped driver
error the table does not name.

**Consciously not handled:**

- **A `TypeError` from calling the client wrongly** is translated into
  `BlobFailure` rather than passed through. ADR-0025 keeps a `TypeError` a
  `TypeError` at the *transaction* boundary, which is wide — it wraps the
  repository's own code. These boundaries are narrow: they wrap one driver
  call, so what reaches them is the driver's error or a bug in the call, and
  either way it is a substrate-side failure. The original is the `__cause__`,
  so the traceback still names the `TypeError` ✓.
- **A `create_bucket` that fails with `BucketAlreadyOwnedByYou`** becomes
  `BlobFailure` — the same as today (a raw `ClientError`), and no worse. It is
  a benign condition that ought to be treated as success; that is an
  out-of-scope finding (§13).
- **The S3 error-code table is not exhaustive.** A code it does not name
  becomes `BlobFailure` — deliberately: a guess would be worse than an honest
  "the substrate failed and we do not know why".

**Unknown:** what codes SeaweedFS and RustFS answer with. The unit suite
proves the *mechanism*; the table's coverage of real servers is wave 2's to
prove.

## 10. Performance and security considerations

**Performance.** The translation runs on the failure path only. The one
per-chunk cost is `_translated_chunks`'s `try` around `next(reader)` — a
`SETUP_FINALLY`/`POP_BLOCK` pair per chunk, against a SHA-256 update of the
same bytes. No allocation on the success path changed.

**Security.** The driver's text is not in the message, so it is not in the
ledger ✓. The details are identifiers ✓. The rejected digest is bounded ✓.
The hostile-digest guard is unchanged and now raises a class that says
"malformed request" ✓. A hostile server cannot pick the exception type ✓.

## D3. Load and scalability analysis

The vocabulary is seven classes and three tables of strings; the translation is
a bounded number of set lookups. The hot path is unchanged: `put`/`get` do the
same hashing, the same compression and the same number of requests. The only
per-chunk cost added is the `try` in `_translated_chunks` — a `next()` inside a
`try` instead of a `for`, which is one `POP_BLOCK` per chunk against a SHA-256
update of the same bytes (SHA-256 dominates by orders of magnitude). At 100x
the payload size nothing changes; at 100x the *concurrency* nothing changes
either, because the stores hold no new state and the unwrap reads
per-exception attributes. The one thing that scales differently is the
**ledger**: an error's details are merged verbatim into a payload, so the
detail set was kept small and bounded on purpose (the rejected digest is
truncated to 128 characters) — a failure cannot inflate the ledger.

## D4. Security / threat model

**Trust boundaries.** (1) The S3 server is untrusted: it chooses the error
code, and a hostile or broken server must not choose the *local* exception
type. (2) The caller's input is untrusted: a digest becomes path components
and a ledger payload. (3) The driver's text is untrusted: it is the server's
words, relayed.

**Attacker capabilities and mitigations.**

- *A server that answers with an arbitrary code*: the code maps to a fixed
  class or to `BlobFailure`; the server never picks the type ✓. It can, however,
  put arbitrary text in `Error.Message` — which is why that text is **not** in
  the error's message and so **not** in the ledger payload ✓.
- *A server that quotes the endpoint URL back*: botocore's connection errors
  do. The endpoint URL may carry credentials if an operator wrote them there.
  Keeping the driver's text out of the message keeps them out of the ledger ✓
  — the residual risk is the traceback and the logs, which is where a
  credential belongs.
- *A caller that supplies a megabyte of "digest"*: refused at the door, and
  the echoed value is truncated to 128 characters, so the ledger payload stays
  bounded ✓.
- *A path traversal through the digest*: unchanged (the digest is validated
  before it becomes a path) ✓, and now the refusal is a named class ✓.

**Residual risk.** The ledger records the concept and the identifiers; it no
longer records the driver's wording. That is a deliberate loss of fidelity in
exchange for a bounded, secret-free payload. Anyone who needs the driver's
wording has the traceback.

## D5. Rollout, migration and rollback plan

- **Ordering.** No flag, no feature switch, no data migration. The new classes
  are additive; the only behaviour change is the missing-bucket raise.
- **Compatibility window.** A caller that catches `StorageError` is unaffected
  ✓. A caller that catches `PaaError` is unaffected ✓. A caller that catches
  `botocore.exceptions.ClientError` — which the code never did, and which a
  caller could only have written by importing the driver — would stop
  catching; that is the *point* of the change, and no caller in this tree does
  it ✓ `[VERIFIED by grep over src/paa]`.
- **Rollback.** Revert the commit. The vocabulary disappears with it, the
  missing bucket goes back to answering `False`, and the raw exceptions come
  back — which is the state the tests in §7 demonstrate fails 26 assertions.
- **The live suite (wave 2) depends on this.** Its failure-mode assertions
  will name these classes; the names are in ADR-0032 and in
  `paa.storage.coldlake.errors`, and the vocabulary is additive, so wave 2 can
  be written against it without waiting for anything else in this change.
