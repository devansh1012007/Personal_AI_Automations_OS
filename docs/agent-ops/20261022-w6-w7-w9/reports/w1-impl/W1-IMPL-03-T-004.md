## 3. Root cause

**Root cause:** a *mechanical* refactor (`Database` → `RelationalBackend`) was
applied to nine files in one commit, and the author converted **one** of the
nine imports to runtime while leaving **eight** behind `if TYPE_CHECKING:`.
The two spellings are interchangeable to a reader — the annotation still says
`RelationalBackend` either way — so the inconsistency has no *visible* cost at
the call site. It only costs at the moment something asks for the class.

**Why it was not caught:** the type checker is satisfied by both spellings
(`from __future__ import annotations` makes every annotation a string, so the
guard is free), and no runtime code needed the class. The inconsistency lived
entirely in the space between "the type checker is happy" and "the class is
there".

**Why it is not a cycle:** the family is provably acyclic.
`paa.storage.relational.base` imports `paa.storage.relational.connection` and
`paa.storage.relational.dialect`, and importing the submodule executes the
package `__init__`, which imports `paa.config` and
`paa.storage.relational.database` (`aiosqlite` + the migration runner) — all
required dependencies, no optional extra, and **no back edge** to
`paa.memory`, `paa.agents`, `paa.skills` or `paa.marketplace`. Verified
empirically: all 137 modules import cleanly in a fresh interpreter after the
conversion (§11), and the sweep that produced that number is the same sweep
that catches a cycle (§7, `test_the_probe_would_notice_a_cycle`).

## 4. Approach chosen and why

**Chosen:** move the `RelationalBackend` import to module scope in the seven
files, matching `memory/creator.py` exactly; drop the `TYPE_CHECKING` block
where it held nothing else; add a three-part lock in a new
`tests/conventions/` package.

**Per-file decisions** (the brief asks for them explicitly):

| File | `TYPE_CHECKING` block held | Decision |
|---|---|---|
| `memory/contradiction.py` | `RelationalBackend` only | block removed; `TYPE_CHECKING` dropped from the `typing` import |
| `memory/decay.py` | `RelationalBackend` only | same |
| `memory/curator.py` | `RelationalBackend` **and** `paa.config.MemorySettings` | **both** converted, block removed entirely |
| `marketplace/installer.py` | `RelationalBackend` only | block removed |
| `skills/registry.py` | `RelationalBackend` only | block removed |
| `agents/policy.py` | `RelationalBackend` only | block removed |
| `agents/context_agents.py` | `RelationalBackend` only | block removed |

**Why `MemorySettings` went too** (it is the only judgement call in the diff):
`paa.config` is a first-party module whose module scope defines pydantic model
*classes* and nothing else — no settings are instantiated at import time
(`get_settings()` is `lru_cache`d and `Settings.ensure_directories()` is
explicit), and it imports only `pydantic`, `pydantic-settings`, `dotenv` and
`paa.core.types`. `paa.memory.curator` already depends on `paa.config` at
runtime — `MemoryCurator.__init__` does `from paa.config import get_settings`
(`curator.py:124`). Leaving a one-member guard for a module the file already
imports at runtime would have left the file expressing the same dependency
two ways, which is the defect. It also makes `MemoryCurator.__init__`'s
`settings: MemorySettings | None` annotation resolvable, like the other six.

**Alternatives considered and rejected:**

* **Convert the whole family including `observability/runs.py`** — forbidden by
  the brief; it is wave 2's file and T-008 converts it there. Recorded as a
  deferral with its owner.
* **Convert the other 33 blocks while I was in the tree** — forbidden, and out
  of scope. The brief says a reviewer will check the write-set.
* **A lock scoped to the seven files only** — rejected. It would have left the
  eighth sibling free to drift, and it would have been a weaker statement than
  the tree can support: the invariant that is actually true is *"no module in
  `src/paa` resolves this contract lazily"*, which is checkable over the whole
  package.
* **A lock that forbids `observability/runs.py` outright** — rejected: it
  would make wave 1's gate red for a file wave 2 is about to fix. Instead the
  lock carries a **deferral map** (module → the task that owns it), and the
  assertion is that the set of lazy resolvers is a **subset** of the deferrals.
  When T-008 lands, the subset is empty and the lock still passes; the stale
  entry is then deleted by whoever converts it.
* **A text/regex search for the guard** — rejected. The difference between the
  two spellings is *structural* (module scope vs. nested in a guard), and a
  text search cannot tell them apart without also matching the word in a
  comment or a docstring. The lock parses the AST.
* **A lock that greps for the *class name*** — rejected: the invariant is
  about the *import*, not the name. A module can import the contract under an
  alias, or import something else and merely mention it. The lock works on
  import statements.

**How the fresh-interpreter check distinguishes a cycle from a missing extra.**
This matters, because a check that swallows every `ImportError` cannot see a
cycle at all — and a check that fails on every `ImportError` fails on a
minimal install. The classifier is:

* a message containing `partially initialized` or `circular import` → **fatal**
  (checked first, before anything else can excuse it);
* `ModuleNotFoundError` naming a **third-party** package → tolerated, and the
  module must be on the named `OPTIONAL_EXTRA_MODULES` list;
* `ModuleNotFoundError` naming a **`paa.*`** module → **fatal** (a first-party
  module is missing — the tree is broken);
* `ImportError` whose message names an extra → tolerated, same list;
* anything else → **fatal**.

`test_the_probe_would_notice_a_cycle` proves the first rule works, using two
modules written into `tmp_path` that really do form a cycle.

**Edge and abuse cases covered:** a module that cannot import at all; a module
that imports but does not bind the class; a module that binds it under an
alias (the bound check is by *identity over the module's globals*, so an
aliased import still counts as resolved); a deferral that names no task; a
deferral that names a module that does not exist; a hung import (120 s
timeout → reported as a failure, not as a pass); a cycle.

**Determinism and isolation:** the probes are independent subprocesses; the
`probes` fixture is module-scoped and read-only (it writes nothing, and its
result does not depend on test order); the cycle fixture is written into
`tmp_path` and never into the repository; nothing binds a port, starts a
container or touches a database.

## 8. Long-run test

* **Source.** One commit, one contract, one spelling. The diff is seven
  import lines and one new test file; there is no state, no migration and no
  data-format change, so a rollback is a revert with no residue.
* **Load.** No runtime behaviour changed. The conversion's cost is at import
  time and is concentrated in one module: `paa.marketplace.installer` pays
  **+95 ms** because it now pulls the relational substrate, `paa.agents.policy`
  pays **+11 ms**, and the other five pay ≤ 2 ms (§6). The CLI's version path
  is unaffected (measured). The new test costs 10 s of wall clock and ~60 s of
  CPU across 8 workers; on a host running the whole suite in parallel with
  other agents that is the price of the acceptance criterion, and it is paid
  once per session, not per test.
* **Partial failure.** The fresh-interpreter check is the partial-failure
  case, and it is the one that matters: a module that fails to import is
  reported by name with the exception type and message, and the failure is
  **not** swallowed. A single bad module fails the test; it does not degrade
  it.
* **Hostile input.** The inputs are the repository's own source files. The one
  adversarial case the check can meet is a module that raises on import — and
  that is the case the check exists for. A module whose import *hangs* is
  caught by the timeout. The probe catches `BaseException`, deliberately, so a
  module that refuses to load by raising `SystemExit` is reported as a
  failure rather than mistaken for success.
* **Operability.** The lock is a plain pytest file: no fixtures to set up, no
  service to start, no database. The deferral map is the only mutable-looking
  part of it, and it is a dict literal at the top of the file with a comment
  saying what to do with it when its owner lands.
* **Reversal.** **The convention lock is the answer, and I proved it fires.**
  Reverting `src/paa/memory/decay.py` to the `TYPE_CHECKING` form fails
  `test_the_contract_is_not_imported_behind_type_checking` and
  `test_the_family_resolves_the_contract_one_way`; reverting
  `src/paa/agents/policy.py` fails the same two. Both reverts were performed
  by hand and undone by hand, and the evidence is in §7.

## 9. Edge cases and abuse scenarios

* **Handled:** a module that cannot import (fatal, unless a named optional
  extra on a named module); a module that imports but does not bind the class
  (fatal); an aliased import (counted as resolved, by identity); a deferral
  with no owner (fatal); a deferral naming a module that does not exist
  (fatal); a hung import (fatal, by timeout); an import that raises
  `SystemExit` (caught, reported as a failure); a module added to the package
  after the lock was written (picked up automatically — the module list is
  derived from the filesystem, not hard-coded, so W1-IMPL-01's new
  `storage/coldlake/errors.py` was covered by the very first run).
* **Consciously not handled:** a module whose import depends on the *current
  working directory* (the probe inherits the test session's cwd, which is what
  a developer would have); a module that is deliberately not importable
  outside a particular environment (the extras list is the place to record
  one, and it is a named list, not a blanket exemption).
* **Unknown:** whether a future module in `src/paa` will need an extra that
  is not on `OPTIONAL_EXTRA_MODULES`. It will fail the test, with the module's
  name, and the fix is to add it to the list — a deliberate act, not a silent
  one.

## 14. Known limitations, risks, rollback notes

* **The lock is a convention, not a proof.** It says the contract is resolved
  one way in this repository *today*. It cannot see a module added outside
  `src/paa`, and it cannot see a contract other than `RelationalBackend` being
  resolved two ways — the same defect in a different shape would not be
  caught by this lock. A general form ("every module that imports a contract
  binds it") would need a machine-readable notion of "contract", which the
  repository does not have. I chose the narrow, true statement over a broad
  one that cannot be checked.
* **The `DEFERRED` entry will go stale.** When T-008 converts
  `observability/runs.py`, the entry becomes unnecessary. The lock still
  passes (the assertion is a subset), so nothing breaks — but a reader may
  think the file is still lazy. The entry's comment says to delete it.
* **`OPTIONAL_EXTRA_MODULES` is a list that must be maintained.** A new
  extras-gated module will fail the test until it is added. That is the
  intended direction of the failure: it is a deliberate act, not a silent one.
* **The fresh-interpreter sweep costs 10 s per session.** On a host with a
  slow filesystem or a very large `src/paa`, it grows linearly with the module
  count. The timeout (120 s per module) bounds the worst case.
* **Rollback:** revert `7747fa0`. There is no state, no migration and no
  data change; the only residue would be the two new files, which the revert
  removes.

## 15. Where I am least confident / what the reviewer should scrutinize

1. **The classification's method, not its result.** My classification rests on
   *converting* each block and observing what breaks. That is a stronger
   method than reading, but it is not the same thing as a proof of
   cycle-freedom: a cycle reachable only through a path my probe does not
   take (a runtime `importlib.import_module` inside a function, a plugin
   loader, a `try: import` that swallows `ImportError`) would not be seen.
   The repo has one `try: import` that re-raises (`storage/graph/kuzu_backend.py:82`)
   and one that does not (`storage/relational/postgres.py:119`, lazy) — I
   checked both by hand. A reviewer who wants certainty should look for
   dynamic imports, not for more of my measurement.
2. **`curator.py`'s `MemorySettings`.** I converted it on the argument that
   `paa.config` is light and side-effect-free at import. If a reviewer
   disagrees — if `paa.config` is meant to be import-lazy for a reason I did
   not find — then that one import should go back behind the guard and the
   block stays. It is a one-line change either way.
3. **The deferral map.** The lock's global assertion is "the set of lazy
   resolvers is a subset of the deferrals". A reviewer might reasonably want
   the stronger "the set is **exactly** the deferrals" — which would fail
   the moment T-008 lands. I chose the subset on purpose; the comment says
   why.
4. **The 8-worker probe.** If the gate host is memory-constrained, 8
   concurrent interpreters is ~500 MB transient. `PROBE_WORKERS` is a
   constant at the top of the file if it needs lowering.
