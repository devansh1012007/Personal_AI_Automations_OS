# Implementation report — W3-IMPL-03 — T-011 the marketplace's untrusted HTTP body

## 1. Task and acceptance criteria (restated)

The brief: `HttpRegistry` fetches a remote body and lets the **server** choose
the local exception type. The requirement, verbatim from the plan
(`docs/plans/w6-w7-w9.md:248`):

> The remote body is untrusted: a malformed body must produce **the project's
> own error**, with the server's text **bounded** and **never interpolated
> into a message that reaches a log**.

Acceptance criteria I set myself from the brief, and measured in §7:

1. every path that reads a body raises one project error type, on every
   malformed shape;
2. the server's text is bounded, and the rule for where it may appear is
   written down in the code;
3. the remote text does not reach a log line unescaped, and a test shows
   exactly what does reach the log;
4. each malformed shape has a test that fails without the fix;
5. the callers that catch the old exception types are identified, and what
   happens to them is stated.

## 3. Root cause

The client **parsed a body it had not validated**, in two places:

* `registry_client.py` called `resp.json()` and then `RegistryEntry(**entry)`
  on whatever came out. The shape of the answer was never checked, so the
  answer decided which Python exception came out — and, for a 500, `httpx`'s
  own `raise_for_status` decided it.
* `package.py` called `json.loads` on the manifest and splatted the result
  into the dataclass, with the same consequence.

Underneath both: the client's contract was "whatever the server sends, I
will try to interpret", and the project's error vocabulary was not on that
path at all. `raise_for_status` was doing two jobs it should not have been
doing: choosing the exception type, and putting the server's reason phrase
in a message.

## 4. Approach chosen and why

**One error type, and the client validates before it parses.**

* A new `RegistryError(PaaError)` in `registry_client.py:226` is the type
  for every way a remote registry can fail the client. It is a `PaaError`
  because `core/errors.py` is read-only for me and because the marketplace
  already sets the precedent of a package-local error (`PackageError` in
  `package.py:80`). **Proposal for the record** (the brief asks for one if
  the error does not exist): `core/errors.py` has no "remote input"
  section, and the closest thing in it is `ValidationError`
  ("Deterministic validation rejected an artifact"), which would have been
  usable but too broad — a caller could not tell "the registry is broken"
  from "a skill contract failed validation". If the orchestrator wants one
  error type for the whole project, `RegistryError` is the candidate to move
  into `core/errors.py`; I did not edit that file.
* The client now checks, in this order: the **status** (a 2xx is the only
  success; a 500 with a good body and a 302 are both failures), then the
  **size** (the body is read through a ceiling), then the **emptiness**,
  then the **shape** (an object, a list, an entry with a string identity,
  a manifest that parses into an object whose fields are the right types).
* The **rule for the remote's words** is written down in the module
  docstring (`registry_client.py:34`) and is implemented in one place.

Alternatives considered and rejected:

| alternative | why not |
|---|---|
| catch the raw exceptions and re-raise `ValueError`/`RuntimeError` | the brief forbids a bare `ValueError`, and a caller still could not tell a broken server from a broken client |
| use `core.errors.ValidationError` | exists, but too broad: it cannot say "the registry" (see above) |
| keep `httpx.HTTPStatusError` for a 500 and only fix the parse | the status is the server's too, and `httpx`'s message carries the server's reason phrase |
| let the client **degrade** (return `[]`) on a malformed index, the way `LocalDirectoryRegistry` degrades | the local registry degrades because its index is a local file the user can fix; a remote registry's answer is the *server's* failure, and the brief requires an error. The difference is stated in `search`'s docstring (`registry_client.py:663`) so it is a rule and not an accident |
| put the server's text in the error's **details** | a detail is written straight into a ledger event payload (`PaaError.to_payload`), and the brief's complaint is precisely "an untrusted body writing into the project's logs". The excerpt is an **attribute**, not a detail, so it cannot reach the ledger by accident |
| put the server's text in the **message** | a message is a format. The HTTP boundary's messages are drawn from a closed vocabulary of seven fixed strings (`_MESSAGES`, `registry_client.py:117`) |
| log the excerpt | a log line is a format too. The refusal is logged with facts about the answer — status, reason, byte count, character count — and the test pins the exact key set |

**The rule, as written in the code** (`registry_client.py:34`, and enforced by
the tests):

* a **message** may name a remote value only as a *bounded, repr-quoted*
  fragment (≤ 64 characters). The HTTP boundary's messages name none at all;
* a **detail** never carries remote text;
* a **log line** carries facts *about* the answer and never the answer;
* a **cause** is kept only where its own message obeys the message rule — a
  `json.JSONDecodeError` (which holds the whole document) and a
  `BadZipFile` (which names a member) are never chained, so neither travels;
* the remote's words live in **one** place: `RegistryError.remote_excerpt`,
  at most 200 characters, escaped to a single ASCII line, quoted, and
  stripped of the client's own credential. It is an attribute and not a
  detail, so a caller who does not want it cannot have it by accident.

**What happens to the callers that caught the old exception types: there are
none.** `HttpRegistry` is a public class with **zero** call sites in `src/`
and `tests/` — the marketplace is not wired into the CLI, the daemon or the
runtime yet. So the contract change is not silently breaking anybody, and
this is stated rather than assumed:

* a caller that caught `json.JSONDecodeError`, `AttributeError` or
  `TypeError` around `search`/`fetch` now catches `RegistryError` — which
  is the point, but it *is* a change, and a future caller that wrote
  `except TypeError` around the registry will now see the error escape;
* a caller that caught `httpx.HTTPStatusError` (or any `httpx.HTTPError`)
  now catches `RegistryError`. The transport failure keeps its `httpx`
  exception as the **cause** (`excinfo.value.__cause__`), so the diagnosis
  is still there, and the class name is in `details["transport_error"]`;
* a caller that caught `PackageError` around `HttpRegistry.fetch` still
  catches it: the `PackageError` is the **cause** of the `RegistryError`,
  and the `RegistryError` is *not* a `PackageError` — so this one is a real
  change. I chose not to make `RegistryError` a `PackageError` because
  `PackageError` means "a package is malformed" and a search index is not a
  package; the blast radius is zero today (no callers), and §9.3 records the
  alternative;
* `LocalDirectoryRegistry` is unchanged: it still raises `FileNotFoundError`
  for a missing package and `PackageError` for a malformed one, and it
  still degrades a damaged index to an empty registry.

**The one caller-visible behaviour change that is not an error type:** the
HTTP registry's `search` now applies `limit` client-side (the server is
asked for `limit` and the client applies it too) and ignores unknown keys
in an index entry (the local registry has always ignored them). Both are
documented in the code (`registry_client.py:663` and `:609`) and both are
covered by tests.

**`httpx` is now imported at module scope** in `registry_client.py` (it was
imported inside the three methods). `httpx` is a **core** dependency

## 8. Long-run test

* **Source** — the input is a remote body; there is no second source of
  truth and no state to corrupt. The client holds no state between calls.
* **Load** — 100× is a non-question for the parsing path (the body is read
  once and thrown away) and the interesting number is the *ceiling*: 1 MiB
  for an index, 16 MiB for a package, 64 MiB unpacked, 4 KiB for an error
  body. The 100× case that matters is a server that sends a large body
  repeatedly: each call is bounded by the same ceiling, and the client
  allocates no more than the ceiling. Concurrency: each call builds its own
  `AsyncClient` and its own response, so two calls cannot share a buffer.
  Partial failure: a failure mid-read (the transport raises) leaves the
  client with nothing but a `RegistryError`.
* **Hostile input** — covered: a body that is not JSON, a body that is JSON
  but not the expected shape, an empty body, an enormous body, a
  decompression bomb, a manifest with a wrongly typed field, a body that
  tries to forge a log line, a body that echoes the client's token, a
  reason phrase the server controls, a redirect, an unreachable host, and a
  zip-slip member name (the pre-existing guard, kept and now bounded).
* **Operability** — the refusal is observable: one warning line with the
  operation, the reason, the status, the byte count and the character
  count; the error carries the same facts as structured details, so it can
  go into a ledger payload; and the bounded excerpt is there for a human
  who asks for it. Roll back: revert the two commits; nothing else in the
  tree depends on the new behaviour (no callers).
* **Reversal** — the question "which test fails if the fix is reverted?"
  has two answers, both measured: revert the *whole* fix and the new
  module does not import (1 collection error, 0 tests run); revert only the
  *behaviour* (keeping the seam and the name) and **29 of the 33** new
  tests fail. And fifteen single-rule mutations are each caught.

## 9. Edge cases and abuse scenarios

**Handled:** every shape in §7's table; the credential echo; the log-line
forgery; the decompression bomb; the redirect; the 3xx; the transport
failure; a body that is valid JSON but an empty string (which would
otherwise read as "no results").

**Consciously not handled:**

9.1. **A body that is valid UTF-8 but not valid JSON** is refused as
`not_json`; the distinction between "not UTF-8" and "not JSON" is not
reported separately. Both are the same failure for the caller.

9.2. **A `results` that is a list of valid entries but a thousand of them**
is bounded by the body ceiling (1 MiB) and by the client's own `limit`.
A server that ignores both is bounded by the body.

9.3. **The finer diagnosis of a malformed package.** The refusal's reason
is `malformed_package`; the *why* ("not a zip" vs "invalid kind") is in the
`PackageError` kept as the cause. A reviewer may prefer a closed-vocabulary
`reason` detail on the package errors instead of a cause, so that the
ledger payload can be queried by it. That is a small follow-up and I did not
do it, because it touches every `PackageError` site in `package.py` and the
brief is about the *registry's* refusal.

9.4. **A body that is enormous but the status is an error**: the status
dominates (`http_error`) and the error-body ceiling (4 KiB) applies, so the
client does not read the rest. The excerpt is the first 200 characters.

9.5. **A `Content-Length` header that lies** is irrelevant: the ceiling is
counted on the bytes that arrive, not on the header. (The header is not
consulted at all, which also means a 16 MiB body with no length header is
handled the same way.)

**Unknown:** whether a real server sends a `results` shape other than
`{"results": [...]}`. The client's contract is now explicit and strict
about it, and a server that answers differently will be refused rather than
half-understood.

## 10. Performance and security considerations

* The client now **streams** the body (`client.stream` + `aiter_bytes`)
  instead of buffering it, so the ceiling is a real ceiling rather than a
  check after the fact. The cost is one extra `async with` per call.
* An **error body is read through a 4 KiB ceiling** rather than the
  operation's ceiling, because it is only read for its excerpt — a 16 MiB
  error body is not worth the bandwidth.
* The excerpt is computed from the **first 800 bytes** of the body and
  truncated to 200 characters, so the cost of building it does not depend
  on the size of the body.
* `unicode_escape` is applied to the excerpt, so the result is **ASCII**:
  a terminal cannot be asked to interpret it, and a control character cannot
  move a cursor.
* The client's **own bearer token is removed from the excerpt** before
  anything else happens to it, so a server that echoes the
  `Authorization` header back cannot turn the excerpt into a credential
  leak. This is the marketplace's answer to the models layer's T-007
  finding, applied at the marketplace's own boundary.
* The client's own credential is **not** sent anywhere else: the excerpt is
  the only place a body could have carried it back.

## 14. Known limitations, risks, rollback notes

* **The refusal is coarser than the failure.** `unexpected_shape` covers
  five different malformations. The reason is a closed vocabulary, and a
  finer one (a `detail` naming which check failed) would be a better
  ledger payload. I chose the closed vocabulary because a detail that
  carries remote text is what the brief is about.
* **The body ceiling is a constant.** 1 MiB for an index, 16 MiB for a
  package. A legitimate marketplace with a larger index would be refused.
  The constants are module-level and named, so raising them is a one-line
  change; they are not constructor knobs, because a knob nobody sets is
  still a default and a knob everybody sets is a policy.
* **The 64 MiB unpacked ceiling** is measured on the sizes the zip
  *declares*, which is what `zipfile` will hand back (`zipfile` reads at
  most `file_size` bytes per member), so the declared total is a sound
  bound. A zip that lies about its sizes is caught by `zipfile`'s own CRC
  and size checks.
* **`httpx` at module scope** costs an import on `import paa.marketplace`.
  It is a core dependency and the models layer already does it; the
  marketplace package is imported by nothing else in `src/`.
* **Rollback**: `git revert 01b5adb efd18f6`. Nothing else in the tree
  depends on the new behaviour, and the old behaviour is the one that
  leaked `TypeError`s.
* **`RegistryError` is not a `PackageError`.** A future caller that writes
  `except PackageError` around a `fetch` will not catch a malformed
  *remote* package any more (the local registry still raises
  `PackageError`). Making `RegistryError` a subclass of `PackageError`
  would have preserved that, at the price of saying "a search index is a
  malformed package". §9.3; zero callers today.
