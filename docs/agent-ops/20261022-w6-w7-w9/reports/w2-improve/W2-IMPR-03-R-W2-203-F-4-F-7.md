## 2. Code changes (per file, with rationale; root-cause level, no band-aids)

### 2.1 R-W2-203 — the exception chain, closed

**Chose (a): close it.** Not (b).

**Why (a) and not (b).** The brief allows either, and the choice turns on one
question: *can the router promise that the exception it chains is clean?* It
cannot. `redact` knows three shapes — `sk-…`, `Bearer …`, and
`api_key: …`/`x-api-key: …`/`authorization: …` — and a provider's key in any
other shape (a Gemini `AIza…` key, a bare token, a base64 secret) survives
every pattern the router has. The router does not hold the key; only the
provider does. So "the provider's exception is probably clean" is not a
guarantee the router can keep, and a guarantee it cannot keep is not a
guarantee. Meanwhile the surface the chain reaches is the one that matters
most: `traceback.format_exception` renders the cause, and the rendered
traceback is what an operator pastes into a bug report — where the key then
lives in a third-party tracker, forever, outside every control this runtime
has.

The tempting counter-argument is that dropping the chain "loses the
diagnosis". It does not: the diagnosis was **already being copied** into the
raised error's details (`underlying_error`, `underlying_message`,
`underlying_<key>…`), scrubbed. The chain was a *second* copy of the same
facts, unscrubbed, in the one place where scrubbing does not apply. Dropping
it removes a duplicate, not the information.

**What changed** (`src/paa/models/router.py`):

* `_local_only` no longer raises inside the `except` handler. It captures the
  provider's failure, and the error is built by a new helper
  (`_local_only_error`) and raised **outside** the handler with `from None`.
* `_route`'s "escalation is permitted but no frontier provider is configured"
  branch had the same leak (`from local_error`); it now goes through a new
  helper (`_no_frontier_error`) and is raised with `from None`. Because the
  chain was that path's *only* place for the provider's diagnosis, the
  helper adds the scrubbed `underlying_*` details, so the operator reads the
  same facts from a surface that cannot carry a credential.

**Why "outside the handler" and not just `from None`.** Measured on this
host's CPython (3.12), and the difference is the whole fix:

| how it is raised | `__cause__` | `__context__` | rendered traceback |
|---|---|---|---|
| `raise X from exc` inside the handler (the old code) | the provider's error | the provider's error | contains the provider's error |
| `raise X from None` **inside** the handler | `None` | **the provider's error** | clean (the context is *suppressed* in the rendering) |
| `raise X` **outside** the handler | `None` | `None` | clean |
| `X.__context__ = None` set by hand, then raised inside the handler | `None` | **the provider's error** (CPython overwrites it) | clean |

So `from None` alone would have silenced the *rendering* while leaving the
provider's exception reachable through `__context__` — the reviewer measured
exactly that attribute, and a claim that only holds in the rendering is not a
claim. Raising outside the handler is what makes **both** attributes empty.

**The precise guarantee, stated so it can be checked.** The router's raised
error never carries **the provider's exception**: not as `__cause__`, not as
`__context__`, not in the rendered traceback. (An exception raised while a
*caller* is handling an unrelated exception does get that caller's exception
as its `__context__` — that is Python's rule, it is the caller's exception
and not the router's, and it is outside anything the router controls. The
test calls the router outside any handler, so `__context__` is `None` there.)

**What is lost, stated plainly:** the provider's *stack frames*. The
diagnosis — type name, message, every detail — is still on the raised error,
scrubbed, in the details.

**The claim in the test file** (`tests/models/test_key_secrecy.py`) is now the
one the assertion can see: no key reaches a log line, a ledger payload, or
**an error the router raises** — its message, its details, its chain and its
rendered traceback. The docstring also says what is *not* claimed: a
provider's own exception is the provider's to scrub, and the router does not
vouch for it (it simply never attaches it to an error of its own).

### 2.2 F-4 — the ordinal, and the read it needed

**Chose "none": no read, no ordinal.** The reviewer's second suggestion ("one
read, best-effort") was considered and rejected — the reasoning is in §4.

The discriminator is now `escalation:<the event's own uuid4 hex>`.

* **Not weaker.** The uniqueness argument is the ledger's own: "the event id
  is unique". The wave-2 property — *the ledger must not silently suppress
  the second audit record* — is untouched and is pinned by two tests
  (a restart, and two writers racing).
* **The lineage's sequence is not lost; it is better.** The ordinal was a
  denormalised copy of a fact the ledger already holds exactly:
  `state_version` is dense, per-correlation, and assigned inside the store's
  per-lineage lock (`ledger/store.py::append` takes `lock_correlation`
  *before* reading the tip), so "the Nth crossing of this boundary in this
  lineage" is a fact the ledger answers **deterministically**, including
  under concurrency. The router's copy was racy exactly where the original
  was not: two writers that read the lineage at the same moment took the
  *same* ordinal, so the "per-correlation ordinal" was a sequence only in the
  sequential case.
* **The read is gone.** The escalation path performs no ledger read before
  the write. That removes the O(lineage) parse *and* the new failure point:
  a store whose `read_correlation` raised used to abort the escalation
  **before** the frontier call, so a *label* could cost a crossing of the
  privacy boundary.

**What the human loses:** the label "escalation:3" in the discriminator
column. What the human keeps: the count, from the ledger, and a *better*
ordering than the label gave — the ledger's own.

**The concurrency case is now deterministic**, and the test says exactly what
is guaranteed and what is not:

* both records survive (distinct idempotency keys — the nonce);
* the ledger's order of the two is a **total order**: their `state_version`s
  never tie;
* the *order in which the two writers arrive* is **not** asserted and must
  not be: which writer gets the lineage lock first is the scheduler's
  business, not the ledger's.

### 2.3 F-7 — the mode the router was constructed with

`EscalatingModelRouter.__init__` now captures the deployment's permission
mode when it is available:

* the whole `Settings` handed over → `settings.policy.mode`;
* only the model half (`ModelSettings`, which carries no mode at all) or no
  settings at all → the mode is **unknown**, and the default is
  **`LOCKDOWN`** — the most restrictive mode there is.

`healthcheck(*, permission_mode: PermissionMode | None = None)` uses that
mode when the caller passes nothing; an explicit argument still wins.

**Why LOCKDOWN and not ASK.** "No" is the answer that cannot leak. A router
that does not know its mode has no business assuming that escalation is
permitted, and LOCKDOWN is the mode whose whole meaning is "do not cross".
The default is what runs when nobody says anything, so it must be the safe
one — that is the entire point of a default, and the defect F-7 describes is
precisely a default that was not safe.

**The mode is deliberately *not* added to `describe()`.**
`tests/models/test_settings_resolution.py::test_both_shapes_of_configuration_resolve_identically`
asserts that a router built from the whole `Settings` and one built from the
model half `describe()` identically, and that test is not my file. As long as
`get_model_router` narrows to the model half (today's state) the two agree
by accident; the moment the NEED below is actioned, the whole-`Settings`
router would know the deployment's mode and the model-half one would not —
so putting the mode in `describe()` would break that test at that moment.
The mode is visible in the *behaviour* (the healthcheck) and in the runtime's
own `describe()` (`runtime.py:376` already reports
`mode=settings.policy.mode.value`).

**The NEED** (posted to COMMS, `src/paa/models/__init__.py` is not my
write-set): `get_model_router` currently does

```python
models = resolve_model_settings(settings)
return EscalatingModelRouter(build_local_provider(models), build_frontier_provider(models),
                              settings=models, ledger_store=ledger_store)
```

so the router never sees `Settings.policy.mode`. The change is to hand it the
whole `settings` (`settings=settings`) and keep `resolve_model_settings` for
the two provider halves. Until then the production router uses the fail-closed
default — which is *safe*, and costs nothing today because there is no
in-tree caller of `router.healthcheck()` (verified: `grep -rn "healthcheck"
src/` finds the router's definition, the providers' and the sandbox's, and no
caller of the router's).

## 4. Alternatives considered and rejected

**R-W2-203, option (b) — narrow the claim and keep the chain "for
diagnosis".** Rejected: the chain is the surface that reaches the bug
tracker, and the diagnosis it carried is *already* in the details. Keeping it
means keeping a copy of the provider's exception that the router cannot
prove is clean, in the one place where scrubbing does not apply. (b) would
also have left the wave-2 claim's *shape* intact — "no key in an exception" —
with a footnote, which is how the original over-claim happened.

**R-W2-203, scrub the cause instead of dropping it.** Rejected on
mechanics: the router cannot construct a scrubbed copy of an arbitrary
exception safely (`copy.copy` on a `PaaError` goes through
`BaseException.__reduce__`, which calls `cls(*args)` — and
`ModelUnavailableError.__init__` requires a keyword-only `provider`, so the
copy raises `TypeError`). A hand-rolled copy would be a lie about the
exception's type, and the provider's *frames* would still have to be
re-attached to be worth anything. Dropping the chain and keeping the
diagnosis as data is smaller, honest, and has no failure mode.

**F-4, "one read, best-effort"** (the reviewer's second suggestion). Rejected:
it satisfies "one read" but not "make the concurrency case deterministic",
and it keeps three things the fix is supposed to remove — an O(lineage) parse
on the audit path, a dependency of the *write* on a *read*, and a racy
duplicate of a number the ledger already holds exactly. It also keeps a
label that can repeat, which is the "noise" the finding names.

**F-4, the discriminator as the ledger's `state_version`.** Not reachable:
the discriminator is part of the event, and the event is sealed by the store
*after* the idempotency key is computed — the router cannot know the version
the store will assign. (Wave 2 rejected the same idea in §4(c) of its
report; the reason there was "reading the tip is racy", which is a slightly
different reason from the real one, but the conclusion is the same.)

**F-7, defaulting the healthcheck to LOCKDOWN always.** Rejected: it would
make the healthcheck useless for every router (the frontier's key would
never be in the report) and it would make the mode the router was *given*
irrelevant — the finding is that the mode was thrown away, not that it
should be ignored.

**F-7, adding the mode to `describe()`.** Rejected for the reason in §2.3:
it would break `tests/models/test_settings_resolution.py`'s "both shapes
describe identically" the moment the NEED is actioned, and that file is not
mine.

## 6. Long-run test (source / load / hostile / operability / reversal)

**Source.** The leak's source is a provider's own exception — the one object
in the path that can hold a credential the router cannot recognise. The
tests drive the *real* router over a provider that deliberately leaves its
key in a detail, and assert on the *identity* of the exception the provider
raised, not on a pattern.

**Load (100x, concurrency, partial failure).** The concurrency case is now
covered by a test rather than by a docstring: two routers over one ledger
and one correlation, escalating at the same moment → two records, two
distinct discriminators, and a ledger order with no tie. The partial-failure
case is the *interesting* one and it is covered directly: a store whose
`read_correlation` raises used to abort the escalation before the frontier
call; after the fix the escalation path reads **nothing**, so there is no
read to fail. (A 100× repetition run was not performed: the property under
test is a *guarantee about a write path*, and the five consecutive green runs
plus the mutation battery are the evidence; the reviewer of wave 2 made the
same call for the same reason.)

**Hostile input.** The hostile input is a secret of a shape the router does
not recognise — a Gemini `AIza…` key, a bare token. That is exactly why the
guarantee is "no chain" rather than "a scrubbed chain": a pattern-based
scrub cannot cover an unknown shape, and a chain cannot be pattern-scrubbed
at all without re-implementing the provider's error. The nested-detail
hostile shapes (a list of strings, a dict of lists) are still covered by the
existing `_redact_detail` recursion, and the router's copy of the
diagnosis is scrubbed at every depth.

**Operability (observe, roll back, migrate).** *Observe:* the diagnosis is
still there — `underlying_error`, `underlying_message` and the scrubbed
`underlying_<key>` details — and the scrubbed value is `***REDACTED***`, so
an operator sees that something was removed. *Roll back:* the change is a
pure function of the inputs; reverting `router.py` restores the old
behaviour and the old (leaky) records stay in the ledger as they are. *Migrate:*
nothing to migrate — the discriminator is not parsed by anything, the
pre-change `escalation:<ordinal>:<nonce>` rows remain valid rows, and a
replay does not regenerate them.

**Reversal (which test fails if the fix is reverted?).** Reverting
`router.py` fails **6** tests (listed in §3.1): two for the chain, two for
the discriminator/ordinal, two for the healthcheck's mode. Six targeted
mutations each fail exactly one test (§3.1). Nothing in the fix is
unpinned.

## 8. Known limitations, risks, rollback notes

* **The provider's stack frames are gone from the router's error.** That is
  the price of closing the chain, and it is a real cost: a diagnosis that
  used to be readable from the traceback is now readable only from the
  details. The details carry the provider's message and every detail it
  had — which is the diagnosis — but not the frames.
* **The discriminator lost its human-readable ordinal.** The count is still
  available (and is more reliable) from the ledger's own ordering.
* **The escalation path's write is now the only thing it does to the
  ledger** before the frontier call — one append, no read. If a future
  change needs the lineage's shape at write time, it must be computed by
  the store (which knows the chain) rather than read back by the router.
* **Rollback** is a single-file revert (`src/paa/models/router.py`), plus
  the test files. No data migration, no ledger rewrite; rows written with
  the new discriminator format are read by nothing that parses it.

## 9. Where I am least confident / what the reviewer should scrutinise

1. **The decision to drop the ordinal rather than keep a best-effort read.**
   This is the judgement call in this report. My reasoning: the ordinal was
   a racy denormalisation of a fact the ledger holds exactly, and the brief
   asked for the concurrency case to be *deterministic*, which a racy label
   cannot be. The cost is a human-readable label that is gone from the
   discriminator column. If the orchestrator prefers the label, the
   alternative is a best-effort read — and I would then want the
   "no lineage read" test replaced by a "the read is not fatal" test.
2. **Whether "no chain at all" is too strong for the provider's diagnosis.**
   I have argued above that the diagnosis is not lost (it is in the
   details) and that the chain is the only route to an *unrecognised*
   credential. The reviewer should check the claim that the details really
   carry everything the chain carried, on both changed paths.
3. **`__context__` semantics.** The guarantee is about *the provider's*
   exception. An exception raised while a *caller* handles an unrelated
   exception gets that caller's exception as its `__context__` — Python's
   rule, not the router's. The tests call the router outside any handler,
   so `__context__` is `None` there; a reviewer who wants the guarantee to
   hold under a caller that *is* handling an exception should note that the
   caller's exception is out of the router's reach.
4. **The LOCKDOWN default for a router built from the model half.** It is
   safe, but it is also *silent*: a router that does not know its mode
   never probes the frontier, and nothing says so at runtime. The
   `describe()` discussion in §2.3 is where a reviewer may disagree with
   me; if the mode belongs in `describe()`, then
   `tests/models/test_settings_resolution.py`'s "both shapes describe
   identically" test has to change with it — and that file is not mine.
5. **The five-run evidence.** Five green runs is evidence of *no observed
   flake*, not a rate — I have said so in the report and in the corrected
   T-007 §7.4, and I have not repeated the mistake anywhere else.
