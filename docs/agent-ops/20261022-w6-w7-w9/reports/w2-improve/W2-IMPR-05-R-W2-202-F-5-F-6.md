## 0. The finding, in one paragraph

The wave-2 T-002 report (`W2-IMPL-01-T-002.md` §7.6, §8 and §13.1) says that
boto3's *transfer manager* wraps the driver's `ClientError` in an
`S3UploadFailedError`, that the wrapper "carries neither a response nor a
cause", that the store therefore has "no wrapper to unwrap" on the path
`put_stream` takes, and that the live suite catches the store if it ever
takes the wrapping route (its mutation 11). ADR-0032's decision 4 repeats the
mechanism, and three comments in `minio_backend.py` repeat it again.

**Measured, on both servers: the wrapper carries no response of its own and
no `__cause__`, but the driver's error IS its implicit `__context__`, and
`_driver_cause` follows the `__context__` as well as the `__cause__`.** So
the store's answer is *the same* on both routes, the record's "opaque wrapper"
is false, and the report's mutation 11 **survives all 40 live tests** — which
is what the reviewer measured.

**The code, judged against ADR-0032's intent, is correct.** Every failure
that crosses the blob boundary is a `BlobError`; no raw botocore exception
escapes. The **record** is what is wrong: the ADR's decision 4, three
comments in the code, and four separate statements in the wave-2 report.

**This is the whole finding.** The wrapper is real, it is boto3's, and:

* it carries **no response of its own** (`.response` is `None`) — the record
  is right about *this*;
* it carries **no `__cause__`** — the record is right about *this* too;
* but it carries the driver's error as its **implicit `__context__`**, and
  `minio_backend.py:330` reads `exc.__cause__ or exc.__context__`, so
  `_driver_cause` finds it, reads the code and the status off it, and the
  translation classifies the wrapper **exactly as it classifies the raw
  error**.

The T-002 report's table row — `upload_file` … "carries a cause: **no**" —
is true only of `__cause__`. Read as "the wrapper carries no cause at all",
it is false, and everything the report concluded from it follows.

Why the wrapper carries the `__context__` and not the `__cause__`:
`boto3/s3/transfer.py:452-459` raises `S3UploadFailedError(...)` **inside**
`except ClientError as e:` and without a `from`, so CPython sets the
implicit context. `[VERIFIED .venv/lib/python3.12/site-packages/boto3/s3/transfer.py:452]`

## 2. The judgement: the code holds, the record did not

ADR-0032's intent, in its own words, is in decision 2: *"the translation
happens at the boundary, once"*, and in decision 1: a caller *"catches a
concept — absent, refused, unreachable, corrupt — and never has to import
`botocore` to know which one happened"*. The brief renders the intent as
*"every blob error that crosses the boundary is a `BlobError`"*.

**Judged against that, the code is correct.** §1.3 measured every failure
mode of `put_stream` on both servers: a missing bucket, a missing object,
wrong credentials, a corrupt payload (four readings of it), a dead endpoint,
an out-of-band corruption and a mangled frame. Every one of them arrives as
a member of `paa.storage.coldlake.errors` — `NotFound`, `AccessDenied`,
`MalformedRequest`, `Unreachable`, `Corrupt` — and **no raw botocore
exception crossed the boundary in any of them**. The driver's own error is
in the chain as the `__cause__`, so ADR-0032's decision 6 holds too.

**So the code needed no behavioural change.** What it needed was for its
comments to stop saying something false about the mechanism, and for the
records that repeat the false mechanism to be corrected. That is what this
task did.

### 2.1 The one thing the code *was* missing

Nothing in the tree pinned the claim ADR-0032's decision 4 makes. The unit
suite's stub has no `upload_file` at all, so the wrapping route is
unreachable there; and the live path (`upload_fileobj`) never produces a

## 4. The "two independent implementations" claim — what I did and why

The reviewer's two options were *assert it* or *narrow it*. **I did both,
and the narrowing is the primary fix**, because the assertion cannot reach
what the claim says.

**The narrowing.** The suite never established "independence", and it
cannot: nothing in the environment says which programs the two endpoints
are, and nothing in the S3 protocol says what independence would be. The
file's docstring now says what the suite guarantees — *two servers that
answer differently* — and says plainly that the labels name the
implementations and that the suite does **not** establish independence.

**The assertion.** `test_the_two_servers_are_distinguishable` makes the
narrowed claim **true by construction** rather than leaving it to the
operator's good intentions: the two endpoints must not answer identically.
The discriminator is the set of HTTP response **header names** — a property
of the program that answered, where the header *values* (request ids,
dates) move on every call. Measured on both servers: stable across five
identical requests, and different between them.

**Why the header names, and what it does not prove.** A header name is
program-shaped and version-free, so it does not mistake two *versions* of
one program for two programs. It is not a proof of independence either way:
two different implementations that happened to answer with the same header
names would make the test fail (and its message says so: *"the suite cannot

that matters — two containers of one image — is caught, and it is caught on
a *fact about the program*, not on a convention.

## 8. Residual risks and what the next reviewer should check

1. **The fingerprint is a proxy, not a proof.** The header-name set is
   stable and program-shaped, and it catches the case the review named (two
   containers of one image). It would *also* fail for two genuinely
   different implementations that happen to answer with the same header
   names. The failure message says "the suite cannot tell them apart"
   rather than "they are the same program", so the operator is not misled —
   but a reviewer should decide whether a third implementation is worth a
   richer fingerprint (the error *message* text for a missing bucket is
   another discriminator, and it was not used because it is not stable
   across versions).
2. **`put_stream`'s `upload_fileobj` is pinned only indirectly.** The new
   test asserts that the store hands the driver a **file object**, which is
   what the module's docstring claims and what keeps the spool's in-memory
   phase alive. It does not assert the *name* of the boto3 call. A store
   that uploaded the spool through some third mechanism that still took a
   file object would pass — which is the right granularity, and the
   reviewer may disagree.
3. **The new test's upload does not reach the server.** The store's HEAD
   does; the upload's *request* does not, because the error is substituted
   at the client. That is unavoidable — a server-refused upload cannot be
   provoked on both servers while the store's HEAD succeeds (SeaweedFS
   creates the bucket a write names; RustFS refuses it) — and the exception
   that is substituted is the driver's own, produced by the real driver
   against the real server one call earlier. A reviewer who wants the
   request itself to be real should look at the RustFS-only variant.
4. **`_MAX_CAUSE_DEPTH` is 3 and the chain is 2 deep** in every measured
   case (wrapper → `ClientError`). Nothing in the tree measures the *cost*
   of a deeper chain; the bound is a safety net, and this task did not
   change it.
5. **The independent-review subagent could NOT be run.** Two attempts
   (`code-reviewer` and `general`) both returned *"Subagent depth limit
   reached (1)"* — a platform limit at this dispatch's depth, the same one
   two earlier agents in this run reported. **This work is therefore
   reviewed by one pair of eyes**, with the checks the reviewer was asked
   for performed by hand: the four mutations (§5.3), the two-container
   demonstration (§4), the sentence-by-sentence reading of decision 4
   against the code (§5.2), the sweep for the old mechanism in all three
   records (§5.5), the scope check (§5.6), and the scoped gate (§5.1). A
   reviewer should read it as one pair of eyes and not as an independent
   one.
