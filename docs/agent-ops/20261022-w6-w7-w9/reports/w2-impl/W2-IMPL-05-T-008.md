## 3. Root cause

Three separate causes, one per clause. None of them is "the tests are
missing" alone — two of them are a **documented contract the code does not
keep**, and one is a **documented contract nobody had checked**.

1. **The percentiles were labelled, never valued.** The file's own test
   compared `summary["p95"]` to `percentile(sorted(values), 0.95)`, so the
   suite pinned the *wiring* and asserted nothing about the *number*. The
   module's argument for choosing linear interpolation over nearest rank —
   *"the nearest-rank alternative can only ever return an observed sample"* —
   was a comment, not a check.

2. **`finish_run`'s COALESCE promise was false for one parameter.**
   `[VERIFIED src/paa/observability/runs.py:341]` — the UPDATE coalesced
   `tokens_consumed`, `peak_rss_mb`, `model_used`, `escalated`, `telemetry`
   and `error_detail`, but wrote `exit_code = ?` plainly. The docstring
   says *"Every optional parameter left as `None` preserves the existing
   value"*, so a second finish that omitted the exit code **erased** the
   first one — and because `ExecutionRun.status` is derived from
   `exit_code` (`"OK" if exit_code == 0 else "ERROR"`), omitting a field
   turned a recorded success into a recorded failure. The two parameters
   that are *not* measurements — `ended_at` and `duration_ms` — are the ones
   a finish is *for*: `ended_at=None` must mean "now" (a finish that did not
   end the run would leave it `IN_FLIGHT` forever) and `duration_ms` is
   computed, never supplied. So `exit_code` was the only parameter the
   promise was false for, and it was false for exactly the case the
   promise exists to cover.

3. **`_safely`'s boundary was real, correct, and undocumented.** Catching
   `Exception` rather than `BaseException` is the *right* choice —
   `KeyboardInterrupt` and `SystemExit` are how a process is told to stop,
   and swallowing them would produce a runtime that cannot be interrupted.
   What was missing was the statement: the module docstring asserted the
   opposite of what the code does.

4. **`logging.py` had no test at all**, so five documented claims — the
   correlation id being a field rather than a substring, the call site
   winning, the previous value being restored, ISO-8601 UTC timestamps, JSON
   being opt-in — were assumptions.

## 4. Approach chosen and why

**Hand-computed values, not values read off the function.** Every number in
`TestTheHandComputedValues` is derived on paper in the test's docstring
(`rank = (n-1)·q`, `lower = floor(rank)`, `upper = ceil(rank)`,
`value = v[lower] + (rank-lower)·(v[upper]-v[lower])`) and the derivation is
written next to the number. A test that reads its expectation off the
function under test passes for any implementation whatsoever.

**The module's own argument turned into an assertion.** The claim is not "the
value is 4.8" — it is "the value is **not an observed sample**", because that
is the property that separates interpolation from nearest rank. So
`test_the_result_is_not_one_of_the_samples` asserts exactly that, and
`test_the_result_lies_strictly_between_the_samples_it_interpolates` asserts
the stronger geometric form.

**The algorithm pinned by a property, not by four more numbers.** Four
hand-computed values pin four points; a property pins the line through
every point. Two properties do the work:

- `test_each_sample_sits_at_its_own_quantile` — sample *k* is the answer at
  `q = k/(n-1)`. **This is what `rank = (n-1)·q` means**, read backwards, and
  it is the statement that separates the formula from its neighbours:
  nearest rank puts sample *k* at `k/n`, and a formula on `n·q` stretches
  the samples across the wrong end of the range.
- `test_the_value_sits_where_the_rank_formula_says` — drawn positions on the
  grid, asserting the value is strictly between the two neighbours at an
  interior fraction and *is* a neighbour at the endpoints.

**The adversarial quantile is drawn, not hoped for.** The fraction strategy
is `st.one_of(st.just(0.0), st.just(1.0), st.floats(1e-3, 1-1e-3))` — the
two endpoints are *explicitly* in the strategy, because they are the
positions where the answer is an observed sample and the boundary of the
rule. The index is drawn from `st.integers(0, len(samples)-2)` *after* the
sample, so it ranges over exactly the positions that sample has, including
the first and the last interval.

**The sample grid is quarters, not arbitrary floats — deliberately.** The
strict-betweenness property needs the interpolated value to be observably
*between* two samples. With two adjacent doubles near 1e6 the interpolated
value rounds straight back to the lower one and the property would fail for
reasons of floating point rather than reasons of algorithm. Multiples of a
quarter are exactly representable and never closer than 0.25 apart, so a
thousandth of the gap is still visible in the result.

**The fix for `exit_code` is one word, and the docstring is made exact.**
`exit_code = COALESCE(?, exit_code)`. The behaviour is unchanged for every
*first* finish (the column is NULL, so `COALESCE(NULL, NULL)` is NULL and
the status is still `ERROR` for a run that ended without saying how). Only
the *second* finish changes, and there the change is the point: a caller
that knows less must not erase what a caller that knew more recorded. The
docstring now names the two exceptions (`ended_at`, `duration_ms`) instead
of leaving a blanket promise that two parameters quietly broke.

**Alternatives considered and rejected.**

- *Narrow the docstring instead of fixing the code* — i.e. say that only the
  measurement parameters are preserved. Rejected: the other five parameters
  are already coalesced, so the exception would have been one parameter
  wide, and the parameter it excluded is the one the derived `status`
  depends on. Narrowing the prose would have made the code and the prose
  agree at the price of the behaviour.
- *Leave `exit_code` alone and assert only what the code does* — rejected:
  that is asserting the symptom, and the brief asks for the promise.
- *Make `_safely` catch `BaseException`* — rejected: it would make a
  telemetry failure able to swallow `KeyboardInterrupt`, which is a
  correctness regression in the other direction. The brief asks for the
  boundary to be **pinned and documented**, not removed.
- *Test `_safely` directly* — rejected: it is a private helper, and the
  boundary is observable through the public seam (the exporter), which is
  where a user meets it.
- *Shadow `sys.modules["logging"]` in-process to demonstrate the collision*
  — rejected: it poisons the module for every later test in the session. The
  demonstration runs in a child interpreter instead.

## 8. Long-run test

* **Source.** The data comes from three places: the caller's own
  observations (arbitrary finite floats), the clock (`utc_now`), and the
  caller-supplied identifiers. Every one of them is validated at the
  write: a non-finite observation, a quantile outside `[0, 1]`, a trace id
  that is not a UUID, a capacity that cannot retain anything.
* **Load.** The registry is guarded by a `threading.Lock` rather than an
  `asyncio.Lock` — a deliberate choice recorded in the source, because
  the sandbox watchdog samples from a real thread. The histogram's ring
  is O(1) per observation; `summary()` is O(n log n) over the retained
  window, which is bounded at 4096 samples. `query_runs` is indexed on
  `started_at DESC`; the new `trace_id` tie-break is applied inside the
  index's order, so the cut stays reproducible without a second index.
* **Partial failure.** A failed exporter does not break the traced
  operation (`Exception`); a failed *metric* does not either; a failed
  *bridge* does not either. What is **not** swallowed is a
  `BaseException`, and that is pinned.
* **Hostile input.** NUL, traversal and injection are not applicable to
  this package (no string is interpolated into SQL here — the only
  interpolation is a fixed column list). The hostile inputs that *are*
  applicable are covered: a non-UUID trace id, an out-of-range quantile,
  a `nan` quantile, a non-finite observation, an overflowing total, a
  zero capacity, a shadowed `logging` module.
* **Operability.** Every published number is observable in the snapshot;
  every run row carries its outcome, its duration and its telemetry; the
  retained-span ring is bounded and clearable; the run repository can be
  swept by age without touching an unfinished run.
* **Reversal.** Which test fails if the fix is reverted? All of them —
  the table in §7 is the answer, one row per mutation. The three source
  fixes (the `COALESCE`, the total order, the `window` key) each have a
  named test that goes red when they are undone.

## 9. Edge cases and abuse scenarios

**Handled, and where:**

| Case | Where |
|---|---|
| a quantile outside `[0, 1]`, on an empty series too | `metrics.py::percentile` — the check now runs before the empty-series shortcut |
| a `nan` quantile | same — `0.0 <= nan <= 1.0` is false, so the range check catches it |
| a non-finite observation | `metrics.py::Histogram.observe` |
| an observation that would overflow the running total | `metrics.py::Histogram.observe` — the published summary has to be JSON |
| a counter that would overflow | `metrics.py::MetricsRegistry.counter` |
| a histogram capacity that cannot retain anything | `metrics.py::Histogram.__post_init__` and `MetricsRegistry.__init__`, one shared rule |
| a trace id that is not a UUID | `runs.py::_canonical_trace_id` (pre-existing) |
| a partial finish that omits what an earlier finish wrote | `runs.py::finish_run` — every optional parameter is coalesced |
| a second finish that omits the exit code | same — the exit code is coalesced too |
| an unfinished run of any age | `runs.py::purge_older_than` — `ended_at IS NOT NULL` |
| a run started exactly at the cutoff | same — the boundary is strict (`<`), and that is asserted |
| an exporter raising `KeyboardInterrupt` | `tracing.py::_safely` — it propagates, and the span is still finished and retained |
| a test that shadows `sys.modules["logging"]` | `tests/observability/test_logging.py` — the demonstration runs in a child interpreter |

**Consciously not handled, and why:**

* *A `BaseException` from an exporter does not break the traced
  operation.* Making it safe would mean swallowing `KeyboardInterrupt`,
  which is how a process is told to stop. The brief asks for the boundary
  to be pinned and documented; it is.
* *The percentile label's half-way convention.* See §13 — the convention
  is Python's banker's rounding, and changing it would split the history
  of every half-way series.
* *A concurrent `MetricsRegistry` snapshot racing an observation.* The
  registry takes the lock for the whole snapshot, so a snapshot is
  internally consistent; there is no test for the interleaving because
  the lock makes the interleaving unobservable.
* *`query_runs`'s `limit` is not validated.* A negative limit means "no
  limit" on SQLite and is an error on PostgreSQL — a substrate
  difference, but one that only a caller passing a nonsense limit can
  reach, and there is no caller.

**Unknown.** Whether the *server* substrate behaves identically for the
new `trace_id` tie-break — the ordering is now specified, so it should,
but the PostgreSQL path was not exercised here (it needs a live server,
which the standing orders forbid me from starting). The lock's own
substrate-comparison tests are wave 1's and they do not cover this query.

## 10. Performance and security considerations

* **Performance.** The added work in the hot path is one `math.isfinite`
  per observation and one per counter increment. `percentile` is
  unchanged in complexity. `query_runs`' extra sort key is applied
  within the existing index's order, so the plan does not change.
* **Security.** No new I/O, no new SQL interpolation, no new
  deserialisation. The `json_valid` constraint on the telemetry column
  is *strengthened* in practice: a snapshot can no longer contain a
  non-finite number, so the column's check constraint can no longer be
  the thing that discovers the problem.
* **The standard-library name collision** is the one genuine hazard in
  this package, and it is now demonstrated in a child interpreter rather
  than left as folklore.

## 13. Out-of-scope findings

Three, all posted to `COMMS.md` as `FINDING`s.

1. **`storage/relational/database.py::dumps` can write invalid JSON.**
   `json.dumps` writes a non-finite float as the bare token `Infinity`, and
   the `telemetry` column carries `CHECK (json_valid(telemetry))`.
   `[RAN SELECT json_valid('{"x":Infinity}') -> 0]`. The general fix is
   `allow_nan=False` in `dumps` — `storage/relational/**` is **not** my
   write-set, so I refused the value at the write in `metrics.py` instead.
   The general fix belongs upstream, and it would protect every other JSON
   column in the tree, not just the telemetry one.
2. **The percentile label uses banker's rounding.** `round(99.5)` is 100
   but `round(98.5)` is 98, so a p98.5 series is filed under `"p98"` —
   which contradicts the source comment's "the key names the percentile the
   value *is*". **I did not change the rule**, for two reasons: the brief
   states the labels are *already pinned* and that the gap is the *values*,
   and a rule change splits the history of every half-way series — the very
   thing the test file's own docstring warns about. Instead the behaviour is
   **pinned by a test** (`test_a_half_way_quantile_takes_the_even_label`)
   and the **comment corrected** to say what the code does. The one-line
   alternative, if the orchestrator wants it, is
   `math.floor(quantile * 100 + 0.5)` — it keeps the existing `p100`/`p2`
   expectations green. The default quantiles (0.50, 0.95, 0.99) are not
   half-way, so no series the system produces by default is affected either
   way.
3. **`configure_logging`'s stdlib level is best-effort.**
   `logging.basicConfig(level=…)` is a **no-op** when the root logger
   already has handlers — which is the case under pytest and in any process
   where a library added a handler first. structlog's own level *is*
   applied (`make_filtering_bound_logger`), so the observable behaviour is
   right; only the stdlib root level is skipped. The fix would be
   `force=True`, which removes the root logger's existing handlers — a
   change with real blast radius on a shared global, so it is not mine to
   make. Noted in the report rather than fixed.

## 15. Where I am least confident / what the reviewer should scrutinise

1. **The `exit_code` `COALESCE`.** I chose to make the code keep the
   docstring's promise rather than narrow the promise to fit the code. The
   alternative reading — that `exit_code` is the *outcome* and a finish
   always sets it — is defensible, and under it the fix would have been a
   docstring change instead of a SQL change. I went the other way because
   the other five optional parameters are already coalesced (so the
   exception was one parameter wide), because `status` is derived from
   `exit_code` (so the omission silently flipped a success to a failure),
   and because "an omission is not a value" is the rule the rest of the
   method already follows. **This is the change most worth a second
   opinion.** It is behaviour-preserving for every first finish.
2. **The sample grid in the hypothesis strategy.** Multiples of a quarter,
   because a strict-betweenness property is not observable between two
   adjacent doubles near 1e6. That is a real constraint, stated in the
   strategy's comment — but it means the property is exercised over
   well-separated samples, not over arbitrary ones. The two properties that
   *do* use arbitrary floats (the range bound and monotonicity) are
   unaffected. A reviewer who wants the betweenness property over
   arbitrary floats would need a relative tolerance, and a relative
   tolerance would weaken it.
3. **The total-order test's dependence on insertion order.** Without the
   fix, SQLite returned the ties in insertion order, which is what makes the
   test red here — but that is SQLite's *unspecified* behaviour, so on
   another substrate the test might not have gone red. The test is correct
   either way: with the fix it asserts the *specified* order, which both
   substrates now produce.
4. **The six source fixes are the part a reviewer should push on hardest.**
   Four of them (the `COALESCE`, the total order, the `window` key, the
   quantile order) are strictly contract-keeping. Two (the finite-total
   guards and the capacity guard) are *new* refusals — they turn a
   previously-accepted input into a `ValueError`. The blast radius is nil
   (nothing in `src/` calls this package), but a reviewer may reasonably ask
   whether refusing at the write is too strong a hand.
