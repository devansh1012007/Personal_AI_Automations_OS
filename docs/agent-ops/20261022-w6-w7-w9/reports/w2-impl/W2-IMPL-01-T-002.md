## 2. Verification that the problem exists

### 2.1 The problem, as the code stands

`[VERIFIED src/paa/storage/coldlake/minio_backend.py]` — the store translates the driver's errors
through a **table of S3 error codes** (`_S3_OBJECT_MISSING_CODES`, `_S3_BUCKET_MISSING_CODES`,
`_S3_REFUSED_CODES`, `_S3_RETRYABLE_CODES`) plus a status fallback and an MRO class-name fallback. The
table's correctness is the whole question, and the table was written by the same hand that wrote the

`[VERIFIED tests/storage/test_minio_backend.py:34]` — the stub is a duck-typed fake. The previous
dispatch's own module docstring records the gap precisely: it has no `head_bucket`, no `create_bucket`
and no `list_objects_v2`, so the **bucket probe** — the mechanism ADR-0032's second Amendment is
entirely about — was never exercised against a server that can answer it.

### 2.3 Three claims in the inherited draft that were **wrong**

The previous dispatch's draft was never run, and it carried three claims that do not survive contact
with a server. All three are corrected in the committed code.

1. **"SeaweedFS accepts a bucket name with an underscore; RustFS refuses it."** — `[VERIFIED]` **both
   refuse it**, with `InvalidBucketName`, before the bucket exists. The draft's conftest docstring said
   otherwise, and the correction is in the committed conftest (`tests/storage/conftest.py:122-132`).
   The *conclusion* (spell the name with hyphens) was right; the reason given for it was not.
2. **"The credentials default to the empty string, which is what a server that does not authenticate
   wants."** — half right and half unstated. The empty string is a *named* credential no
   authenticating server accepts (SeaweedFS: `InvalidAccessKeyId`; RustFS: `UnauthorizedAccess`, and
   the store reports both as `AccessDenied`). The docstring now says that, and says **why** the
   default is the empty string rather than unset: an unset credential would let boto3 resolve one
   from the developer's own environment or `~/.aws/credentials`, so a test pointed at a server could
   authenticate with a key the operator never named.
3. **"The bucket is `paa_s3_test_{pid}_{uuid8}`."** — the committed name is `paa-s3-test-{pid}-{uuid8}`,
   with hyphens, because both servers refuse underscores (§2.2). The draft's own prose said hyphens
   while its own comment said underscores; the comment was wrong.

### 2.4 One test in the inherited draft was **vacuous**

`test_a_second_put_of_the_same_bytes_stores_one_object` asserted that the bucket holds one object
after two puts of the same bytes. That is true **by construction**: the key is derived from the
content, so a second *write* lands on the very same object and the listing is blind to the difference
between "the store looked and did not write" and "the store wrote again".

`[RAN]` proof, not inference: the mutation that makes the store's dedup short-circuit disappear
(`_locate` → always `None`) leaves that test **green**. The listing cannot see the no-op.

The store's dedup is a load-bearing property — a second write of the same bytes costs a request, a
version and a multipart abort for nothing — so the suite now observes the **request** through a spy
in front of a **real** boto3 client, over a real server, and asserts that the second put looked
before it wrote and did not write. `[RAN]` the same mutation now fails
`test_a_second_put_of_the_same_bytes_is_a_no_op` on both servers.

The same argument applies to `stat`, and the draft's `stat` test had the same hole: the store has a
fallback that re-reads the blob to count its bytes when the raw-size record is missing, so a broken
metadata round-trip still produces the right size. The committed test asserts that `stat` did **not**
download the body, which is what the docstring claims. `[RAN]` the mutation that hides the raw size
now fails it.

### 2.5 Two failure modes the inherited draft did not cover

1. **`put_stream` against a missing bucket.** The draft's missing-bucket test exercised `put`,
   `get`, `get_stream`, `exists`, `stat` and `delete` — but not the *other write path*. The
   `put`/`put_stream` divergence is the very defect ADR-0032's decision 4 exists to close, and
   `put_stream` takes a different route to the server (`upload_fileobj` against `put_object`), so it
   is the one that can disagree. The committed test drives **both** write paths at a missing bucket
   of their own and asserts they answer alike. `[RAN]` the mutation that makes `put_stream` take the
   wrapping variant is caught by it (§7.6).
2. **The write path's answer to a missing bucket at all.** The draft asserted it only through the
   "if the server created the bucket, the store's answers are true" branch.

## 3. Root cause

Not a bug: a **coverage shape**. The S3 path was tested only against a stub that could not raise the
failures the path exists to handle — no `head_bucket` (so the bucket probe was unreachable), no
`create_bucket` (so the "a cold lake whose bucket is missing fails on its first write" clause was
unreachable), no `list_objects_v2` (so nothing could see the server's own view of the bucket), and no
transfer manager (so the upload-wrapper unwrapping was unreachable). A stub shaped like the code
proves the code agrees with itself.

## 4. Approach chosen and why

**The suite consumes servers through the environment, and the run supplies them.** The brief asks for
both "a test-owned server per session, per implementation" and the `PAA_TEST_S3_*` env convention with
a clean skip. Those are reconciled the way the repository already reconciles the same tension for
PostgreSQL (`tests/storage/conftest.py:29`, `PAA_TEST_POSTGRES_DSN`): **the environment names a
server; the fixture makes a resource of its own on it.** A suite that started its own containers
could not skip cleanly, and a suite that skipped cleanly could not be pointed at a server an operator
already runs. The containers this run used were started by the run (unique names, loopback ports,
removed in teardown) and the suite was pointed at them by environment.

**The label convention is one rule, not two.** `PAA_TEST_S3_ENDPOINT` is the label-less member of
`PAA_TEST_S3_<LABEL>_ENDPOINT`; the same four names describe any number of implementations. The label
is what a failing test id names, and that is the entire point of running one body twice: a difference
between two implementations has to be *visible*.

**The two invisible claims are observed in the request.** A spy in front of a real client (§2.4). It
is a wrapper, not a fake: every request reaches the server and every answer comes back unchanged.

**No mock, and no list operation.** The `BlobStore` contract did not grow a list operation (D-6). The
one assertion that needs to see the raw object uses a raw boto3 client; the contract-level assertions
use `exists()` / `stat()` / `delete()`.

### Alternatives considered and rejected

* **Start the containers from the test session.** Rejected: the acceptance criterion requires a clean
  skip with no `PAA_TEST_S3_*` set, and a session that starts a Docker daemon's containers cannot
  skip cleanly — it would have to decide at import time whether to skip, and a developer with Docker
  but no intention of running two S3 servers would get two anyway. The recipe is in the module's
  docstring and in ADR-0033 instead.
* **Point the suite at the deployment's `paa-stack-seaweedfs-1`.** Rejected twice over: it publishes
  **no host port**, so it is unreachable from the host, and writing to it would be writing to the
  operator's data. Never touched; verified still running and healthy at teardown.
* **Assert a *single* implementation's behaviour as the truth.** Rejected: the point of the second
  server is that a client and a server written by the same mind agree about everything that matters,
  including the things that are wrong. Where the two differ, the suite asserts the **invariant that
  holds on both** and reports the difference.
* **Add a `list` operation to the `BlobStore` protocol** so the suite could enumerate. Rejected: D-6,
  and ADR-0032 records the asymmetry. Enumeration is not part of a content-addressed store's contract.
* **Mock the transfer manager to exercise the upload-wrapper unwrapping.** Rejected: the real driver
  is available and the real path is better. §7.6 shows the live suite catches the divergence when the
  driver really does wrap.

### `tests/storage/conftest.py` — the fixture

`s3_bucket` is **session**-scoped and **indirectly** parametrised (the server arrives as
`request.param`), so the bodies carry no server plumbing and a failing id names the implementation.
The bucket is `paa-s3-test-{pid}-{uuid8}`, created once per run and **dropped in teardown**; it is
emptied between tests so each test starts from an empty namespace.

*One design note worth recording, because it is not obvious:* the bucket is **per run, not per
test**. A SeaweedFS server maps every bucket onto a filer collection with a volume of its own, and
it cannot allocate one for an unbounded number of buckets — the volume server runs out and every
write then fails with a `500 InternalError` that names no writable volumes. A suite that made a
bucket per test exhausted the server in a dozen tests. One bucket per run is one collection, which is
what the deployment uses too.

| 11 | `put_stream` written through the **wrapping** variant (`upload_file`) | `test_both_write_paths_agree_about_a_missing_bucket[RUSTFS]` | **caught** |

Mutations 3a/3b are the interesting negative: the unreachable answer has **two independent supports**
(the driver's class names off the MRO, and the errno of the unwrapped cause), so breaking either alone
leaves the answer right. The suite asserts the *answer*, which is the right granularity; asserting one
of the two supports would be asserting an implementation detail.

Mutation 10 is the interesting positive-negative, and it is a finding rather than a gap — §8.1.

### 7.7 Flakiness

`[RAN]` the live suite three times back to back: 40 passed each time (23.05s, 20.17s, ~23s). The
bucket is emptied between tests, so there is no order dependence; the suite's bodies share no
mutable state beyond the run's own bucket, and the "absent" buckets are per-test and dropped in
teardown. The only timing-sensitive assertions are the connection-refused one (a closed port, bound
and released rather than a fixed number) and the spool-spill one (a 1.125 MiB incompressible payload
against a 1 MiB cap, so the spill is not marginal).

## 8. Long-run test

**Source.** The suite's input is a payload and a digest. The digests are the interesting source: a
digest that is not 64 hex characters is refused before it becomes a key, and the two hostile shapes
(the unicode one and the traversal-shaped one) are asserted. The payload sizes are 0, 20, 100, 1000
and 1 179 648 bytes — the last one chosen to be **incompressible** (sha256 of a counter), because a
compressible payload would shrink under the spool cap and never spill, and the test would then pass
without testing the path it claims to test.

**Load.** The suite is a single process against a single session bucket. The interesting load
property is the *bucket count*: a SeaweedFS server maps every bucket onto a filer collection with a
volume of its own, and a suite that made a bucket per test exhausted the server in a dozen tests
(§5). The suite therefore makes **one** bucket per run per server, and empties it between tests. Two
servers, two buckets, two requests per lifecycle step. Not a throughput test, and it does not claim
to be: the store's production caller is a daemon writing cold-lake signals, and this suite proves
correctness against two implementations, not concurrency.

**Partial failure.** This is where the suite earns its keep, and it is the whole reason it exists.
Every failure mode is a *partial* failure of the substrate — the server is there and says no, or the
server is not there, or the bytes are wrong — and each is asserted to arrive as a **named concept**
(`NotFound` / `AccessDenied` / `Unreachable` / `Corrupt`) with the identifiers in the details and the
driver's own wording in the `__cause__`. The raw-exception escape sites are what a partial failure
produces when nobody translated it, and there are six of them.

**Hostile input.** The digests (§Source). The payload size above the spool cap. The **corrupt
content** case is the hostile one in the interesting direction: the bytes are replaced *behind the
store's back*, with a raw boto3 client, so the address is right, the object is there, and the bytes
are wrong — and the store's answer must be `Corrupt` on both read paths, not a transport failure and
not plausible-looking data handed to a caller that would then archive it. The bad-frame case is the
same idea one layer down: a valid object whose payload is not a frame.

**Operability.** The failure modes name the *remedy*, which is the point of the vocabulary:
`Unreachable` is retryable, `AccessDenied` is not (the operator has to go and fix the credentials or
the policy), `Corrupt` is archive damage (quarantine it, do not retry the read), `NotFound` is
nothing (the thing simply is not there). A caller that catches `StorageError` still catches all of
them; a caller that wants to know *which* can now say so. The details carry identifiers only — `key`,
`sha256`, `bucket`, `namespace`, `s3_code`, `http_status`, `driver_error` — because they are merged
verbatim into a ledger payload, and the driver's own wording is the `__cause__` where it cannot reach
a ledger.

**Reversal — which test fails if the fix is reverted?** Named, per fix:

| wave-1 fix | the test that goes red without it |
|---|---|
| the bucket probe (ADR-0032's second Amendment) | `test_a_missing_bucket_is_not_found_with_the_bucket_namespace` |
| the `namespace="bucket"` rule | `test_a_missing_object_is_not_found_without_the_bucket_namespace` |
| the refusal classification | `test_wrong_credentials_are_access_denied` |
| the unreachable classification | `test_an_unreachable_endpoint_is_unreachable` |
| verify-on-read | `test_content_corrupted_out_of_band_is_corrupt` |
| the corrupt-frame classification | `test_a_frame_that_is_not_a_frame_is_corrupt` |
| the upload-wrapper unwrapping (the *outcome* of it) | `test_both_write_paths_agree_about_a_missing_bucket` |
| the dedup short-circuit | `test_a_second_put_of_the_same_bytes_is_a_no_op` |
| the spool cap | `test_a_payload_above_the_spool_boundary_round_trips` |
| the raw-size record | `test_exists_and_stat_describe_a_stored_blob` |

Every one of the ten was confirmed by a runtime mutation, not by argument (§7.6).

## 9. Edge cases and abuse scenarios

**Handled.**

* A missing bucket, from every method, with the namespace detail.
* A missing object, with the namespace detail **absent** — the rule is "present ⇔ the namespace is
  what is missing", and the suite asserts both directions.
* Wrong credentials, on a HEAD (the first thing every method does) and on a write.
* An endpoint that is not there — a **bound-and-released** loopback port, not a fixed number, so
  "the endpoint is unreachable" cannot be confused with "the endpoint is something else".
* Content corrupted out of band, and a frame that is not a frame.
* A payload of zero bytes; an uncompressed payload; a payload over the spool cap.
* A digest that is not hexadecimal; a digest shaped like a path.
* A **second** write path against a missing bucket, with a missing bucket **of its own** — the first
  write on a server that creates buckets would leave the second one writing into a bucket that is
  already there, and the second path would never meet the condition at all.
* A bucket name carrying an underscore — refused by both servers, and the suite's own name is spelled
  so it cannot happen.
* An empty credential — refused by both servers, and the store reports the refusal as
  `AccessDenied`, which is the right answer for "the server said no".

**Consciously not handled.**

* **Multipart uploads of the store's own.** `put_stream` above 8 MiB would take the multipart route
  inside boto3. The suite's largest payload is 1.125 MiB. The failure of a multipart upload is still
  a `ClientError` (measured, §8.1) and the classification is the same, so the *classification* is
  covered; the multipart *mechanics* are boto3's and not this client's.
* **Listing.** The contract has no list operation (D-6). The raw client is used where the suite needs
  to see the server's own view of the bucket, and the asymmetry is recorded in ADR-0032.
* **Presigned URLs, versioning, encryption, replication, lifecycle rules.** Not used by the cold
  lake; the client uses nine S3 operations and those nine are covered.
* **A server that is wrong in a way this client never asks about.** Out of scope by construction —
  see ADR-0033's limits.

**Unknown.**

* Whether a *third* implementation would agree with these two. Two servers agreeing is evidence that
  the client's answers are not an artefact of one server's habits; it is not a proof.

## 10. Performance and security considerations

**Performance.** The suite's cost is 40 tests in ~23 s against two local servers, of which the 1.125
MiB payload and the two connection-failure probes dominate. The store's own cost model is unchanged —
this suite adds no request to any production path. The one request the store makes per *absent*
blob is the bucket probe (ADR-0032's second Amendment), and the suite measures the consequence: an
absent blob costs a HEAD and a HEAD-bucket. The suite is the first thing that has ever *observed*
that cost against a server, and it confirms the probe's answer is the same on both implementations.

**Security.** The suite holds no secret. The credentials are the throwaway `paa-test-key` /
`paa-test-secret` of a container the run created and removed; they are not in the repo, not in the
report, and not in COMMS. The store's own ADR-0032 guarantee is exercised and holds: the details
carry identifiers only, and the driver's wording — which can quote an endpoint URL — stays in the
`__cause__`. The suite asserts the *class* of every failure and the *identifiers*; it never asserts
on the driver's text, so it does not depend on a message shape. The `test_a_unicode_digest_is_refused`
body asserts the *bounded* echo of a caller-supplied value, because an unbounded caller-supplied
string in a ledger payload is a leak, and the bound is the property.

## 12. Deviations from the plan/brief; ownership issues; deferred dependencies

**Deviations.**

1. **The env convention carries an optional label.** The brief names four variables
   (`PAA_TEST_S3_ENDPOINT`, `…_ACCESS_KEY`, `…_SECRET_KEY`, `…_BUCKET`). The suite needs **two**
   servers in one run, and the house convention is one variable per *thing*. The label
   (`PAA_TEST_S3_SEAWEEDFS_ENDPOINT`) is the same four names with a label in front of the last word;
   the unlabelled spelling is the label-less member of that one rule, so the brief's convention still
   works exactly as written for a single server. The label is what a failing test id names, which is
   the point of running one body twice.
2. **`PAA_TEST_S3_BUCKET` names the BASE of the test's bucket**, not a bucket to use. The brief says
   the variable names the *server* and the fixture makes its own bucket; a variable naming a bucket to
   use would contradict that. So it is the base name and the fixture appends `{pid}-{uuid8}`.
3. **The bucket is per run, not per test.** §5. The reason is measured (a SeaweedFS server cannot
   allocate a filer collection per bucket without exhausting its volume server), and the alternative
   was a suite that fails after a dozen tests for an environmental reason.
4. **A spy, in two tests.** §2.4. A wrapper around a *real* client, not a fake; the stub stays the
   unit suite's tool.

**Ownership issues: none.** `git status` shows no change outside the four files in the write-set, and
the ownership table (`docs/agent-ops/20261022-w6-w7-w9/ownership/W2.tsv`) lists exactly those four
paths for W2-IMPL-01. `src/paa/storage/coldlake/**` was read and **not** edited; the one defect the
live suite found in that package is §8.1, and it is a defect in a *record*, not in the code.

**Deferred dependencies: none.**

## 13. Out-of-scope findings

### 13.1 ADR-0032's decision 4 mis-states the mechanism (a record defect, wave 1's file)

ADR-0032's decision 4 says: *"`put()` writes through `put_object` and `put_stream()` through
`upload_fileobj`, and boto3's transfer manager catches the driver's `ClientError` and raises an
`S3UploadFailedError` instead — without chaining it explicitly, so the original is the implicit
`__context__`."*

**Measured against both servers, on boto3 1.43.117** (`[RAN]`, single-part and multipart alike):

| call | raises | carries a response | carries a cause |
|---|---|---|---|
| `upload_fileobj` — the call `put_stream` makes | the driver's `ClientError` (`NoSuchBucket`) | **yes** | no |
| `upload_file` — the filename variant | `S3UploadFailedError` | **no** | **no** |

So on the path the store actually takes there is **no wrapper to unwrap**: the raw `ClientError`
carries the answer and the store reads it directly. The *outcome* ADR-0032 wanted — one answer from
both write paths — is reached, by a different route than the record describes.

The wrapper is not a fiction: it is what `upload_file` produces, and it is **opaque** — no response,
no cause, and therefore nothing for the translation to read. The live suite proves what happens if
the store ever takes that route: the answer degrades from `NotFound` to the unclassified
`BlobFailure`, and the two write paths stop agreeing. Mutation 11 (§7.6) reproduces it exactly, and
the committed test catches it.

**The record is wrong; the code is not.** The unwrapping machinery is still load-bearing — for the
connection-error chain, where the cause is the raw `ConnectionRefusedError` — and the translation is
correct on the path the store takes. What ADR-0032 mis-states is the *mechanism*. A maintainer who
believed the record would not have thought to check whether the wrapper it describes is ever produced
on this path; that check is ADR-0033's, and the answer is "not on this path, in this boto3".

`docs/adr/0032-blob-error-vocabulary.md` is wave 1's record and is **not** in my write-set, so I have
not edited it. **The exact change required, for whoever owns it:** decision 4's first two sentences
should read that `put_stream` writes through `upload_fileobj`, that boto3's *`upload_file`* — not
`upload_fileobj` — is the variant that wraps the driver's `ClientError` in an `S3UploadFailedError`,
that `upload_fileobj` propagates the `ClientError` with its response intact, and that the wrapper
`upload_file` produces carries neither a response nor a cause. The decision's *conclusion* — that
both write paths must answer alike — stands, and the live suite now proves it.

**Nothing in `src/paa/**` needs to change for this.** The store's behaviour is right.

### 13.2 Two codes the table does not name, and why that is fine

`UnauthorizedAccess` (RustFS's answer to an empty access key) and `InvalidBucketName` (both
servers' answer to a name with an underscore) are not in ADR-0032's code table. Neither can reach the
store on a path it takes: the first is covered by the **status** fallback (403 → `AccessDenied`), and
the second is about a name the store never invents. The table is deliberately small, and the
classification does not depend on it being complete — a code the table does not name is still
classified when the **status** names the judgement. Recorded in ADR-0033; no change proposed.

## 14. Known limitations, risks, rollback notes

**Limitations, stated plainly.**

* The suite is **skipped** on a developer laptop. That is the honest state of it, and the `dev` extra
  is what makes the skip mean "no server" rather than "no driver". Making it a gate is a CI job
  (wave 3's T-009), not this task.
* Two implementations are not a population (§9).
* It is not a conformance test of S3 (ADR-0033's limits).
* The `ensure_bucket=True` construction path is not covered — it would create a bucket in whatever
  namespace it was pointed at, which is the operator's business, not a test's.

**Risks.**

* The suite depends on `boto3`'s *request* API and on the two servers' behaviour. A boto3 major
  version that changed `upload_fileobj`'s error shape would show up as a failure in
  `test_both_write_paths_agree_about_a_missing_bucket` — which is the point.
* The per-run bucket is a **single** bucket: a test that left an object behind would be seen by the
  next test. The fixture empties it before each test, and the emptiness is asserted by the
  listing-based tests.
* The SeaweedFS volume exhaustion (§5) is a real hazard for anyone who extends the suite to make a
  bucket per test. The fixture's docstring records it.

**Rollback.** Delete `tests/storage/test_s3_live.py` and the S3 block in
`tests/storage/conftest.py`, and drop the two `pyproject.toml` lines. The S3 path goes back to being
tested only against the stub; nothing else changes, because nothing else depends on any of it.

**No hidden debt.** The stub stays — it is the right tool for the mechanism. The live suite is the
tool for the table. The two claims that neither tool can see (the dedup no-op and `stat`'s
provenance) are observed in the request, through a spy, and the spy is confined to the two tests that
need it.

## 15. Where I am least confident / what the reviewer should scrutinise

1. **The `S3UploadFailedError` unwrapping in the store.** The live suite shows the outcome is right
   on the path the store takes, and shows the outcome is *wrong* if the store ever takes the
   wrapping route. I did not touch it, because `src/paa/**` is not mine and because the unwrapping is
   still load-bearing for the connection-error chain. **A reviewer should decide whether the
   unwrapping machinery earns its keep** — if `upload_fileobj` is what the store uses and it does not
   wrap, the wrapper-specific half of `_driver_cause` may be dead code. It is *not* dead in the
   sense that matters: the MRO-name fallback and the errno fallback both need the chain.
2. **The `dev` extra's effect on the gate.** `paa[s3]` adds `boto3` to every developer's
   environment. The `api` extra set the precedent and the argument is the same, but the reviewer
   should note the download weight: `boto3` is ~15 MB, against `fastapi`+`uvicorn` at a similar
   order. It is the *right* trade — an untested path is worse — and the brief mandates it.
3. **The label convention.** It is an extension of the brief's four names, not a replacement. A
   reviewer who thinks the extension is unwarranted should say so; I have kept the brief's spelling
   working unchanged for a single server.
4. **The two "not caught" mutations** (§7.6, 3a/3b and 10). Both are explained and neither hides a
   defect, but they are the two places where a reader should check my reasoning rather than take it.
5. **The `stat` provenance assertion** is a *negative* assertion on the request log
   (`"get_object" not in spy.calls`). It is the right assertion and it is what the docstring claims,
   but it is coupled to the store's internal choice to use the head — a future change that made
   `stat` read the body would fail it. That is intended: the claim would no longer be true.
