## 3. Root cause

Three distinct defects, three distinct root causes.

**(a) The exception redacted one of its two secret-bearing fields.**
`StructuredOutputError.__init__` applied `redact()` to `message` and to
`raw_excerpt` but stored `schema_errors` verbatim (`base.py:108` pre-fix).
`schema_errors` is built by `validate_against_schema`, which quotes the
offending instance into its message
(`f"{path}: {instance!r} is not one of {allowed!r}"`, `base.py:358`), so it is
the model's *own output*. A provider that echoed a credential back put it
there. `PaaError` merges `details` into a ledger payload **verbatim**
(`core/errors.py:52-54`) and `PaaError.__str__` renders every detail
(`core/errors.py:46-50`), so the unscrubbed list was in the exception's text,
in its details, and therefore in anything that touched either.

*Why the same exception did both:* the excerpt and the errors are the same
kind of material — the model's output — and one was treated as sensitive and
the other as not. That was an oversight in the constructor, not a policy.

**(b) The escalation path copied a diagnosis without scrubbing it.** The
local-only path (`_local_only`) builds `underlying_*` details through
`_redact_detail`, which recurses into lists and dicts, precisely because a
detail is not always a string. The escalation path copied
`str(local_error)` into the payload — and `str()` of a `PaaError` renders the
message *and* every detail, including the ones `ModelUnavailableError`
carries verbatim (`**details` is not scrubbed by that exception either; only
the HTTP provider scrubs its own `body_excerpt` before constructing it).

*Why the two paths diverged:* the `_redact_detail` treatment was added to the
local-only path when the block-reasons diagnostics were built (ADR-0015's
rule 1 needs the details). The escalation path was never given it, and the
copy is a *different* code path, so "the local path scrubs" was never a
reason to think the escalation path did.

**(c) The escalation discriminator was per-process, not per-lineage.**
`self._escalation_seq` lived on the router instance. The idempotency key is
`SHA-256(correlation|event_type|attempt|discriminator)`
(`ledger/events.py:101`), so the discriminator is what makes two escalations in
one lineage distinct. A counter in memory is a counter in the *process*: a
restarted router began again at `escalation:1`, re-used the key its
predecessor had spent, and the ledger suppressed the write — in silence, from
the ledger's point of view, and with a `model.escalated` log line claiming an
escalation that the audit trail does not contain.

## 4. Approach chosen and why

### (a) Redact `schema_errors` at construction, in `base.py`

The alternative was to scrub at the *use* site — which is what the local-only
path does, and which is why the leak had two holes instead of one. Scrubbing
at the boundary means the exception is safe *by construction*: every consumer
(`str()`, `details`, `to_payload()`, a log line, a ledger payload) is safe
without knowing who consumes it. It also matches what the exception already
does to `raw_excerpt`, so the rule becomes "everything the model produced is
scrubbed" rather than "two of the three things the model produced are
scrubbed".

*Rejected:* scrubbing in `PaaError.__init__`. `core/errors.py` is read-only for
me, and — more to the point — it is the *wrong layer*. `PaaError` is the
runtime's generic error base; it has no idea what a credential is, and the
model layer already owns the secret-hygiene vocabulary
(`models/base.py::redact`). The brief says the same: *"the redaction belongs
at the model boundary, and the `_redact_detail` helper already exists there"*.

### (b) Scrub the escalation payload with the same treatment the local path has

`payload["local_error"] = redact(str(local_error))`.

*Rejected:* copying the structured details instead of the rendered string
(the local path's shape). It would widen the ledger payload's contract — a
new key per detail — for no gain: the rendered string already carries the
diagnosis, and `redact()` on a flat string covers nested structures too
(the details are rendered by `repr` into that string), which is why the
simpler call is sufficient where `_redact_detail` had to recurse.

*Rejected:* relying on the base.py fix alone. It would make this particular
leak disappear, but the router would still be copying an *arbitrary*
provider's diagnosis into a permanent record, and `ModelUnavailableError`'s
details are not scrubbed by the exception that carries them. The two fixes
are layers, and each has its own test (§7).

### (c) The discriminator becomes `escalation:<ordinal>:<nonce>`

* `ordinal` — the number of `MODEL_ESCALATED` events the **correlation**
  already holds, plus one — is **read from the ledger** at write time. It is
  a property of the lineage, so it survives a restart: the second router
  reads 1 and writes 2.
* `nonce` — the event's **own uuid4** — makes the write collision-free.

*Rejected:* a persisted counter (a new table, or a counter event in the
ledger). A counter is state the ledger would have to carry for a value the
ledger already carries: the lineage's own event count. And a counter event
would be a second kind of bookkeeping in the one store that is supposed to
have exactly one kind.

*Rejected:* deriving the discriminator from the ledger's `state_version`
alone (the brief's first suggestion, and the shape `ledger/recovery.py` uses
for `sweep-v{state_version}`). It is O(1) instead of O(lineage), and it is
the house shape — but it is **not collision-free**: two writers that read the
tip at the same moment take the same number, and the idempotency key
suppresses one of them. That is the same silent under-count, in a narrower
window. It would have made the restart case pass while leaving the
concurrency case broken, which is the shape of a fix that satisfies the test
rather than the property.

*Rejected:* a retry loop (append; if the store reports a duplicate, re-read
and append again). It has a real hole: with N concurrent escalations in one
lineage, the losers need up to N attempts, so any *bounded* loop eventually
gives up and loses an audit record — the one thing the module exists to
prevent. The nonce removes the need for a loop entirely: no collision is
possible, so there is nothing to retry.

*Cost, stated honestly:* one `read_correlation` per escalation (O(lineage))
against one append. Escalations are the rare path, and a lineage is a task's
history, not a table.

### (d) `healthcheck()` gained a permission-mode gate

`healthcheck(*, permission_mode: PermissionMode = PermissionMode.ASK)` probes
the frontier only when escalation is permitted in that mode. `MAX` is the
modality passed to `evaluate()`, so only rule 1 (the permission mode) can
block the probe — a healthcheck has no task, and the modality floor must not
decide it.

*Why I fixed it rather than only reporting it:* the brief said to fix it "if
the fix is small and obvious". It is five lines, it is the same rule the
module already applies to every other call, and the alternative is leaving a
documented way to make an authenticated HTTP request to a hosted endpoint
under a mode whose entire meaning is "no". The frontier's key is **absent**
from the report when it was not probed: absent means "not asked", which is not
`False` ("asked, and it cannot serve").

*Not done, and why:* the router does not know the deployment's permission
mode, so the default is `ASK` — the same default `complete()` uses. A
deployment in `LOCKDOWN` must pass its mode. `src/paa/runtime.py` (read-only
for me) has no call to `healthcheck()` today, so there is no call site to
update; the right long-term change is for the runtime to pass its live mode
when it grows one. That is recorded as a finding (§13).

**Contracts changed** (both deliberate, both stated in the code):

1. **The `MODEL_ESCALATED` event's `discriminator`.** Before:
   `escalation:<per-router-instance counter>` — `escalation:1`,
   `escalation:2`. After: `escalation:<per-correlation ordinal>:<the event's
   uuid4 hex>`. The *meaning* of the first field is unchanged (the Nth
   escalation of that lineage); it is now read from the ledger instead of from
   memory, and it is qualified by the event's own id so that two writers
   cannot collide. The ledger's stored `discriminator` column is TEXT and has
   no length constraint; nothing parses it (§6).
2. **`EscalatingModelRouter.healthcheck()`.** Before: `healthcheck()` — probed
   both tiers, unconditionally. After: `healthcheck(*, permission_mode=ASK)` —
   probes the frontier only when the mode permits escalation, and omits the
   frontier's key from the report when it did not probe it. The default keeps
   the old behaviour for a caller that passes nothing.

**Backward compatibility / migration.** None needed. No stored discriminator is
parsed; the pre-fix `escalation:N` rows remain valid rows; a replay does not
regenerate them. `AGENTS.md`'s "payload hashing uses `canonical_json`" is
untouched: the discriminator is not part of the digest
(`ledger/events.py::compute_event_digest` hashes `prev`, `correlation_id`,
`event_type`, `state_version`, `payload`, `recorded_at`), and the payload's
*shape* did not change — only the value of one field inside `local_error`.

### 7.3 Design notes on the two mechanical fakes

**The spy.** `EchoProvider` is the house spy — it records every request in
`calls` and counts them in `call_count`. Two subclasses were needed, both
documented in place:

* `_HealthcheckSpy` adds a `healthcheck_count`, because `EchoProvider`
  records *generations* and says nothing about healthcheck probes, and the
  frontier's healthcheck is the one call that can leave the machine without
  a completion being requested.
* `_InFlightEcho` adds the in-flight measurement, and a `fail` flag for the
  escalation path.

**The key.** The key-secrecy suite uses the *real* `complete_structured` and
the *real* `validate_against_schema` — a provider answers with the
credential and the schema rejects it — rather than a hand-written
`StructuredOutputError`. A hand-written exception would exercise the
constructor and not the path that fills it, and the path that fills it is
where the model's own output arrives.

### 7.4 Flakiness

`pytest tests/models` was run 5 consecutive times after the code commit:
154 passed every time (2.39–3.65 s). The concurrency tests are deterministic by
construction — the providers are *held* at a gate the test releases, and the
assertions are on a **peak** (`max_in_flight`), which can only be affected by
extra concurrency, never by less. The one scheduling-sensitive assertion is
`spy.in_flight_by_name.get("frontier-echo") == cap`: it is made immediately
after a `_wait_for` that returns on the same condition, with no `await`
between them, so the state cannot move in between.

### 7.5 `NOT-RUN` items

None. No test needs a network, a container, a port, or a database server: the
ledger is the embedded SQLite one (`tests/conftest.py::ledger`).

## 8. Long-run test

**Source.** The leak's source is a *model's own output* — the only way a
credential gets into `schema_errors` is for it to have been in the prompt or
the context. Both are covered: the test's model answers with the credential,
and `validate_against_schema` quotes it into the error.

**Load (100x, concurrency, partial failure).** The concurrency tests run 6
calls against a cap of 2 — a 3× oversubscription, the shape that finds a
semaphore that is not a semaphore. The escalation path is exercised under
concurrency in the two-tier test (6 escalations, 2 in flight). A **100×**
run was not performed: the property under test is a *bound*, and a bound is
proven by reaching it, not by repetition; the 6-call version already
saturates it. The partial-failure case is the *interesting* one and it is
covered directly: the local provider failing is what drives the escalation,
and the failing-local variants are the ones that catch mutation G.

**Hostile input.** The hostile input here is a *secret*, and the hostile
shape is a **list**: `schema_errors` is a list of strings, which is exactly
the shape a top-level-only scrub misses — the reason `_redact_detail`
recurses and the reason this fix redacts each element. The other hostile
shape is a **nested dict** in a provider's details
(`{"choices": [{"text": "…"}]}`), already covered by the existing
`test_underlying_nested_dict_details_are_redacted_before_attachment`; the
escalation path now scrubs the *rendered* string, which covers nesting for
free. Over-long inputs: `raw_excerpt` is still truncated at 400 characters
before scrubbing, and `schema_errors` is bounded by the number of schema
violations (a list the model cannot make arbitrarily long without making the
response arbitrarily long). NUL bytes and control characters in a detail:
`redact()` passes them through, as it always did — they are not credentials,
and the ledger's JSON encoder handles them.

**Operability (observe, roll back, migrate).** *Observe:* the scrubbed value
is `***REDACTED***`, so an operator sees that something was removed, not that
the field is empty — the diagnosis survives. The `model.escalation_unaudited`
error line says in words what happened to an audit record. *Roll back:* the
change is a pure function of the inputs; reverting the two source files
restores the old behaviour and the old (leaky) records stay in the ledger as
they are — a redacted record is not re-readable, which is the point.
*Migrate:* nothing to migrate; the ledger's rows are not rewritten.

**Reversal (which test fails if the fix is reverted?).** The full reversal is
§7.2: reverting `base.py` fails `test_the_schema_failure_carries_no_key`;
reverting the router's payload scrub fails
`test_the_escalation_payload_scrubs_the_provider_details`; reverting the
discriminator fails `test_the_escalation_ordinal_survives_a_router_restart`;
reverting the healthcheck gate fails `test_lockdown_does_not_probe_the_frontier`.

## 9. Edge cases and abuse scenarios

**Handled:**

* A key in the exception's message, in `raw_excerpt`, in `schema_errors`, in a
  provider's `details`, in the ledger payload, in the log line — each with
  its own test.
* A key in a **nested** structure in a provider's details (the rendered
  string covers it).
* The escalation payload with **no** local error (`force_escalate=True`):
  there is no `local_error` key, so there is nothing to scrub — and the test
  suite never asserts a key exists.
* An escalation with **no ledger**: the `model.escalation_unlogged` warning
  path is unchanged and still carries the (now scrubbed) payload.
* An **unattributed** escalation (no correlation id): unchanged, except that
  the ordinal is read from the fresh synthetic lineage, so it is 1.
* A **suppressed** audit write: now loud (`model.escalation_unaudited`), and
  the `model.escalated` line is *not* emitted, because the trail does not
  contain the record.

**Consciously not handled:**

* **A credential that does not match the generic patterns.** `redact()` is the
  project's existing secret-hygiene vocabulary and it catches `sk-…`,
  `Bearer …` and `api_key=…` shapes. A credential in a shape none of them
  recognises is not caught — but that is a property of `redact()`, which is
  shared with every other call site, and changing it is a change to the
  whole runtime's policy rather than to this path. The *provider* knows the
  literal key and passes it to `redact(text, *secrets)`; the router does not
  hold it.
* **Concurrency inside one router instance.** The nonce makes the write
  collision-free, so two concurrent escalations in one lineage are two
  records ✓. Their *ordinals* may be equal (both read the lineage at the
  same moment), so the ordinal is a label rather than a strict sequence
  under contention. The trade is stated in the code: a complete trail with a
  possibly-repeated label, or an incomplete one.
* **A credential in the *payload* the caller supplies** (`reason=`): the
  caller's own free text is copied verbatim. It is the caller's text, not
  the provider's diagnosis, and the local-only path treats the caller's
  `reason` the same way. Not changed.

**Unknown:** whether any deployment outside this repo relies on the exact
discriminator string. Within the repo, nothing parses it (§6).

## 10. Performance and security considerations

**Performance.** The only new cost on a hot path is *none*: `redact()` on the
schema errors is O(errors) per structured failure, and the payload scrub is
O(len(message)) per escalation. The new cost on the *rare* path is one
`read_correlation` per escalation — O(lineage) rows — against one append
(O(1) amortised, with a transaction and a per-lineage lock). For a task
lineage of tens to hundreds of events this is noise; for a pathological
lineage of tens of thousands it is a scan. I chose the readable ordinal over
the O(1) `state_version` for exactly this reason and would revisit it if a
deployment ever showed lineages that long.

**Security.** This is the security task. The changes *reduce* the attack
surface: a credential that was written into the ledger and the log
aggregator — twice, in two forms, from two paths — is now written nowhere.
The healthcheck gate removes a documented way to make an authenticated
request to a hosted endpoint under `LOCKDOWN`. The audit trail now records
every crossing, including across a restart, which is what makes the boundary
*auditable* rather than merely intended.

## 12. Deviations from the plan/brief; ownership issues; deferred dependencies

1. *The brief's §3 offered "derived from the ledger's own `state_version`" as

   from the ledger's **event count for that event type** instead, and added a
   nonce. Reason: a `state_version` discriminator is not collision-free under
   concurrency (§4c), and the brief's requirement is that the "exactly one
   per escalation" claim be *true*, not merely true in the tested case. The
   brief's acceptance criterion ("the escalation counter survives a router

2. *The brief said "the escalation path never was [given `_redact_detail`]"*,
   which points at the router's copy. I fixed **both** ends: the router's

   The brief's acceptance criterion explicitly lists the exception's `str()`
   and `details` as surfaces the key must be absent from, and `core/errors.py`

3. *The brief asked me to "cover [the healthcheck] too or say why not".* I
   covered it **and** fixed it (§4d), because a healthcheck that reaches the

4. *The brief listed `ModelProvider.__repr__`, `EchoProvider`'s determinism
   claim, and `token_usage()`/`reset_usage()` as untested.* `token_usage()`
   and `reset_usage()` are covered (in the concurrency file, where the

   covered: they are about `ModelProvider` and `EchoProvider`, whose test

## 13. Out-of-scope findings

1. **`EscalatingModelRouter.healthcheck()` has no caller in `src/`**, and
   the router does not know the deployment's permission mode — so the gate I
   added is only effective for a caller that passes its mode. The default is
   `ASK`, which probes the frontier. `src/paa/runtime.py` (not my write-set)
   is where a live mode would be threaded; it has no `healthcheck()` call
   today, so nothing is broken, but the door is open. *Suggested change:
   when the runtime grows a permission mode, call
   `router.healthcheck(permission_mode=mode)`.*
   ev: `src/paa/models/router.py:266`.
2. **`ModelProvider.__repr__` is untested.** It is a two-line method on the
   provider contract; the file that would host the test
   (`tests/models/test_backward_compat.py`) is not in my write-set.
   ev: `src/paa/models/base.py:697`.
3. **`EchoProvider`'s determinism claim is untested** — *"Nothing here reads
   a clock, generates a random number, or touches a socket"*
   (`echo_provider.py:11`). It is the property the ledger's replay guarantee
   leans on, and it is asserted nowhere. The natural home is a
   `tests/models/test_echo_provider.py`, which is not in my write-set.
   ev: `src/paa/models/echo_provider.py:9-12`.
4. **`ModelUnavailableError` does not scrub its `**details`**, only its
   message. The HTTP provider scrubs its own `body_excerpt` before
   constructing the error, so nothing leaks today — but the *contract* does
   not say so, and any other provider that forgets would leak. The router no
   longer depends on it (§4b), which is the mitigation; the durable fix
   belongs in `base.py` (my write-set) but I did not make it, because
   scrubbing arbitrary provider details at the exception boundary would
   change what a provider can put in an error, and the router-side scrub
   already covers the path that writes to the ledger.
   ev: `src/paa/models/base.py:81-83`.
5. **`_redact_detail` is now used by exactly one call site** (the local-only
   path) — the escalation path uses `redact` on the rendered string instead.
   The two are not equivalent in general: `_redact_detail` scrubs *values* at
   any depth and leaves keys alone, while `redact` on a rendered string also
   scrubs a key that happens to look like a credential. The rendered-string
   form is the one the escalation payload wants (it is a string), but the
   asymmetry is worth a comment in the module. Recorded, not changed.
   ev: `src/paa/models/router.py:125-150`.

## 14. Known limitations, risks, rollback notes

* **The discriminator's format changed.** Rows written before this commit
  carry `escalation:N`; rows written after carry `escalation:N:<hex>`. No
  reader parses it (§6), and the two forms coexist in the ledger without
  ambiguity. A deployment that greps the ledger for `escalation:` still
  matches both.
* **The ordinal is best-effort under concurrency** (§9): two writers that
  read the lineage at the same moment can take the same ordinal. The records
  are both written (the nonce makes them distinct); the *number* may repeat.
* **`healthcheck()`'s default is `ASK`**, so a caller that does not pass a
  mode still probes the frontier. That is the pre-existing behaviour and the
  same default `complete()` uses; the mode has to come from the caller.
* **The redaction is the generic policy, not a literal-secret scrub.** The
  router does not hold the API key and cannot scrub it literally; the
  provider does, and does (§13.4).
* **Rollback.** Revert `src/paa/models/base.py` and `src/paa/models/router.py`
  to `HEAD` and the behaviour returns to the pre-fix state, leak included.
  The new tests would fail (7 of them) — that is the point of the reversal
  measurement, and it is why the rollback is visible rather than silent.
  Nothing in the ledger is rewritten by either version.

## 15. Where I am least confident / what the reviewer should scrutinise

* **The discriminator design.** The nonce is the part I would most like a
  second opinion on. It is a change to a stored field's shape, made to
  close a concurrency hole that the brief did not name. The alternative I
  rejected — a bounded retry loop — has a *worse* failure mode (a lost audit
  record), and the alternative of leaving the ordinal alone leaves the
  concurrency hole open. But a reviewer may reasonably ask whether the
  nonce is worth the format change at all, given that the restart case
  alone is what the brief named. My answer is in §4c: the brief asked for
  the "exactly one per escalation" claim to be *true*, and only a
  collision-free key makes it true.
* **The ordinal's cost** (one lineage read per escalation). Measured, not
  guessed; the trade is in §10.
* **The concurrency tests' determinism** under a loaded host. The
  assertions are on a *peak*, so a slower host can only make the peak
  *lower* (and then the test fails loudly), never spuriously higher. The
  `_wait_for` drain is bounded, so a hang is a failure, not a stall.
* **The `healthcheck` gate's default.** A reviewer who believes the default
  should be the restrictive one (never probe) has a better argument than I
  do about API safety; I chose consistency with `complete()`'s default and
  with the router's "the caller states the mode" contract.
* **`test_the_frontier_is_probed_when_escalation_is_permitted` fails
  pre-fix for a *signature* reason** (the pre-fix `healthcheck()` takes no
  `permission_mode`), not a behavioural one. It is in the 7-failure list for
  that reason; the behavioural half of the gate is pinned by mutation F.
