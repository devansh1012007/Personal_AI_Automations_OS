### 2.2 The phase map was *not* the culprit — the plan's diagnosis was imprecise

`phase: TaskPhase.AWAITING_HUMAN`, four events, no `MUTATION_COMMITTED`.

## 3. Root cause

**Root cause.** `ChiefOrchestrator.run()` inspected the task's phase for a
park **once**, after `_check_policy`
(`[VERIFIED src/paa/agents/orchestrator.py:318]` pre-fix). A park raised by an
*earlier* stage — hydration, the first stage — was therefore never inspected,
and the next event the orchestrator wrote (`PLAN_COMPILED`) moved the
projection off `AWAITING_HUMAN` and on to `POLICY_REVIEW`. From there the
pipeline ran to `MUTATION_COMMITTED`.

The defect is a **missing check**, not a wrong mapping. The park machinery
(`AWAITING_HUMAN_ATTESTATION`, `clear_human_gate`, `TaskPhase.AWAITING_HUMAN`,
the phase map's entry for it) was all present and correct; the orchestrator
simply did not consult it at the point where the park was raised.

Two secondary root causes surfaced while fixing it, both of which would have
left the gate only half-closed:

* **The gate had no history.** The projection cannot express "a human has
  already ruled": `apply_event` clears `awaiting_reason` on
  `HUMAN_GATE_CLEARED` (`src/paa/ledger/replay.py:261`) and the phase is
  overwritten by whatever event comes next. So the orchestrator had no way to
  know whether a question was still open.
* **A second run could walk past the park.** Because the builder was
  re-consulted on every run, and the context builder's answer legitimately
  changes (the density is the filled ratio of the task's *declared* required
  slots, and the memory store changes underneath a task — the gatherer even
  has a `TRIGGER_BACKGROUND_HYDRATION` mode for exactly that), a re-run could
  get `PROCEED_TO_PLANNER`, emit a fresh `CONTEXT_HYDRATED`, leave
  `AWAITING_HUMAN`, and **commit without anyone having been asked**. I found
  this in my own first cut (commit `8527fe7`) and closed it in `487c6d5`; see
  §4.

## 4. Approach chosen and why

### The fix (three parts, 30 lines, one file)

1. **`run()` honours a park raised by any stage.** A phase check after
   `_hydrate`, mirroring the one that already sat after `_check_policy`.
2. **The release mechanism is the existing one.** `clear_human_gate` is
   untouched: it raises unless the phase is `AWAITING_HUMAN`, it emits
   `HUMAN_GATE_CLEARED` (or `HUMAN_GATE_REJECTED`), and nothing in the
   automated path calls it. The escalation therefore reuses the policy gate's
   machinery rather than inventing a second mechanism, exactly as D-4 says.
3. **The gate's *history* decides, not its present.** A new private helper
   reads the lineage's last gate event:

   ```python
   gate = await self._last_gate_event(ctx.correlation_id)
   if gate is EventType.HUMAN_GATE_CLEARED:      # the human answered → carry on
       return state
   if gate is EventType.AWAITING_HUMAN_ATTESTATION:  # still open → stay parked
       return state
   ```

   and `_hydrate` consults it *before* asking the context builder. The
   lineage is read rather than the projection because the projection cannot
   express "has someone ruled?" — `apply_event` clears `awaiting_reason` on
   the clear and the phase is overwritten by the next event. The ledger is the
   truth; a projection is one view of it, and this question is about the
   *past*.

   Plus one additive payload key, `"directive":
   "HARD_STOP_ESCALATE_TO_USER"`, so the ledger says *which* question was
   asked: the policy gate and the context escalation are the same event type
   and only the payload distinguishes them.

### Why the phase map was left alone (no `NEED`, no `DEFERRED-DEPENDENCY`)

`src/paa/ledger/replay.py` was **read-only** for me and **did not need to
change**. §2.2 is the evidence: the map already lands a parked lineage in
`AWAITING_HUMAN`. Changing it would have treated the symptom — it would have
made the projection report `AWAITING_HUMAN` for a lineage that had in fact
committed, which is a *less* honest projection, not a more honest one. The
projection agrees with the intent once the orchestrator stops writing events
after the escalation, and it then agrees with it exactly.

The one projection-level property that matters here is already in place and
is now exercised: `TaskPhase.AWAITING_HUMAN` is excluded from the resumable
phases (`src/paa/ledger/replay.py:64`), and `ledger/recovery.py:278` parks
such a lineage (`RecoveryOutcome.PARKED_HUMAN`). A crash is never read as
consent.

### Alternatives considered and rejected

* **Change `_PHASE_MAP` so the escalation "sticks".** Rejected: it would
  make the projection lie about lineages that committed (§2.2), it is
  read-only for me, and it treats the symptom. The map is *right*; the
  orchestrator was wrong.
* **A second, escalation-specific gate** (a new event type, a new
  `clear_escalation` method). Rejected: D-4 says reuse the existing
  machinery, and two gates would mean two places where "a human answered"
  has to be checked — with the same history problem in both.
* **Raise instead of park** (the context packet's own
  `raise_if_insufficient`). Rejected: the RFC's shape here is a *recorded,
  recoverable* outcome, and an exception would land the task in `FAILED`
  (terminal) instead of waiting for a human. A park is recoverable; a
  failure is not.
* **Have the orchestrator ask the builder again on resume** (the
  "re-hydrate and try harder" reading). Rejected — and this is the trap I
  fell into in the first cut: the builder's answer is not stable, so
  re-asking can *walk past* an unanswered gate. The escalation is a question
  and a human has to answer it.
* **Fix the policy gate's resume path too** (same `_last_gate_event`
  mechanism). **Deferred, deliberately** — D-4 is about the context
  escalation, the brief models the fix on the policy gate's *existing*
  behaviour, and changing a second live path in the same commit widens the
  blast radius of a behaviour change. Recorded as a FINDING (§13) and in
  ADR-0034's closing paragraph. The mechanism is one line away if the
  orchestrator wants it.

### The tests

Four kinds, each aimed at a specific clause:

* **Exact event lists** — list equality for happy / failure / block /
  anti-goal-block / gate, in the isolated orchestrator suite (so a failure
  points at the orchestrator, not a collaborator) *and* in the integration
  suite (so the real wiring is proved to add and remove nothing).
* **The mediated cycle** — three real agents, each delegating to the next
  through `ChiefOrchestrator.mediate_delegation`, at **MAX**, asserting the
  error's `cycle` field and that the refusal was *not* the depth guard.
  A companion test pins *why* STANDARD would be wrong (the depth ceiling
  fires first and the cycle is empty), so the reason lives in the suite and
  not only in a comment.
* **The 0.82 cosine path** — an injected embedder returning hand-built unit
  vectors whose dot product is **exact** in IEEE-754 (`[1,0]·[s,√(1−s²)]`
  is exactly `s`), so "exactly 0.82" is a boundary case and not a rounding
  accident. Every test passes an explicit `settings=`.
* **The critic's two halves** — a model may downgrade a deterministic PASS;
  an unparseable verdict is coerced to a failure; and the model *is*
  consulted after a deterministic PASS (the ordering constraint is a
  sequence, not a veto).

at `context/metrics.py:202` — so it never escalates. Only a task that
*declared* slots and could not fill 40 % of them is affected, and that is
exactly the set of tasks whose plan was previously being guessed at.

**Ledger invariants.** "Ledger event before side effect" holds: the
escalation event is written before the park is reported, and the
`CONTEXT_HYDRATION_REQUESTED` event is still written before the builder is
called. The new "the question is still open" branch emits **no** event —
correctly, because nothing happened: the builder was not called.

### 7.1 Which tests are regression locks rather than fix tests

The brief asked for the exact event list on four paths, and three of those
paths are **unchanged** by the fix. Those assertions are *characterisation
locks*: they pass before and after, and their value is that they fail on any
future drift of the sequence (an extra event, a missing event, an event in
the wrong place). The tests that genuinely fail without the fix are the
seven in `TestHardStopEscalation` plus the mediated-cycle, cosine and critic
tests. I have not dressed the characterisation locks up as fix tests.

### Edge/abuse cases covered

* the exact list for a **two**-site block (policy refusal vs. anti-goal
  security violation) — they are different event types on purpose;
* a **rejected** escalation (`approved=False`) → `HUMAN_GATE_REJECTED`,

* a parked task **re-run** without a human → still parked, no

* a **diamond** through the orchestrator → allowed, because the guard refuses

## 8. Long-run test

* **Source.** The ledger is the truth and every derived view is rebuilt from
  it. The fix adds one event payload key and no new state. The gate's history
  is read from the ledger, so a replay rebuilds it — a projection alone
  cannot, which is why the read is from the lineage.
* **Load.** One extra `read_correlation` per `run()` on the hydration path.
  The orchestrator already re-reads and replays the whole lineage about eight
  times per run (`project()` is called at every stage), so the marginal cost
  is a fraction of what is already being paid. A lineage with N events is
  read N+1 times per run instead of N — linear, unchanged in complexity. For
  a very long lineage the honest improvement would be a projection field for
  the gate state, which needs `ledger/replay.py` (read-only for me) and is
  not worth it.
* **Partial failure.** The park is written *before* the task is reported as
  parked, so a crash between the event and the return leaves the lineage
  parked — recoverable, and the recovery sweep agrees
  (`RecoveryOutcome.PARKED_HUMAN`). The reverse — a crash after the work and
  before the event — cannot happen, because the work (planning) is strictly
  after the park.
* **Hostile input.** The directive is compared to a literal; a packet with
  `routing_directive` set to anything else is not an escalation. The
  `vacant_slots` list is copied into the payload as-is (it is model-supplied
  and lands in the ledger — the same exposure every other model payload in
  this codebase has; it is JSON, and the ledger stores JSON).
* **Operability.** Observe: the parked lineage's last event says which
  directive parked it and why. Roll back: revert three edits in one file
  (ADR-0034 §"How to roll it back"). Migrate: nothing to migrate.
* **Reversal.** The test that fails if the fix is reverted:
  `TestHardStopEscalation::test_the_escalation_parks_the_task` — it asserts
  the phase is `AWAITING_HUMAN`, that the event list is exactly four events,
  and that neither `EXECUTION_STARTED` nor `MUTATION_COMMITTED` was emitted.
  Eleven more mutations are caught by the battery in §7.

## 9. Edge cases and abuse scenarios

**Handled:** the park itself; a re-run while parked; a re-run by a builder
whose answer changed; a human's approval; a human's rejection; a crash
between the park and the report; a task with no planner or no policy agent
(the escalation parks it, which is how §2.2's evidence was produced); the
exact trace of every path.

**Consciously not handled:**

* The **policy gate's** resume path (the FINDING in §13). It works today
  because the ledger suppresses the second `AWAITING_HUMAN_ATTESTATION`, but
  it depends on the policy agent being deterministic. Out of D-4's scope;
  one line of the same mechanism would close it.
* The **critic's verdict for a retry** is still not in the ledger (§13). The
  brief asks for the trap to be *asserted*, not removed, and removing it
  would change the failure-path event list this task is asked to pin.
* A **missing** model verdict from the critic is read as `PASS` (§13) — in
  `agents/reasoning.py`, which is read-only for me.

**Unknown:** whether a deployment's `.env` sets `PAA_CONTEXT__DENSITY_*` in a
way that escalates more often than the default. The behaviour is
configuration-driven and the defaults are what the ADR quotes.

## 10. Performance and security considerations

* Performance: one extra lineage read per run (§8). The recovery sweep and
  the projection are untouched.
* Security: the fix **strengthens** two properties and weakens none. A task
  escalated for a human can no longer be planned and committed without one —
  that is the entire point. The anti-goal gate's fail-closed path is now
  *tested* rather than merely written. The critic's coercion of an
  unparseable verdict is now pinned.
* The fix does not add a way to clear a gate: `clear_human_gate` still
  refuses a task that is not parked, and nothing in the automated path calls
  it. The new `_last_gate_event` helper only *reads*.

## 13. Out-of-scope findings

Four, all posted to `COMMS.md`:

1. **The policy gate's resume path depends on idempotency suppression.**
   After a human clears a *policy* gate, `run()` re-consults the policy
   agent; the second `AWAITING_HUMAN_ATTESTATION` is suppressed by the
   ledger's key, so the release works only because the policy agent is
   deterministic. A non-deterministic verdict (say, `STATUS_BLOCKED` the
   second time) would block a task a human had approved. The same
   `_last_gate_event` mechanism I added would close it.
   `src/paa/agents/orchestrator.py:561` is the emit site.
2. **`RecursionGuardError` normalises its attribute but not its payload.**
   `self.cycle = cycle or []` while `to_payload()["cycle"]` keeps the raw
   `None`, so a depth refusal carries `cycle=None` in the payload and `[]` on
   the exception. `src/paa/core/errors.py` is not my write-set; my test
   asserts `not error.get("cycle")`, which is true either way.
3. **The critic's verdict for a retry is not in the ledger.** `_critique`
   emits `CRITIQUE_CONCLUDED` without an `attempt`, so the store's key
   suppresses every retry's critique: the trace says the step failed, but
   not what the critic said about attempts 2 and 3. `VALIDATION_FAILED`
   *does* carry the attempt, so the retry itself is visible. Pinned as a
   test; fixing it would change the failure-path event list this task was
   asked to pin, so it is its own change with its own justification.
4. **`CriticReviewer` reads a *missing* model verdict as `PASS`.**
   `str(review.get("verdict", "PASS"))` — an unparseable verdict is coerced
   to `FAIL_REJECT_RETRY` (correct, and now tested), but an *absent* one is
   a pass. A fail-open on a malformed model response, in a file that is
   read-only for me. I assert the unparseable case only, deliberately: I do
   not want to enshrine the absent case as intended behaviour.

## 14. Known limitations, risks, rollback notes

* **A behaviour change on a live path.** A task whose context is too thin
  now waits for a human instead of committing. The blast radius is bounded
  and quantified in §6 (tasks that *declared* required slots and could not
  fill 40 % of them). The release paths (API, TUI, CLI) already exist.
* **The resumed task plans with an empty context packet.** There is no API
  for supplying the missing context, so "proceed" means "proceed without
  it". Recorded in ADR-0034 §3.
* **The gate's history costs a lineage read per run.** Acceptable at the
  current read volume (§8); a projection field would be the fix if the
  lineage ever gets long, and that needs `ledger/replay.py`.
* **The exact event lists are pins.** Any future change to the orchestrator's
  event sequence — a new event, a reordered stage — will fail these tests.
  That is the intent, but a maintainer adding a legitimate event must
  update the lists, and the lists are in the test file's docstrings so the
  reason travels with them.
* **Rollback.** Revert three edits in `src/paa/agents/orchestrator.py` (the
  phase check after `_hydrate`, the two gate-history branches, and the
  `_last_gate_event` helper with its `_GATE_EVENTS` set). The `directive`
  payload key is additive and can stay. Nothing stored depends on the change.
* **No hidden debt:** the ADR index row for 0034 is missing and belongs to
  the records task (§12).

## 15. Where I am least confident / what the reviewer should scrutinise

1. **The empty-context resume.** After a human clears the escalation, the
   task plans from `{}`. I chose that because there is no API for supplying
   the context and "proceed" is not "here is what you were missing". A
   reviewer may reasonably want the task to *fail* rather than plan blind.
   The alternative is one line in `_hydrate` and a different ADR sentence.
2. **`_last_gate_event` reads the whole lineage.** Correct, but O(N) per
   run on a long lineage. I argue the marginal cost is small (§8); a
   reviewer may want it in the projection instead — which needs
   `ledger/replay.py` and therefore an owner.
3. **The "still open" branch is a behaviour I invented.** It is not in D-4's
   letter. It closes a real hole (M12), but it also means a task whose
   context *would* now be sufficient still waits for a human. I think that is
   right — the human was asked a question and has not answered it — but it
   is a judgement, and it is the part of the diff most worth a second pair
   of eyes.
4. **The `_GATE_EVENTS` set treats `HUMAN_GATE_REJECTED` as a no-op branch.**
   It is unreachable in `_hydrate` (a rejected gate is `BLOCKED`, which is
   terminal, so `run()` returns before `_hydrate`). I documented that in the
   docstring rather than adding a dead branch.
5. **The exact event lists are pinned against the *current* implementation.**
   If the RFC's §7 order turns out to differ from the implementation's, the
   lists will enshrine the implementation. I did not find a document that
   contradicts the observed order.
