## 3. Root cause

Three distinct causes, three distinct fixes.

**(a) The crash — a keyword's value was used without being checked.**
`validate_instance` read keyword values with `schema.get("minLength")` and then
*used* them: `len(payload) < limit`. A value of the wrong type made the
comparison itself raise, and the comparison is the only thing the keyword does.
The module had no notion of a keyword's *value shape* at all: `SUPPORTED_KEYWORDS`
listed which keywords are understood, and nothing said what their values must
look like. A crash was therefore not an error path — it was the only path.

**(b) The silence — a malformed keyword was not distinguished from an absent
one.** `schema.get("minLength")` returns `None` both when the keyword is absent
and when its value is `None`; there was no third state. So the design could
not express "this keyword is present and unusable" — and a keyword that is
present and unusable is exactly what a model produces when it writes
`"minLength": "abc"`.

**(c) The missing tests.** The three headline claims had no tests, so the
defects in (a) and (b) had no way to surface: a security layer whose only
evidence is its own docstrings.

## 4. Approach chosen and why

### The policy (decided, written down, and applied to every keyword)

> **A keyword whose value has the wrong shape is a schema error: reported in
> the same shape as any other invalid schema, and never raised. The malformed
> keyword is reported *and not applied*. The rule does not depend on
> `strict_keywords`.**

Three decisions inside that, each with its reason:

1. **A malformed *value* is a value problem, not a supported-keyword problem.**
   `strict_keywords` answers "does this implementation *understand* this
   keyword?" — a coverage question, and the lenient default exists so a schema
   carrying documentation-only extensions still works. A keyword that *is*
   understood and given a nonsense value is a different failure: the author
   believes a constraint is in force and it cannot be. Leaving that to the
   lenient mode would mean the default silently ignores a broken constraint,
   which is the failure the module exists to prevent elsewhere (the same
   argument the module makes for `$ref`). **So the rule holds in both modes**
   (`test_malformed_keyword_value_is_rejected_in_both_keyword_modes`).

2. **The shape includes the range JSON Schema itself imposes.** `minLength`
   is a *non-negative integer* and `multipleOf` is a *number greater than
   zero*; `minLength: -1` and `multipleOf: 0` are values the keyword cannot
   use, exactly as `minLength: "abc"` is. This is the "same rule for every
   keyword" the brief asks for: the rule is *the keyword's own JSON Schema
   type*, applied uniformly. It changed one pre-existing assertion
   (`multipleOf: 0` used to be a silent no-op) — see §5 and §12.

3. **An unknown *type name* keeps the existing "do not guess" behaviour.**
   `{"type": "strng"}` is a value of the right *shape* (a string) with a name
   the implementation does not know; `_matches_type` already documents that it
   returns `True` for an unknown type on purpose. Changing that is a separate
   decision about the *vocabulary*, not about the *shape*, and it belongs to
   the module's owner. The shape check only requires the value to be a string
   or a list of strings.

### The mechanism

One table of keyword shapes (`_KEYWORD_SPECS`), and **one function**
(`_value_defects`) that decides whether a value has the shape its keyword
requires. The *report* and the *decision to apply* both come from that one
function, so they cannot drift apart — which is what "the same rule for every
keyword" has to mean if it is to be true rather than aspirational.

* `_value_defects(spec, value) -> list[(suffix, message)]` — empty means usable.
* `_schema_shape_errors(schema, path)` — walks the schema tree and reports
  every defect, **including in branches the payload never reaches**: a schema
  is a contract in its own right, and the author needs to hear about a broken
  constraint before the payload that touches it arrives (one LLM round trip
  earlier).
* `_keyword_value(schema, keyword)` — the read side. A keyword whose value is
  malformed reads as `None`, which is the code's existing "this keyword is not
  here" state, so every call site needed one word changed and no call site
  needed a new branch.

**Rejected alternatives:**

* *Guard each use site with an `isinstance` check.* This is what
  `src/paa/skills/contracts.py:224` already does — and it is why there are
  *two* schema validators in this repo with two different policies. A guard at
  each of thirteen sites is thirteen chances to forget one, and "the same rule
  for every keyword" would be a convention rather than a property. Rejected.
* *Report the malformed keyword and return early (skip the instance
  validation).* Simpler, but it hides the instance errors behind the schema
  error, and the module's own philosophy is to collect all failures rather
  than force a fix-one-rerun loop where each round trip costs an LLM call.
  Rejected in favour of "report the shape error *and* validate the instance,
  skipping only the malformed keyword".
* *Make the malformed value an exception.* A crash is neither a pass nor a
  fail — it is the gate absent. Rejected by the brief and by the module's
  purpose.
* *Only fix `minLength` (the reported case).* Explicitly forbidden by the
  brief, and it would have left twelve more crashes in place. Rejected.

### The shape of a keyword's value — the table

| kind | keywords | required value |
|---|---|---|
| `type` | `type` | a type name, or a list of type names |
| `number` | `minimum`, `maximum`, `exclusiveMinimum`, `exclusiveMaximum` | a number (not a boolean) |
| `positive_number` | `multipleOf` | a number greater than zero |
| `non_negative_int` | `minLength`, `maxLength`, `minItems`, `maxItems`, `minProperties`, `maxProperties` | a non-negative integer |
| `boolean` | `uniqueItems`, `nullable` | a boolean |
| `string` | — | — |
| `regex` | `pattern` | a string that compiles |
| `array` | `enum` | a list |
| `string_array` | `required` | a list of strings |
| `schema` | `additionalProperties`, `items`, `not` | a schema (a mapping or a boolean) |
| `schema_array` | `prefixItems`, `anyOf`, `oneOf`, `allOf` | a list of schemas |
| `schema_map` | `properties`, `definitions`, `$defs` | a mapping of names to schemas |
| *annotation* | `const`, `default`, `title`, `description`, `examples`, `$schema`, `$id`, `$comment` | anything |

The union of the constrained set and the annotation set is asserted to be
exactly `SUPPORTED_KEYWORDS`, **read from the module's source** — so a keyword
added to the supported set without a shape is a loud failure rather than a
keyword whose value is never checked.

### The tests

Same principle: derive the inventories from the source, not from a copy.

* the **rule inventory** is an AST sweep of `ast_scanner.py` for the two call
  shapes the module uses to emit a rule (`Finding(rule=…)` and
  `self._add(node, "rule", …)`), asserted equal to the hand-written list of 19;
* the **keyword inventory** is an AST sweep of `schema_validator.py` for
  `SUPPORTED_KEYWORDS`, `_KEYWORD_SPECS` and `_ANNOTATION_KEYWORDS`;
* the **deny lists** are read from the policy's own data
  (`policy.denied_modules` etc.) — the single source of truth — and each entry
  is exercised.

The scanner sweep's limitation is stated honestly in the test's docstring: a
rule emitted through a *third* call shape would escape the sweep. Every rule in
the module today is emitted through one of the two.

  keyword value either has the shape the keyword requires or is reported.
* **Load (100×, concurrency, partial failure).** The validator is called once
  per skill output; the shape walk is a second traversal of a small schema
  tree, so the cost is O(schema size) per call and constant in the payload.
  The engine is stateless per call (`AstSecurityScanner` builds a fresh
  visitor per scan — pinned by `test_the_scanner_is_stateless_across_calls`).
  Partial failure is the patch layer's case: the mid-patch unwind is asserted.
* **Hostile input.** The scanner's hostile corpus (13 cases) and the
  never-raises property; the schema validator's 37 malformed cases; the
  patch layer's 23 escape forms; the workspace's symlink and unreadable-file
  cases.
* **Operability.** The report names the keyword and the schema path, so an
  operator can find the broken contract without a stack trace; the engine's
  report names the check and the short-circuit point; the test runner's
  payload names the reason a suite did not pass.
* **Reversal.** 81 tests fail without the fix (§7). The three `xfail`s name
  the exact change required for each read-only defect.

## 9. Edge cases and abuse scenarios

Handled: every keyword's wrong-typed value (§4's table); a non-string schema
key; a pattern that is not a regex, and one that raises `OverflowError`
(`a{99999999999}`) or `RecursionError` (1000 nested groups) from `re.compile`
— all three are caught and reported, not raised; a malformed keyword in a
branch the payload never reaches; a malformed keyword *and* an instance error
in the same validation (both are reported); the four patch escape classes; a
symlink that points outside the workspace; an unreadable file in a manifest; a
symlinked directory in a manifest.

Consciously **not** handled, and why:

* *An unknown type name* (`{"type": "strng"}`) — the module documents that it
  does not guess at unknown types, and changing the vocabulary is not a
  shape question. Reported in §13 as an observation.
* *`enum: []`* — an empty list is a list; the instance validation then rejects
  every payload, which is the author's evident intent and is not a hole.
* *A pattern that is a valid regex but a catastrophic one (ReDoS)* — the
  pattern is applied to a payload the caller controls; the timeout is the
  engine's problem, not the validator's. Noted in §13.
* *`{"x-anything": ...}`* — extension keywords are ignored by design (they
  are excluded from `unsupported_keywords` too).

Unknown: whether any skill contract in the wild carries a keyword shape this
table would now reject. The in-tree contracts do not (§6).

## 10. Performance and security considerations

* **Performance.** The shape walk is one extra traversal of the schema per
  validation, over a schema that is a handful of nodes. The engine calls
  `check()` once per skill invocation. `_value_defects` is called twice per
  keyword read (once to report, once to decide) — the second call is on the
  same value and is O(1) for every kind except the container kinds, which
  re-check their elements; the cost is negligible at these sizes, and the
  alternative (two tables) would let the report and the behaviour drift.
* **Security.** The change *narrows* what the gate accepts: seven keywords
  that silently accepted malformed values now fail the gate, and one that
  produced a false rejection now fails it for the right reason. The one
  behaviour that got *more* permissive is none: a malformed keyword is
  reported, and the payload is still validated against the rest of the schema.
* **No new dependencies, no new I/O, no network, no ports, no containers.**
  The fix touches one module and adds no import that is not already there.

## 14. Known limitations, risks, rollback notes

* **The shape table is a second list of keywords.** It is asserted to be
  exactly `SUPPORTED_KEYWORDS` (from the source), so it cannot silently drift,
  but a keyword added to `SUPPORTED_KEYWORDS` *and* forgotten in both tables
  would be unchecked. The lock catches the case where only one of the two is
  updated — which is the realistic case.
* **The schema-error path and the instance-error path use different path
  vocabularies** (`$.properties.a.minLength` vs `$.a`). The error carries
  `schema_error=True` and `keyword=<name>`, and the test module documents the
  distinction, but a consumer that only reads `path` could confuse them.
* **The policy's "value domain" reading is a judgement call** (`multipleOf: 0`
  and `minLength: -1` are schema errors). If the reviewer prefers the
  type-only reading, the change is one row of `_KEYWORD_SPECS` plus the
  corresponding test — and the pre-existing `multipleOf: 0` assertion would go
  back to `== []`.
* **Rollback:** the fix is one file. Reverting
  `src/paa/validation/schema_validator.py` restores the old behaviour and
  makes 81 of the new tests fail — the tests are the rollback's alarm. The
  test files are additive and can be removed without touching anything else.
* **The three `xfail`s are strict**: if someone fixes F-1, F-2 or F-3 without
  updating the test, the suite goes red (XPASS(strict)). That is intended —
  it is the orchestrator's signal that a finding was closed.
