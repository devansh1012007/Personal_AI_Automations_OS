### 1.1 The BLOCKER, in detail — what was wrong and what it is now

The finding was right, and the disagreement was three-way: ADR-0032 §5 said a missing bucket
raises `NotFound` "from every method", the `BlobStore` protocol repeated it, the implementer's
report recorded it as a behaviour change — and the code could not do it.

**Why it could not.** A HEAD response has no body. The driver therefore has no code to report
and reports the *status* as the code — the code's own comment says so
(`minio_backend.py`, "a HEAD on a missing key answers 404 with an empty body, and botocore
then reports the status as the code"). So a HEAD on a missing **key** and a HEAD on a missing
**bucket** arrive as the same `"404"`, and `_S3_BUCKET_MISSING_CODES` — whose only member is
`NoSuchBucket`, a code that lives in an error *body* — could never be observed on the path
`_head` uses. One condition, one store, four answers (`exists`→`False`, `stat`→`None`,
`delete`→`False`, `get`→`NotFound("blob not found")`), and the two write paths answered
`NotFound("bucket not found")` because a PUT's response *does* carry a body.

**What I did — the discrimination is earned.** The store asks the server about the bucket
(`head_bucket`) before it tells a caller that something is missing:

* the bucket is there → the blob is not there → `NotFound("blob not found")`, and
  `exists`/`stat`/`delete` answer `False`/`None`/`False` exactly as they always did;
* the bucket is not there → `NotFound("bucket not found")` with `namespace="bucket"`, from
  **every** method.

Measured with a client that answers the way botocore answers a HEAD 404 (`code="404"`, status
404, no body) — the shape the review said the unit suite could not express:

```
bucket missing:  exists/stat/delete/get/get_stream/put/put_stream
                 → NotFound("bucket not found"), namespace='bucket'   (all seven)
bucket present, object missing:
                 exists→False  stat→None  delete→False
                 get/get_stream→NotFound("blob not found")
                 put/put_stream→NotFound("blob not found", s3_code="NoSuchKey")
```

**The alternative I rejected, and why.** The review offered two shapes: *earn* the
discrimination, or *state the truth* (a HEAD 404 is ambiguous; say so in the ADR and the
protocol and drop the claim). I rejected the second as the resolution because it leaves the
store lying in the case that matters: with a truth-telling ADR but an unchanged store,
`exists()` on a deleted bucket still answers `False` and `get()` still says "blob not found"
while the store is gone — the exact lie ADR-0032 §5 was written to remove, now with a
documented blessing. I took the review's *first* shape, with three constraints:

* **The write path does not probe.** A write's own response carries a body, and the body says
  which of the two is missing (`NoSuchBucket` against `NoSuchKey`) — so the write path already
  knew, and asking again would have cost a request on every first write of every blob, the hot
  path. The probe is paid only where the answer is load-bearing: on the path that has already
  decided that something is missing. (The write path *does* resolve an **ambiguous** 404 — a
  bodyless one — through the same probe, on the failure path only.)
* **The answer is not cached.** A cached "the bucket was there" is exactly the answer that is
  wrong when the bucket is deleted under a running daemon, which is the case this exists to
  catch; a cached "the bucket was not there" would be wrong the moment somebody creates it.
* **A refusal is read as "the bucket is there".** `head_bucket` wants `s3:ListBucket`; a
  deployment that grants only object-level permissions gets a 403, and the store then reports
  an object-level absence — the behaviour before this change. S3 answers 404 (not 403) for a
  bucket that does not exist, so a refusal is evidence the bucket is there. The condition is
  not lost: the next write reports the missing bucket in as many words. This is recorded in
  ADR-0032's Amendment and in the code's own comment.

**What it costs.** One extra request on the *miss* path of the read and metadata methods.
`exists`/`stat`/`delete` have no production caller in `src/paa` (verified by grep), a read of
a blob that is not there is an error case, a hit costs nothing, and the write path is
unchanged. Measured: the probe is called 0 times on a hit and 1 time per absent-object query
(`test_the_bucket_is_only_asked_about_when_something_is_missing`).

**What the ADR and the protocol now say.** ADR-0032 §1's false claim ("the details
(`sha256=` against `bucket=`) say which") is replaced by the `namespace="bucket"` rule; §5
keeps its decision and gains a pointer to the Amendment, which explains the mechanism, the
cost, the refusal case, and the four corrections below. The protocol's module docstring says
that the namespace clause is the S3 substrate's and that it is *earned*; `exists`'s docstring
says the same; `stat`'s docstring now says what it raises honestly (it may raise `Corrupt`
when the substrate has to read the bytes to answer — see §6).

## 4. Optimizations applied, and ones declined with a reason

**Applied**

* **One translation at the lookup instead of five** (R-W1-002): the CAS's five leaking
  methods are closed by one guarded call, not five. The alternative — a `try` in each method —
  is the shape the finding explicitly rejects.
* **One raise helper instead of nineteen `raise … from exc` sites** (R-W1-009): the cause
  rule now lives in one place and cannot drift.
* **The probe is not on the write path**: a write's response already carries the answer, so
  the hot path pays nothing. This is the difference between "earn the discrimination" and
  "earn it on every request", and it is the reason the fix is affordable.
* **The tables are pinned by literals** rather than by a parametrisation derived from the
  tables themselves: a parametrisation generated from the table takes its own case with it
  when a member is deleted, which is the M2/M3/M4 mutation that survived with zero failures.

**Declined, with a reason**

* **A cached namespace probe** (the review's "a `head_bucket`, cached per store"): a cached
  positive is the answer that is wrong when the bucket is deleted under a running daemon — the
  case the whole clause exists to catch — and a cached negative is wrong the moment the
  bucket is created. The code says so where the decision is made.
* **A `head_bucket` probe on every HEAD** (i.e. inside `_head`, so the write path pays it
  too): two extra requests on the first write of every blob, to learn what the write was
  about to say.
* **GET-first on the read path** (drop the HEAD pre-check and let the GET's body answer): it
  would save a request on a miss and make the read path self-sufficient, but it restructures
  the read path for a case that is already correct. Declined as out of proportion.
* **A machine-checkable error clause** (the review's optimisation 5 — a
  `(method, condition, class)` table): the right long-term shape, and a bigger change than
  this wave. What this change does is make the *namespace* rule machine-checkable with one
  detail, and the contract test pins it on both substrates.
* **`NotFound` split into `NotFound` + `NamespaceMissing`** (the review's optimisation 6):
  agreed with the review's verdict — the missing-bucket problem was a *detection* problem,
  not a naming problem, and it is now a detection problem that is solved.

**Out-of-scope findings (COMMS)**

* `NEED` — `docs/plans/w6-w7-w9.md` §0/§3.2 carry R-W1-008's wrong measurement ("48
  `TYPE_CHECKING` blocks", "nine are load-bearing"); the correct figures are 41 at the
  baseline, 34 after T-004, and **one** load-bearing block (`storage/coldlake/cas.py`, because
  `base.py` imports `cas` for `BlobRef`). `docs/plans/**` is forbidden to me.
* `NEED` — `briefs/W1-REVIEW-CONTEXT.md:55` still says "28 of the new tests fail against the
  pre-change sources"; the count is 26 and the method is now in the implementer's report.
* `NEED` — `tests/conventions/test_import_conventions.py`'s aggregate import probe passes
  `timeout=300` but does not catch `TimeoutExpired`, so a timeout surfaces as an ERROR rather
  than a verdict (R-W1-216's second half). That file is `W1-IMPR-03`'s.
* `FINDING` — the S3 store's `stat()` answers from the size recorded at upload time and does
  not read the blob, so it cannot see a damaged object; the filesystem store's `stat()` reads
  the frame and does. The asymmetry is pre-existing, is now *documented* in the protocol
  rather than hidden, and fixing it would mean re-reading every blob on every `stat` (O(size)
  — the review's own optimisation 4, marked DO-LATER).

## 6. Residual risks and anything the delta reviewer should check

1. **The probe's cost is on the miss path only, but it is a new request the ADR did not
   have.** If wave 2's live suite finds that a deployment's credentials cannot answer
   `HeadBucket` at all (a 403 on *every* call), the store falls back to the object-level
   absence — the behaviour before this change — and the missing bucket is then reported by
   the next write. That is documented, not tested against a live server.
2. **botocore's real code for a HEAD 404 was not executed** (boto3 is not installed here). I
   assert the *shape* the code's own comment and the review's stub both describe: a bodyless
   404 reported as the status string. If botocore actually reports something else for a
   bodyless 404, the dialect's `_S3_STATUS_AS_CODE` would have to change — but the *design*
   (ask the server about the bucket when the answer is ambiguous) does not depend on it, and
   the store's behaviour is driven by the *absence* of a body-carrying code, not by the
   string. This is the one premise I could not execute, and it is stated as such.
3. **A `403` from `HeadBucket` is read as "the bucket is there"**, on the strength of S3's
   rule that a nonexistent bucket answers 404. A server that answers 403 for a nonexistent
   bucket (to avoid leaking existence) would put the store back to the old behaviour — no
   crash, no wrong class, just the old answer.
4. **The `namespace="bucket"` detail is a new key in the ledger payload.** It is additive, and
   it is only present on a bucket-level absence, but a dashboard that groups on error details
   will see a new key. The rule is stated in the ADR, the protocol and `errors.py`.
5. **The S3 `stat()` asymmetry** (§4) is documented, not fixed. A reviewer should confirm
   that documenting it is the right call for this wave rather than a deferral that should
   have been a change.
6. **`_require_namespace` costs one request per absent-object query, and `exists`/`stat`/
   `delete` have no production caller in `src/paa`** — but an *external* consumer of the
   `BlobStore` protocol could call `exists()` in a loop, and would pay a request per call it
   does not get an answer for. This is a real (small) cost of the fix, and it is the price of
   not lying.
7. **The `TYPE_CHECKING` cycle is intact**, but I touched `cas.py`: the new import is
   `paa.storage.coldlake.errors`, and `errors.py` imports nothing from `coldlake`, so the
   `base → cas → base` cycle is not closed. The conventions lock passes (13 tests).
8. **What I did NOT verify:** the full suite (out of scope by the standing orders), a real S3
   server (no container, no server), and Windows behaviour (the review ran on Linux too; the
   errno classification is portable, but the `Path.exists()` errno set is POSIX-flavoured in
   its trigger).

## 7. The long-run test

* **Source.** The source of truth is unchanged and still the bytes: content addressing, the
  raw-bytes digest, verify-on-read, the fan-out, the dedup and the staging-then-rename are
  untouched. What changed is the *reporting* of a failure — and the reporting is now
  **true**: the store says which of the two absences it is, the details carry identifiers
  and one machine-readable marker, and the driver's wording stays in the traceback rather
  than in the ledger.
* **Load.** The translation is a handful of set lookups on the failure path. The one new
  cost is the namespace probe: **one request, on the miss path only**, never on a hit, never
  on the write path. 100× concurrency changes nothing (the store holds no new state, and the
  probe is not cached — deliberately, see §4). Partial failure: a failed CAS write leaves a
  staging file (recoverable, swept by `clear_staging`) and the cleanup no longer replaces
  the original failure; a failed S3 upload leaves no object.
* **Hostile input.** A hostile digest is refused at the door on both substrates and the
  echoed value is bounded to 128. A hostile *server* cannot choose the local exception type
  (every code maps to a fixed class, an unnamed code becomes `BlobFailure`) and cannot put a
  credential into the ledger (the driver's text is the `__cause__`). The new capability is
  the *opposite* of the old gap: a server that has deleted the bucket can no longer make
  the store answer `False` for a blob it cannot see — it has to answer 404 to a
  `HeadBucket`, and then the store says so. A server that answers a bodyless 404 to
  *everything* is still believed, which is the honest limit of the protocol.
* **Operability.** *Observe:* the ledger gets the concept, the identifiers and the
  `namespace` marker. *Roll back:* revert the commit — the vocabulary is additive, the probe
  is additive, and the only behaviour change (a missing bucket raises) is the one the
  contract always promised. *Migrate:* nothing to migrate (no data, no schema, no flag).
* **Reversal.** Which test fails if the fix is reverted?
  * the bucket clause: `test_a_missing_bucket_raises_from_every_method` (all seven methods)
    and `test_a_missing_namespace_raises_where_there_is_one` (the contract's three);
  * the CAS leaks: `test_an_unreadable_archive_is_a_refusal` (five methods) and
    `test_a_substrate_that_refuses_is_access_denied_on_both`;
  * the codec leak: `test_a_corrupt_frame_is_corrupt_in_the_metadata_path`;
  * the unpinned transport paths: `test_every_transport_path_reports_the_vocabulary` and
    `test_the_upload_wrapper_is_unwrapped` (which asserts `upload_calls == 1`);
  * the unpinned tables: `test_the_tables_hold_exactly_what_is_pinned`;
  * the `__cause__`: `test_the_drivers_error_is_kept_as_the_cause` and the idempotence cases.
