## 2. Code changes

### 2.1 `src/paa/storage/relational/__init__.py` — R-W1-110

Four changes, and the reasoning is in the file because the file's own
docstring was where the false reason lived.

**The imports.** `Settings` joins `StorageSettings` at module scope
(`paa.config` was *already* imported at runtime, so it costs nothing) and
`PostgresDatabase` is imported at module scope from
`paa.storage.relational.postgres`. The `if TYPE_CHECKING:` block and the
`typing.TYPE_CHECKING` import are gone.

**Why module scope is safe.** `postgres.py`'s module-scope imports are
`paa.core.errors` and the package's own submodules (`connection`,
`database`, `dialect`, `errors`, `migrations`) — none of which imports the
package `__init__`'s *attributes*, so no cycle is created. Verified two ways:
the import succeeds (§5, reversal 1 inverts it), and the fresh-interpreter
sweep over all 136 modules is green.

**One spelling, not two.** The factory's body used to do a *local*
`from paa.storage.relational.postgres import PostgresDatabase` inside the
postgres branch. That import is removed and the module-scope name is used.
Keeping both would have left the file expressing the same dependency two ways
— the exact defect class T-004 removed from seven modules, re-introduced in
the package that owns the contract.

**`__all__` gains `PostgresDatabase`.** The name is now part of the package's
namespace and of the package's stated public surface; leaving it out would
make `__all__` a list of names the module no longer has. No star-import of
the package exists in the tree (`[RAN] grep -rn "from paa.storage.relational import \*" src
tests` → nothing), so the change is additive.

**The docstring.** The false paragraph is replaced with three true ones:
(i) the names are bound at module scope *because the annotation names them*,
and under `from __future__ import annotations` a name bound only for the type
checker is absent from the module — so `get_type_hints`, FastAPI's dependency
resolution and a pydantic model all fail on it; (ii) the `postgres` extra was
**never** the constraint, and the docstring now says that the earlier wording
was wrong and why; (iii) what *is* lazy is the **client** — the factory builds
a `PostgresDatabase` only when `backend_relational` asks for one.

The factory's own comment was corrected the same way: the old one said the
local import "documents that the psycopg dependency is only reached on the
server topology", which is true of *psycopg* but was attached to the wrong
thing — psycopg is reached inside `postgres.py`, not by the import site.

### 3.2 The two new mechanisms, and why they are the right shape

**The blocked probe (`_probe_without`).** The tolerance list's entries are
checked by *blocking the packages* with a `meta_path` finder in a fresh
interpreter, and asking the module to import. The block is total — no
`sys.path` trick, nothing uninstalled — and the answer does not depend on
what this host happens to have installed, which is the property the old
list-comment approach could never have. The two probes speak the same
three-field protocol, so the reading is shared (`_read_probe`) and the two
scripts cannot drift apart in how they report.

**The counted sweep.** The claim "every module under `src/paa`" was prose, and
prose became "137/137" and then became wrong. The check now compares the
enumerator's target set against `PACKAGE_ROOT.rglob("*.py")` — a *relation*
between two sets, with the one deliberate exclusion named and explained — and
asserts the probe count against the target count. It cannot go stale: adding
a module moves both sides together and stays green, and forgetting one makes
it red the same day.

### 3.3 Anti-vacuity, because a lock that cannot fail is decoration

Every new check carries a guard against passing for the wrong reason:

* the family-annotation check asserts that **every** family member
  contributed at least one class — so renaming a class cannot silently empty
  the check;
* the tripwire test asserts the attribute exists *before* installing the
  tripwire, so a reverted tree fails with the reason ("the module never binds
  the name") rather than with an `AttributeError` from `monkeypatch`;
* the blocked-probe check asserts the *failure*, so a module that stops
  needing its extra fails the check instead of quietly staying on the list.

## 4. Optimizations applied, and ones declined

**Applied — the tolerance list became a mapping, not a set.** A set of module
names cannot say *which* extra a module needs, so nothing could ever check an
entry. A mapping can, and now does. Cost: one extra subprocess per entry
(one entry today).

**Applied — one probe-reading routine instead of two.** `_read_probe` is
shared by both probes. Copy-pasting the parsing would have been the kind of
drift this file exists to prevent.

**Declined — converting the remaining 33 `TYPE_CHECKING` blocks.** Forbidden by
the brief, and out of scope. Their classification is in §7; the honest reason
to leave them alone is *scope*, with one genuine cycle and two genuine
reasons (an extra, and an import cost) underneath.

**Declined — including `paa/__init__.py` as a probe target.** It would have
made the count 137 and the claim "every module" literally true in a second
sense. It is not needed: the package root is a two-line module
(`__version__` only) and **every probe imports it as the parent package**, so
it is exercised 136 times over. The exclusion is written down with its
reason, and the count is asserted against the files on disk either way.

**Declined — a literal module count (`== 136`) in the test.** A literal is
what produced "137/137": a number that is true on one day and wrong the next
time somebody adds a file. The relation is the same strength and cannot rot.

**Declined — a general "every annotation in the tree resolves" check.** It
would be the strongest form of the convention, and it is **not** green: a
sweep over the tree finds **79** unresolvable annotations across 32 modules —
32 of the 33 remaining `TYPE_CHECKING` blocks produce at least one. A lock
that is red on arrival is not a lock; it is a report. The finding is in §6.
