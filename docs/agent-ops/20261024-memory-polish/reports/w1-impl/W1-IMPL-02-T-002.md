## 3. Root cause

The memory subsystem (creator, facts, cold-lake signals) is fully built and unit-tested, but the FastAPI edge exposes no recall surface. There is no code path from an HTTP request to `FactRepository.query_facts` / `search_facts_by_text`, no listing of `cold_lake_signals`, and no trigger for `MemoryCreator.run_batch`. The fix is additive surface: four routes reusing the existing repositories/creator, plus response schemas and reversal tests. No schema/persistence change (assumption A-004), no new contract.

## 4. Approach chosen and why

Follow the established edge patterns exactly:
- Reuse `_admit(runtime, essential=False)` on every route (same gate as `/signals`) -> 429 under overload.
- Build repo objects from `runtime.db` per route: `FactRepository(runtime.db)` for facts/search, `MemoryCreator(runtime.db)` for drain (mirrors `_signal_repo(runtime)` building `SignalRepository(runtime.db, cas)` at app.py:226-245).
- Define `response_model` pydantic schemas in `src/paa/api/schemas.py` (`FactView`, `SignalView`, `BatchReportView`), mirroring `SignalRequest`/`SignalResponse`.
- For `/memory/signals`, no repo list-by-status method exists (signals.py is read-only for this agent), so query `runtime.db.fetch_all` directly — a read-only operational-table access, consistent with `health` reading the ledger directly.
- NUL byte in `search` -> `ValueError` from `search_facts_by_text` translated to HTTP 400 (hostile input handled, not swallowed).

Alternatives rejected:
- Adding a `list_by_status` method to `SignalRepository`: rejected — signals.py is read-only per the write-set, and modifying it would be a contract change outside scope.
- Inline schemas instead of schemas.py: rejected — brief §6 and the `response_model` pattern favour schemas.py; keeps models importable without FastAPI (schemas.py docstring).
- Drain request body with `limit`: rejected — a query param `limit` (default 50) maps directly onto `run_batch(limit=...)` and keeps `POST /memory/drain` body-free per the brief.

## 8. Long-run test

- Source: routes derive entirely from existing repositories/creator; no new state, fully replayable/derivable.
- Load: backpressure gate sheds at `shed_load_depth`; `query_facts`/`search_facts_by_text` are bounded by `max_scan` (10_000) so no unbounded scan.
- Hostile input: NUL byte in `search` -> 400; empty `q` -> `[]`; unknown `entity` -> `[]`; invalid `status` value is passed to SQL as a bound param (no injection; SQL text is constant).
- Operability: read-only routes need no migration; drain reuses the atomic one-transaction-per-signal claim (`creator.py:832-860`), so concurrent drains are isolated.
- Reversal: reverting the four routes makes every route test 404 and fail; reverting `_admit` removes 429 behaviour.

## 9. Edge cases and abuse scenarios

Handled: empty result sets (`[]`), missing entity, NUL/query-injection (bound params + NUL refusal -> 400), cold-lake absent (n/a for read routes), 429 under queue overload.
Consciously not handled: pagination on `/memory/signals` (fixed 100-row cap, not in brief), per-route distinct essential flags (brief requires the same gate as `/signals`).
Unknown: whether `runtime_full`'s sqlite queue deterministically reaches `shed_load_depth` (50) under `TestClient` — to be verified by running the 429 test.

## 10. Performance and security considerations

- All SQL uses bound parameters; constant SQL text only (no LIKE here, so the `like.py` helper is not needed for these routes).
- `query_facts`/`search_facts_by_text` cap the scan at `max_scan=10_000` and rank in Python.
- Drain is bounded by `limit` (default 50, query param) and isolates failures per signal (`creator.py:791-830`).
- No secrets, keys, or PII introduced.
