## 3. Root cause

`MemorySettings` has no model-selection fields, so there is no config surface for an opt-in LLM fact extractor. The `FactExtractor` protocol + `MemoryCreator(extractor=...)` seam already exists precisely so an LLM extractor can be substituted later (creator.py docstring, lines 14-17); only the config knob and the tests are missing.

## 4. Approach chosen and why

- Config: add two plain `str` fields with default `""` to `MemorySettings`, following the `embedding_model` / `allow_hash_embedder_fallback` pattern (config.py:531-537): a docstring comment plus a default. Empty = rule-based default, so nothing changes for existing users (additive, backward compatible). No vendor hardcoding; provider is a separate string field read by the router layer (W2-IMPL-02's runtime wiring).
- Tests: a `ScriptedLLMExtractor` implementing `FactExtractor` is injected into `MemoryCreator(extractor=...)`. It returns structured triples or raises `MalformedSignalError`, and enforces the same containment bounds as the rule-based path (reusing creator's `_reject_suspicious` / `_scalar_to_text`) so the LLM path is proven to contain like the rule-based path. Tests drive the real `MemoryCreator` pipeline (one transaction per signal in `_commit`), asserting `hot_serving_active_facts` rows and `ProcessingOutcome`.
- Alternatives rejected: importing `LLMFactExtractor` from `creator.py` — `creator.py` is read-only/forbidden for me (T-003 is a separate task; brief §4-§5) and the class does not exist yet, so such tests could never be green in my scoped run. A custom pydantic-settings source to force `PAA_MODELS__*` → `memory.*` — rejected as scope creep / fragile (nested `memory` fields map to `PAA_MEMORY__*` by pydantic-settings mechanics; see §12).
