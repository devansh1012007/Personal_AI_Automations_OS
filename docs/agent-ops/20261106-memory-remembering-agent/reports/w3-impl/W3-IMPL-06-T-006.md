## 3. Root cause
Two independent sources of truth for λ/floor: `MemorySettings` (pydantic defaults transcribed from the RFC matrix once) vs `DOMAINS` (the executable matrix only the sweep reads). Changing `PAA_MEMORY__PRUNE_CONFIDENCE_FLOOR` or `PAA_MEMORY__DECAY_LAMBDA` changed nothing because no reader existed (INV §C06 root-cause chain, confirmed). A secondary architectural cause: `MemoryCurator` holds a settings object but constructs its default sweeper without consulting it, and the daemon's bare `DecaySweeper(db)` likewise can't see settings — so even a per-caller wiring fix would leave prod paths broken unless every construction site changed.

## 4. Approach chosen and why (alternatives rejected; addresses cause not symptom)
- **Floor: explicit-set-only override, two ingresses.** New `MemorySettings.explicit_prune_floor() -> float | None` (returns the value iff `"prune_confidence_floor" in model_fields_set`, else None). `DecaySweeper.__init__` gains keyword-only `prune_confidence_floor: float | None = None` (validated `[0,1]`); when None it lazily reads `get_settings().memory.explicit_prune_floor()`, and the sweep uses `self._prune_floor if not None else policy.prune_floor` inlined (never via `is_stale`, preserving the trap in brief §6). Immutable domains still skip; unknown domains still error. Rationale: makes the setting effective in prod without editing curator/daemon (outside write-set) — every existing bare construction auto-consults settings — while default deployments get byte-identical eviction. Explicit-`0.15` counts as an override (differs from per-domain floors); unset is inert. The lazy settings read (inside `__init__`, mirroring curator's lazy `get_settings` and decay's existing lazy `database` imports) avoids a settings→decay module-load cycle and keeps `sweep()` signature unchanged.
- **Alternatives rejected:** (B) global floor as fallback-only when a domain lacks one — every domain defines a floor (0 means never for several), so near-no-op, fails "effective" criterion. (C) deleting both fields — breaks existing `.env` files; plan chose deprecate-not-remove; `extra="ignore"` [VERIFIED config.py:597] would silently drop them instead (behaviour change hidden). Top-level `decay → config` import — safe graph-wise (config imports only core.types) but couples module load; lazy is strictly safer and matches house pattern (`curator.__init__`, `decay.idle_days` lazy imports).
- **decay_lambda: deprecate-not-remove.** `@model_validator(mode="after")` on MemorySettings warns with `DeprecationWarning` naming `paa.memory.domains.domain_policy` (DOMAINS matrix) as sole source iff `"decay_lambda" in model_fields_set`; value stays parsed but ignored (decay reads domains only — no code path reads settings λ, so "ignored" is structural, not a flag). Unknown domain keys: **warn-and-ignore** (brief's "must not crash load" rules out reject): a `UserWarning` lists the unknown keys and drops them from the dict so downstream never sees them; known keys load normally. The known-key set is derived lazily from `MemoryDomain` (single source; `test_every_domain_has_a_policy` guards drift) — lazy import because a module-level import would cycle via `memory/__init__` → curator → config (verified above). Unset stays silent (no warning for default deployments); `filterwarnings = ["error::DeprecationWarning:paa.*"]` [VERIFIED pyproject.toml:103] makes explicit use fail loudly in tests unless asserted — exactly the deprecation intent.
