## 3. Root cause

Unwired composition, not missing capability (plan §D, investigation §C04):
`MemoryCurator` and `DecaySweeper` were built and tested in isolation, but
no production code instantiated `MemoryCurator`. The daemon maintenance loop
was written as a bare `DecaySweeper.sweep()` and the curator was never
connected. Observable symptom: decay evictions happened (via the bare sweep),
but edge-prune, duplicate consolidation, orphan sweep, vector reconcile, and
analyze — and the budget/resume machinery — never executed in production. A
secondary wart: the bare sweep (and a naively constructed `MemoryCurator(db)`)
constructed `DecaySweeper` with `archive_writer=None`, so evictions deleted
rows without the cold-lake summary the `DecaySweeper` docstring promises
[VERIFIED src/paa/memory/decay.py:131-136] — pre-existing in both paths; C04
does not worsen it and the gap is documented (§14).

## 4. Approach chosen and why (alternatives rejected; addresses cause not symptom)

**Chosen: replace the bare sweep with a curator tick inside the existing
maintenance task, keeping the 6h `maintenance_interval` cadence, budget, and
resume contract.**

- [VERIFIED src/paa/daemon.py:166-178] `_maintenance_loop` now sleeps one
  `maintenance_interval`, calls `await self._run_curation_tick()`, and sleeps
  again. The tick lives in the maintenance task only, supervised by the
  existing `_supervise("maintenance", ...)` wrapper [VERIFIED
  src/paa/daemon.py:71] — ingestion latency is unaffected by construction.
- [VERIFIED src/paa/daemon.py:196-255] `_run_curation_tick()` (appended at the
  end of the file so earlier line numbers shift minimally — see the docs-lock
  note in §12):
  - `settings = self._rt.settings.memory` and
    `budget = settings.curation_max_runtime_hours * 3600.0` — existing config,
    no new knob (brief §3). Budget is passed explicitly to `run_maintenance`
    so the tick's budget is observable in logs and capturable in tests.
  - `MemoryCurator(self._rt.db, settings=settings,
    vector_store=self._rt.vector_store,
    archive_writer=getattr(self._rt, "archive_writer", None))` — settings and
    vector store from the real runtime; `archive_writer=None` is the verified
    degraded value (Runtime exposes none; `SignalRepository` needs a
    `BlobStore` Runtime also does not expose). INVARIANT: a `None` vector
    store must not fail the tick — reconcile no-ops [VERIFIED
    src/paa/memory/curator.py:278-279] and the other five phases run (pinned
    by `test_maintenance_tick_works_without_vector_store`).
  - Resume: the tick passes `start_phase=self._curate_next_phase` (instance
    state, init `None` [VERIFIED src/paa/daemon.py:62]) and after the pass
    sets `self._curate_next_phase = report.stopped_early_at` [VERIFIED
    src/paa/daemon.py:252]. A full pass clears it; a budget stop resumes at
    the stopped phase. This preserves `run_maintenance`'s own resume API
    (brief §6: "Cursor phase order + resume ... preserve it") and fixes the
    investigation's starvation risk (discarded `stopped_early_at` re-runs
    from DECAY forever).
  - Observability (R3): every tick logs `daemon.curation_started` (budget +
    start phase) and `daemon.curation_completed` with the full
    `report.summary()` counts [VERIFIED src/paa/daemon.py:243-254]. The
    curator's own `curator.maintenance_completed` log still fires; the
    daemon log makes the tick attributable in the daemon namespace.
  - Degrade-never-raise, no double-run: **construction** failure (including
    settings/curator wiring) is caught and logged as
    `daemon.curator_unavailable`, then exactly one bare
    `DecaySweeper.sweep()` runs and the tick returns `None` [VERIFIED
    src/paa/daemon.py:231-242]. A **`run_maintenance`** exception is *not*
    caught, so it propagates to `_maintenance_loop`'s
    `except … log.error("daemon.maintenance_failed" …)` [VERIFIED
    src/paa/daemon.py:176-177] and no fallback sweep runs — running the
    sweep after a partially executed curator pass would double-execute decay.
    The daemon loop stays alive either way (supervisor + loop-level catch).

**Rejected alternatives:**

- *Keep the bare sweep + add a separate weekly curator job (investigation

  more ops surface; no deploy surface exists to attach it to (Q1).
- *CLI one-shot (`paa memory curate`) + operator cron (option B):*

- *Wire `maintenance_interval` from `MemorySettings.decay_sweep_interval_hours`
  in this change:* rejected — `config.py` is the single-writer C06 hotspot
  (00-mission.md:30); the brief says "respect existing cadence (verify which
  drives the loop; document)", not rewire. Documented in the loop comment +

- *Synthesize an archive writer from `SignalRepository(db, BlobStore)`:*
  rejected — Runtime exposes no `BlobStore` either, and inventing a writer

## 9. Edge cases and abuse scenarios (handled / not handled / unknown)

Handled (with test or code evidence):

- `vector_store=None` → tick completes, reconcile no-ops (§7 test 2).
- Curator construction raises → one bare sweep, warning log, `None` return,
  daemon alive (§7 test 3).
- `run_maintenance` raises → propagates, loop logs `daemon.maintenance_failed`,
  no fallback double-run (§7 test 4). The supervisor restarts the loop on
  unexpected error [VERIFIED src/paa/daemon.py:99-106], so even a tick that
  escaped both catches cannot kill the daemon.
- Budget stop (`stopped_early_at`) → next tick resumes there, not at DECAY
  (§7 test 5). A full pass clears resume.
- Empty DB → curator phases match zero counts and complete; tick logs once
  per interval (same cost as the old bare sweep + five cheap no-op scans).
- Unknown domain rows → skipped, never deleted (curator decay path).

Not handled / deliberately out of scope:

- `archive_writer` archiving on eviction still degraded (`None`) — no
  cold-lake summary is written. Restoration needs a wired writer (FINDING
  §13), not a guess here.
- Persisted resume across daemon restarts (in-memory only) — restart
  re-runs from DECAY; a very large store + repeated budget stops + restarts
  could still starve late phases. Persisting `stopped_early_at` in the
  ledger/snapshot would need a recovery rule (AGENTS.md replayability
  invariant) — follow-up, not this change.
- Changing `maintenance_interval` default (6h) or wiring
  `decay_sweep_interval_hours` into it — config hotspot C06's call.

## 14. Known limitations, risks, rollback notes

  SQLite-tested phase bug (edge/orphan/consolidate) could delete hot-serving

  not interrupted by `stop()` mid-phase; shutdown waits for it (pre-existing
  sweep behavior). Budget bounds it.
