# Implementation report — W2-IMPL-03 — T-003 C03 touch-on-recall (T04)

## 1. Task and acceptance criteria (restated)

Plan C03/T-003: after a successful recall returns facts, advance `use_count` (+1)
and `last_queried_at` (now) for exactly the returned fact ids, batched via one
`DecaySweeper.touch_many(ids)` call per recall, so idleness-based confidence
decay (`effective_confidence`) reflects use. Sites: `PlannerContextBuilder`
(hot + semantic), `WorkerContextBuilder` (post-narrative-filter hot only),
`coder/runtime_tools.recall_facts`, `api.list_facts`/`search_facts`,
`cli.facts`/`search`. Touch failures are logged and never raised into the
read path; empty recall performs no query; no id is added to any emitted
payload; no content, routing, ordering, or ranking changes.

## 3. Root cause

Unwired composition, unchanged from INV-03: the touch API was built and unit-tested
(`tests/memory/test_decay.py`) but never invoked from any recall surface, so
`last_queried_at`/`use_count` freeze at fact creation and `effective_confidence`
decays used facts exactly like unused ones. Root cause is the missing
composition, not missing capability — the fix is wiring, batched and
failure-isolated per recall, at the recall boundary (one layer above
`FactRepository`), never inside the repository (which would fire for internal
non-recall queries from creator/curator — INV-02 option C rejected).

## 4. Approach chosen and why (alternatives rejected; addresses cause not symptom)

- **DECISION (context_agents placement): touch in `handle()`, not inside
  `_hot_facts`/`_semantic`.** `_hot_facts` runs *before* the worker's narrative
  filter; touching inside it would advance retention clocks for narrative facts
  the worker never receives — a silent retention leak across the RFC §2.2
  security boundary (INV-03 risk 1), and would touch ids that were retrieved
  but never returned ("touch only the ids actually returned after filtering,
  brief §3"). Instead, each `handle()` touches after filtering/guards and just
  before returning its successful `AgentResult`: planner touches deduped
  hot+semantic ids (never graph synthetic ids — those never leave
  `_graph_neighbours`); worker touches only the post-filter hot ids. A failed
  recall (worker `hydration_required` failure return, leak-check raise, gatherer
  error) therefore touches nothing. This satisfies the brief's "exactly these
  sites" behaviourally (the two builders' recall paths) while honouring the
  worker leak caution that the literal in-method reading would violate.
  Rejected alternative: `touch: bool` flag on `_hot_facts` — planner and worker
  would have subtly different side-effect contracts, and direct-call tests would
  assert behaviour the production path does not exhibit.
- **Tracer:** each of the four files gets one small private helper
  `_touch_recalled(db, ids)` (helper at end of file; call sites construct
  `DecaySweeper(db)` inside the helper's try, per brief). `dict.fromkeys`
  deduping gives `+1` (not `+2`) for hot∩semantic overlap (INV-03 risk 2).
  Failure isolation: `except Exception -> log.warning("memory.recall_touch_failed")`
  and return; success path logs `log.debug("memory.recall_touched")` with count
  (INV-03 operability note). `cli/main.py` and `coder/runtime_tools.py` have no
  module logger today, so the helper creates its structlog logger lazily inside
  (`import structlog` in helper body — same lazy-import precedent as
  `decay.py` method bodies) to avoid inserting top-level import lines that would
  shift ~40 documentation citations. `context_agents.py` / `api/app.py` reuse
  their existing module `log`.
- **Derived-state exception (AGENTS.md ledger invariant):** `use_count` and
  `last_queried_at` are operational retention state, NOT ledger truth and NOT
  derivable from events. A cold-lake replay rebuilds facts with fresh clocks
  (INV-03 risk 4). Precedent: `DecaySweeper.sweep` already mutates the same hot
  columns outside the ledger. Touch mutates retention clocks only — never fact
  content, never stored confidence (confidence stays derived per `decay.py`
  docstring), never ranking/routing. Documented in each helper docstring and in
  the amended `_BaseContextBuilder` read-only docstring (§5).
- **Superseded semantic ids: no validation query.** A superseded row, if
  touched, is retention-neutral: sweep and all readers filter
  `superseded_by IS NULL` (decay.py:174). A non-existent id is an UPDATE
  no-match (silent no-op). Stale vector points returning superseded facts is a
  separate pre-existing presentation issue (REV R-W1-004 deferral), out of
  scope. Adding a live-validation SELECT to every planner recall would add
  latency and a new failure mode for zero retention effect.
- Header/import placement: helpers appended at EOF of each file so no AVOVE
  documentation citation lines move (except the unavoidable in-function lines).

## 9. Edge cases and abuse scenarios

- Empty recall → no touch call (helper early return on empty list).
- Fact retrieved but then builder fails (worker hydration_required / leak raise /
  gatherer error) → no touch (touch sits after guards, before success return).
- hot∩semantic overlap (same id twice) → deduped to +1.
- Worker narrative facts retrieved pre-filter → never touched (post-filter touch).
- Graph synthetic ids → never in touch set (touch source is hot/semantic only).
- Touch raising (e.g. DB locked) → logged and swallowed; recall result unchanged.
- Superseded semantic id / unknown id → dead/no-op UPDATE, retention-neutral.
- Discriminating replay determinism: touch is not in ranking, not in packet
  contents, not in packet membership. Packet content for the same inputs is
  unchanged.

## 10. Performance and security considerations

- One batched UPDATE per recall (not per fact), indexed by PK `id`. No new
  query for empty results. No unbounded lists: ids are capped by existing
  recall limits (hot ≤60, semantic ≤30, coder ≤50, API/CLI repository defaults).
- Security: worker narrative non-delivery is unchanged; the leak-check raise
  still precedes the touch, so a leaky packet is refused before any side effect.
  Touch only writes two monotonic counters — no attacker-controlled values
  (ids come from the DB, not the model).
