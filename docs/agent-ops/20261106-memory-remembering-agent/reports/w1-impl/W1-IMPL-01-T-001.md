## 3. Root cause
Embedding substrate built but never composed in `Runtime`:
1. `_build_memory_creator` was written to wire only the extractor; the `_try_vector` pair computed in `Runtime.build` never reached it, so every production `MemoryCreator` had `embedding_sink=None` and `_enqueue_embeddings` early-returned.
2. Facts committed while sink absent/erroring stay `pending` (DB default) with no loop revisiting the partial index.
3. Writer/reader payload key sets mismatch, so even a wired sink produced empty-content semantic hits.

Fixing only (1) leaves pre-existing backlog; fixing only (2) drains into a `None` sink. Must land together (plan ordering C01→C02). Payload alignment (C01b) is required for acceptance "semantic hits return non-empty content".

## 4. Approach chosen and why (alternatives rejected)
- **C01b producer-side alignment (extend payload, keep reader):** added `object_value` (from `Fact.object_value`), `confidence` (from `Fact.confidence`, decayed), `importance` (from `Fact.importance`) to `VectorEmbeddingSink.enqueue` payload, keeping all 5 original keys. Old points without new keys still read with reader defaults (0.8/0.5). Rejected alternative (change reader to use `statement`): reader is READ-ONLY in this wave (brief §4), and `object_value` is the field `_semantic` promises as `content`. Producer alignment is additive and backward-compatible for readers.
- **C01 keyword-only threading:** `_build_memory_creator(..., *, vector_store=None, embedder=None)` + call-site pass-through in `Runtime.build`. DECISION documented in docstring: threading the already-built `_try_vector` pair avoids double-constructing the store (Qdrant local path / numpy load) and reloading the embedder model; keyword-only defaults keep existing 3-positional-arg test calls unchanged. Rejected: rebuilding inside the function (double init cost, risks two stores disagreeing); required-real-embedder (breaks minimal installs, contrary to D2a degrade-never-raise).
- **C02 `drain_pending_embeddings(limit=100)->int`:** delegates to `pending_embeddings` order (never OFFSET), single `sink.enqueue` batch (respects SentenceTransformer `asyncio.Lock` serialisation), `mark_embedded` only with default `indexed`. Sink errors caught → log `memory.embedding_drain_failed`, return 0, rows stay `pending` (never terminal `failed`). Sink-absent/empty logged as `memory.embedding_drain` with `pending`/`indexed` counts. Called after `run_batch` in daemon ingestion loop, `POST /memory/drain`, and `paa memory drain`; each call site wraps in try/except (daemon: `daemon.embedding_drain_failed`, api: `api.embedding_drain_failed`) so a drain hiccup can never stall ingestion or fail the drain report. Rejected: folding into `run_batch` (changes its contract/fixtures, couples signal ETL to embedding budget); daemon-only drain (leaves operator API/CLI paths broken).

What was NOT done: no change to taxonomy/schema/config, no `sentence-transformers` requirement, no edit to reader (`context_agents.py`), `facts.py`, `config.py`, schema files, `pyproject.toml`/CI.

## 8. Long-run test: Source / Load / Hostile / Operability / Reversal
- **Source:** `process_signal` still commits fact + signal status atomically (`_commit_with_retry`); embedding is post-commit best-effort. Crash between commit and `upsert` leaves `pending`, recoverable by drain — never a lost fact. Drain adds no new write path: facts already committed; drain only writes the derived `embedding_status` + vector point.
- **Load (100x):** each drain is one bounded batch (`LIMIT 100`, oldest-first; daemon cadence 1.0s, `limit=25` signals + drain ≤100). 100x backlog drains in ≤100-fact embed batches; SentenceTransformer lock serialises embeds (single `embed` call per batch, no parallel spam). Concurrent drains of the same batch are idempotent: same point-id upsert + same-id `mark_embedded` UPDATE (no dup accumulation, no fact loss).
- **Hostile input:** drain facts come from `pending_embeddings` (already-committed rows), no new untrusted input. Embedder text is `Fact.statement` built from extractor output already bounded by `MAX_VALUE_CHARS=8192`/`MAX_CANDIDATES=200` containment; oversized/hostile payloads are malformed/quarantined before any fact exists. NUL/injection surface unchanged (no LIKE added).
- **Operability:** every drain logs `memory.embedding_drain pending=N indexed=M` (including sink-absent/empty); sink wiring logs `memory.embedding_sink status=wired embedder=<model_name>` / `status=degraded`. Observe backlog via `FactRepository.pending_embeddings()` count. Rollback = revert code commits; facts stay `pending` and re-drainable (no migration, derived data only).
- **Reversal:** reverting payload → round-trip test fails `'' != ''`; reverting drain method → 4 `AttributeError` failures; reverting runtime kwargs → wired test `TypeError`/sink-None (see §7).

## 9. Edge cases and abuse scenarios
- **Handled:** `limit <= 0` → 0 (no query); sink `None` → 0 with pending log; sink raises (embedder/store down, import failure returns `[]` inside sink) → 0, stays `pending`, logged; sink returns partial ids → only returned ids marked (others stay `pending` for next drain); empty pending → 0; `VectorEmbeddingSink` construction raises → degraded None + warning, boot succeeds; missing vector extra → `_try_vector` already returns (None,None) + warning, `_build_memory_creator` degrades.
- **Not handled (by design):** downstream `mark_embedded` DB failure propagates from `drain_pending_embeddings` and is caught at all 3 call sites (logged, ingestion/drain-report unaffected). Hash-embedder lexical-only limitation (R1) unchanged — paraphrase precision with hash vectors is a known degraded mode, not a code bug.
- **Unknown:** live Qdrant/Numpy behaviour at 100x under SentenceTransformer load not exercised (fakes only); `NumpyVectorStore` width agreement (384) relies on `_try_vector` factory pairing (same as context builders).
