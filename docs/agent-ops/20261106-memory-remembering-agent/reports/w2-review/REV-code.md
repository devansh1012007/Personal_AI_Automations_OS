## 4. Findings

### R-W2-001 [MAJOR] Planner/worker touch the candidate superset, not the delivered `packet.elements`
- Location: `src/paa/agents/context_agents.py:323` (planner) and `:387` (worker); the filter that creates the superset is `src/paa/context/gatherer.py:418-512` (`_candidate_pool` floors + `_pack` ceiling).
- Evidence: Planner touches `[e.id for e in hot] + [e.id for e in semantic]` [VERIFIED src/paa/agents/context_agents.py:323]. Gatherer then admits hot only if `confidence >= 0.70` [VERIFIED src/paa/context/gatherer.py:447-451, src/paa/config.py:190], semantic only if `relevance >= 0.75` [VERIFIED src/paa/context/gatherer.py:457-461, src/paa/config.py:187], dedupes by id with hot winning [VERIFIED src/paa/context/gatherer.py:444-465], and greedily packs under the ceiling [VERIFIED src/paa/context/gatherer.py:505-512]. `packet.elements` is `tuple(selected)` [VERIFIED src/paa/context/gatherer.py:573]. So four classes of never-delivered facts are immortalized: (a) hot facts below the confidence floor, (b) semantic hits below the relevance floor, (c) hot∩semantic dedup losers (harmless duplicate, dedup'd anyway), (d) over-budget tail. Worker has the same shape minus (b): [VERIFIED src/paa/agents/context_agents.py:387] touches post-narrative-filter `hot`, but the gatherer still applies the confidence floor and ceiling.
- Why it matters: This is the exact failure C03 was built to fix, in mirror image. Decay's contract is "idle time since last *read* by the context builder" [VERIFIED src/paa/memory/decay.py:39-51]. A fact that was retrieved but filtered or packed out was *not* read by the model, and touching it resets `last_queried_at` anyway [VERIFIED src/paa/memory/decay.py:264-275]. Plan risk R2 ("touch-on-read makes facts immortal") is amplified: the model can be starved of a fact by the floor/packer while the fact's clock keeps resetting, so it never decays. The worker narrative test (`test_worker_touches_only_the_facts_it_delivers`) proves the filter axis (narrative stays 0) but no test proves the floor/packer axis (a confidence-0.5 fact that the gatherer drops would still be touched — a test asserting it stays 0 would fail on current code). Handle-level placement is correct (R-W2-001 is not a placement complaint); the source list is wrong.
- Recommended fix (root cause): Touch the delivered set. After `packet = self._gatherer.compile(...)`, touch `[e.id for e in packet.elements]` filtered to real fact ids (exclude `graph:` synthetic ids, e.g. `not e.id.startswith("graph:")`). Best place is to touch from `packet.elements` at both `handle()` call sites; keep `dict.fromkeys` dedupe. Add the missing regression tests: (i) low-confidence hot fact (`confidence < 0.70`) that the gatherer drops keeps `use_count == 0` after planner handle; (ii) over-budget tail fact keeps `use_count == 0`. API/CLI/coder call sites need no change (touch set already equals returned set, R-W2-001 is context-agents-only).

### R-W2-002 [MAJOR] First production curator tick deletes permanently — no preview, and prune/consolidate/orphans never archive
- Location: `src/paa/daemon.py:196-254` (tick enables six phases at once); delete phases `src/paa/memory/curator.py:193-268`.
- Evidence: The tick runs DECAY → PRUNE_EDGES → CONSOLIDATE → ORPHANS → RECONCILE_VECTORS → ANALYZE on the first 6h interval with no dry-run, no count-threshold, no enable flag and no backup [VERIFIED src/paa/daemon.py:172-178,196-254]. Decay with `archive_writer=None` deletes with `archived == 0` [VERIFIED src/paa/memory/decay.py:235-236] (docstring honestly notes it [VERIFIED src/paa/daemon.py:208-214], but "documented" is not "safe"). Prune/consolidate/orphans have no archive path at all — even with a writer wired, those deletes are unrecoverable except via cold-lake replay of facts (relationships have no cold-lake source at all). Consolidate also drops losers' `source_signal_id` provenance (survivor keeps only its own) [VERIFIED src/paa/memory/curator.py:239-254]. Report counts are logged after the fact [VERIFIED src/paa/daemon.py:253], which detects over-deletion only post-mortem.
- Why it matters: The old daemon already decayed in prod, so DECAY is not new. The three new delete paths are. If any has a scale/threshold surprise on a real DB (e.g. `relationship_prune_floor=0.10` [VERIFIED src/paa/config.py:243] applied to weights on a different scale, or a duplicate-grouping surprise), the first tick deletes those rows with no preview and no cold-lake summary. Plan R3 already names this ("snapshot cold lake before enabling extra phases"); the code as landed gives the operator no mechanical preview to do that measurement against. This is accepted as a MAJOR operational risk, not a code-correctness BLOCKER (the curator logic itself is pre-existing and tested).
- Recommended fix (root cause): Before the first real tick, dry-run counts (or log the phase counts at `info` per phase, not just totals) and take the R3 cold-lake snapshot. Code follow-up: either wire a real archive writer (needs `Runtime` to expose a `BlobStore`/`SignalRepository` — out of wave-2 scope) or gate the three never-archived delete phases behind an explicit operator opt-in for the first runs. At minimum, add an empty-index guard to orphans (R-W2-004) so the first-run failure mode is a logged skip, not a wipe.

### R-W2-003 [MINOR] `MemoryCurator` import is outside the fallback `try` — import failure skips the sweep (and the report's claim is false)

### R-W2-004 [MINOR] Orphan purge has no empty-index guard — one empty `entity_index` wipes all facts
- Location: `src/paa/memory/curator.py:264-267`.
- Evidence: `DELETE ... WHERE entity_id NOT IN (SELECT id FROM hot_serving_entity_index)`. If `hot_serving_entity_index` is empty (truncated rebuild, failed entity ingestion, admin edit), `NOT IN (empty)` is true for every row → all facts deleted in one statement. FK `PRAGMA foreign_keys=ON` [VERIFIED src/paa/storage/relational/database.py:263] makes this unreachable via the normal creator path, which is why the phase exists only as belt-and-braces [VERIFIED src/paa/memory/curator.py:257-263] — but a belt-and-braces delete that can wipe the table when its guard table is empty is itself a hazard. `NOT IN` NULL trap does not apply (entity `id` is PK, non-null), so only the empty-set case matters. No test covers it (the orphan test seeds one FK-off row against a populated index).
- Why it matters: R3 first-run is the moment when an empty/partial index is most plausible (partial migration, rebuild in progress). The delete is a single statement with no row-count precheck.
- Recommended fix: Guard the phase — if `SELECT COUNT(*) FROM hot_serving_entity_index` is 0, log a warning and skip (report `errors += 1` or `orphans_removed = 0`). Add a regression test: empty index + facts present → zero deletions.

### R-W2-005 [MINOR] "Budget caps worst case at 7200s" is false — overshoot is one whole phase; resume is in-memory and can wedge
- Location: `src/paa/memory/curator.py:172-179` (between-phase check); `src/paa/daemon.py:62,243,252` (in-memory resume).
- Evidence: Deadline is checked only between phases [VERIFIED src/paa/memory/curator.py:172-179]; docstring admits phases are atomic. Consolidate re-reads every duplicate group N+1 style with no batch bound [VERIFIED src/paa/memory/curator.py:222-254]. Worst case is `7200s + one phase duration`. Resume lives in `self._curate_next_phase` only [VERIFIED src/paa/daemon.py:62]; a restart resets to DECAY (documented), and a wedged `start_phase` retries the same phase every tick forever if the failure is outside the per-phase catch (e.g. `_PHASE_ORDER.index` on an invalid value).
- Why it matters: Operator planning "curator never runs longer than 2h" is wrong; shutdown mid-phase cancels cleanly (CancelledError is BaseException, escapes the `except Exception` handlers — verified safe), but a multi-hour sweep/consolidate still blocks the maintenance task and holds SQLite write locks (10s busy timeout [VERIFIED src/paa/storage/relational/database.py:130] bounds the wait for ingestion, but ingestion will log `ingestion_failed` under contention). The 6h interval > 2h budget means overshoot rarely misses the next tick, which is why this is MINOR, not MAJOR.
- Recommended fix: Correct the §10/ops claim to "7200s + one phase" and bound consolidate (keyset/batch over groups, or a per-phase time guard that skips consolidation when little budget remains). Persisting resume needs a ledger/snapshot recovery rule (AGENTS.md replayability) — correctly deferred, not a silent hack.
